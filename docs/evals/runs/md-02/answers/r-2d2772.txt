### machinery-domain.Y1
Work-type W1 (build-a-slice), domain D5 (coordination-substrate).
D5's subjectSurface covers "the WorkGraph / lifecycle / messaging machinery as subject - its source, and the blueprints, gates, leases and queue it runs" (domains/D5-coordination-substrate.md). D0 says the same thing: "a coordination change, to its code or to the state of the work itself, resolves to coordination" (domains/README.md, Territory).
W1 is "An engineer implements one scoped increment against a given slice/design spec" (work-types/W1-build-a-slice.md). Its domainEligibility includes coordination-substrate, and D5 is "free for the types that act on any surface, including those that build and ship the machinery's source" (D5, Freedom).
Under the tie-break rule, "For a code change, the surface it alters is where its diff lands" (domains/README.md), and here that is the coordination machinery's source.
GUESS: if the gate type first needs a design of record, that earlier node would be W14 (design-a-contract-or-invariant), and W1 would depend on it ("dependsOn its design/spec node", W1 compositionHooks).

### machinery-domain.Y2
Work-type W2 (fix-a-bug-or-repair), domain D4 (authority-governance).
D4's subjectSurface is "the source of the machinery that enforces it, and SEAL, CODEOWNERS, decisions, class-grants" (domains/D4-authority-governance.md). D0 says "a ruling, and a change to the code that enforces rulings, resolve to authority" (domains/README.md, Territory).
The bad merge is only where the bug shows. The tie-break rule puts the work on "the surface the work alters, not the surface whose benefit motivates it", and the diff lands in the class-grant enforcement code, so the domain is D4, not D5 and not D1.
W2 lists authority-governance in its domainEligibility. But its trigger is "a `bug` substrate entity" (work-types/W2-fix-a-bug-or-repair.md), and W0 says W2 applies "where a defect has been filed" (work-types/README.md, Gaps recorded).
If no bug has been filed, the corpus routes the change to W1 instead. GUESS: in practice the bug should be filed first, so the fix is a W2.

### machinery-domain.Y3
D0 states the general rule: "A part's domain holds its source and its live state together. A part splits into more than one domain only where work on one portion is proved differently and the split has been found needed" (domains/README.md, Territory).
The product was split because "the evidence differs: its source resolves against code and CI, and its data against the records themselves, before and after." D7 entered as a recorded gap: delivery-code "holds the source and distribution the estate, and neither holds the records."
The control plane holds two domains for a different reason: "it is two machineries, each an engineered product". Each machinery's code and live state stay in one domain: "a coordination change, to its code or to the state of the work itself, resolves to coordination."
The corpus also says "a part not yet split may be on the same terms." So the coordination machinery is not unified on principle. It shares one domain because no need to split it has been found yet.
NOT SETTLED: the corpus does not show that coordination's state is "proved differently" from its code in any way that differs from the product's case. D5's own evidence list puts source/PR/CI next to "before/after graph topology", which looks like the same shape as D1 versus D7.

### machinery-domain.Y4
Domain D6 (knowledge-methodology). Its evidence resolves against "mission-kit entries and the tools that check them" (domains/D6-knowledge-methodology.md), and D0 describes the knowledge part as "its entries and the tools that check them" (domains/README.md).
For the work-type, W0 says: "Work on the knowledge corpus is building on its domain, and has no work-type of its own. Adding or revising an entry or a tool is a build slice, W1, or a fix, W2, where a defect has been filed" (work-types/README.md, Gaps recorded).
So revising the entry is W1. Fixing the checker is W2 if a defect against it was filed, and W1 if not. Both W1 and W2 list knowledge-methodology in their domainEligibility.
NOT SETTLED: the corpus does not say whether the two changes together form one node or two. GUESS: one W1 slice if they make one scoped increment, or a W1 for the entry plus a W2 for the checker if the checker bug was filed separately.

### OBSERVATIONS
- The Y3 justification depends on "found needed" rather than a stated difference in evidence. D0 explains the product split by "source against code and CI, data against records before and after", but D5's evidence list (source/PR/CI plus before/after graph topology and WorkItem state) has that same two-part shape. The stated discriminator therefore does not by itself separate the two cases.
- Y2 can be argued either way. Merge gating is a "gate", and D5 claims gates, which tempts a D5 placement. D0's control-plane sentence ("a change to the code that enforces rulings, resolve to authority") and D4's subjectSurface (class-grants) settle it as D4. W0 also says SEAL attest_evidence implements the composition rule, which blurs where the governance machinery ends and the coordination machinery begins.
- W2 needs a filed bug entity. The questions say "a bug" and "fixes" without saying whether anything was filed, so the W1/W2 choice depends on a fact the scenario does not give.
- D1's title in this corpus ("the shipped product's codebase") differs from the D1 title in a version of INDEX.md I had seen elsewhere ("the product/service codebase"). Within the corpus, INDEX.md, D0's index and D1 agree.
