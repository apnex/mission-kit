### OBSERVATIONS
1. W8 contradicts W0. W8's Evidence section says that if the roster collapses attester and executor, "the seed fails or downgrades to `kind:review`". W0 constraints 2 and 9 say "a same-agent review never stands in". The W8 wording can be read as permitting a same-agent review.
2. W22 contradicts itself. Its frontmatter has `evidenceAuthority: verifier-attestation`, while its compositionHooks says "plain kind:review, not verifier-attestation per README constraint 2".
3. R3's `evidenceAuthorities: [verifier-attestation, review]` uses `review`, which is an evidence kind. It is not one of the four evidenceAuthority values in the W0 schema.
4. The trait entries' "Axioms it brings into force" lists are written by hand and are not marked GENERATED. tools/check-traits.mjs only holds the applies-to enum to the trait filenames. I grepped tools/generate-index.mjs and tools/*.sh and found no check of those lists against applies-to. They agree today, but nothing keeps them aligned. This contrasts with the domain/work-type lists, which are generated.
5. Domain "Axiom alignment" sections (D1 citing A1, D7 citing A1/A9) read like binding claims ("a domain cites the axioms it must satisfy"), but A0 says applies-to is the only binding field. No entry says outright that a domain's citation is conditional on the axiom already being in force. That ambiguity is what P2 tests.
6. D3's subject surface names specific tools ("ois/pi/claude launchers"). D0's Faults already records this as "the domain named after a tool".
7. INDEX.md tells readers to resolve links against GitHub when no checkout exists. For this run I used only the provided corpus copy.
