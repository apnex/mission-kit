### s0.Q1
The corpus names this as a population fault: "The forked enforcer. Two tools holding one rule, disagreeing at the edges. This is why a rule names exactly one." (style/README.md, Faults).
The remedy is stated under Enforcement boundary: "An enforced rule names exactly one tool ... One rule, one tool, and that tool owns both the check and the fix, so a rule cannot be reported by one implementation and refused by another."
The pairing is declared in each rule's `enforced-by` frontmatter, and `tools/check-enforcers.sh` checks it in both directions: a rule naming a missing tool fails, and so does a per-rule tool (`tools/sN-*`) that no rule claims.
So the fix is to collapse to one sovereign tool, named in the rule's `enforced-by`, and remove the other.
Limit: check-enforcers.sh matches one tool per rule-number prefix and one `enforced-by` line per rule, so it would catch a second `tools/sN-*` file. It would not catch a second checker living under another name, for example inside a general script. NOT SETTLED whether anything detects that case. GUESS: only review would catch it.

### s0.Q3
No, not by default.
style/README.md: "Style is gated on changed files rather than on the whole corpus. The corpus carries debt that predates the checkers, so gating the diff blocks new debt and converts the rest as sections are edited."
tools/check-all.sh runs the per-rule checkers (s6 s8 s10 s12 s13 s14) only on changed `.md` files. Those are files committed against the base (`--since REF`, default `origin/main`), plus staged, unstaged and untracked files. If no markdown changed, the style step passes.
A whole-corpus run is available through `tools/check-all.sh --all`. CI (.github/workflows/check.yml) does not use it; it runs `--since` the PR base or the push predecessor.
Non-markdown files are never style-checked. The other, non-style gates in check-all.sh (index generation check, schema tests, enforcer pairing and so on) are not restricted to the diff. The tools' own `*.test.sh` files also run every time, against fixtures.
The charter also lists converting all debt in one commit as a fault ("The corpus-wide sweep").

### s0.Q7
style/README.md "Faults" lists five:
(1) the forked enforcer: two tools hold one rule and disagree at the edges;
(2) the orphaned rule: a convention that nobody enforces and nobody reviews, "which teaches readers that the layer is decorative";
(3) the unscoped medium: rules for a non-document medium scattered among document rules with nothing grouping them;
(4) the work rule in style clothing: a convention that governs what the work does or records, filed where rule-appliers will not look;
(5) the corpus-wide sweep: all legacy debt converted in one commit, so no one can review the diff and a real change can hide inside it.
The criteria in "What earns an entry" imply other warning signs: rules admitted on aesthetic preference, and rules that live inside one document. NOT SETTLED as named faults. GUESS: they would count as unhealthy.

### OBSERVATIONS
- The S0 index states the split between tool-held and reading-only rules, and it agrees with each rule's `enforced-by` frontmatter and the "nine of fifteen" claim. I found no inconsistency there.
- tools/check-enforcers.sh only detects orphan tools that follow the `tools/s<N>-*` naming. A forked enforcer inside a differently named script would not be caught, so the "exactly one tool" guarantee is narrower than the charter's prose implies.
- The "unscoped medium" fault is ambiguous: it is unclear whether "a second" means a second rule for one medium or a second non-document medium.
- "The corpus-wide sweep" is listed under Faults, but it describes a single bad commit rather than a population property. E4 (entities/E4-charter.md) says Faults is "for population faults alone".
- tools/check-all.sh shows check-charter-shape.sh as suspended ("tracked as B17"), so charter shape is not currently gated.
