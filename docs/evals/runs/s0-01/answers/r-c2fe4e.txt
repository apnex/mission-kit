### s0.Q1
The corpus names this as a fault, "The forked enforcer. Two tools holding one rule, disagreeing at the edges. This is why a rule names exactly one." (style/README.md, Faults).
The Enforcement boundary section says: "An enforced rule names exactly one tool ... One rule, one tool, and that tool owns both the check and the fix, so a rule cannot be reported by one implementation and refused by another."
The pairing comes from each rule's `enforced-by` frontmatter, and tools/check-enforcers.sh checks it both ways: "a rule naming a tool that does not exist is a broken promise / a per-rule tool that no rule claims is orphaned".
So the fix is to collapse to one tool that the rule names in `enforced-by`, and retire or merge the other.
NOT SETTLED: the corpus does not say which of the two tools should survive.
GUESS: keep the tool whose behaviour matches the rule's stated predicate (and its tests), and fold the other's edge cases into it.
One caveat on the mechanism: check-enforcers.sh only finds orphans among `tools/s[0-9]*-*` names, so a second checker named differently would not be caught by it.

### s0.Q3
No, not by default. style/README.md says: "Style is gated on changed files rather than on the whole corpus. The corpus carries debt that predates the checkers, so gating the diff blocks new debt and converts the rest as sections are edited."
tools/check-all.sh agrees: "s6 s8 s10 s12 s13 s14 one sovereign checker per style rule, on changed files only". It collects changed `.md` files against `origin/main` (committed, staged, unstaged and untracked), and if there are none it prints PASS.

### s0.Q7
The Faults section of style/README.md lists five failure shapes:
(1) "The forked enforcer": two tools holding one rule and disagreeing at the edges.
(2) "The orphaned rule": a convention nobody enforces and nobody reviews, "which teaches readers that the layer is decorative".
(3) "The unscoped medium": rules for a non-document medium scattered among the document rules with nothing grouping them, where a second such rule should have triggered a sub-set.
(4) "The work rule in style clothing": a convention about what the work does or records, filed where rule-appliers will not look.
(5) "The corpus-wide sweep": converting all legacy debt in one unreviewable commit that hides a real change.
The admission criteria imply further unhealthy signs: entries based on aesthetic preference, single-document rules, and predicate-stateable rules left to prose, which "degrades to a matter of taste the first time two authors disagree". The Axiom alignment section adds that a population held mostly by reading is only as strong as its review.

### OBSERVATIONS
- style/S14-hydration-triggers-state-a-condition.md (line 55) says S14 "is enforced by `tools/check-style.sh --rule S14`". That tool does not exist in tools/. S14's frontmatter `enforced-by` and the S0 index name `tools/s14-hydration-triggers.sh`, and tools/check-tool-docs.sh calls check-style.sh the older tool. The S14 body is stale, and it is a small instance of the "forked enforcer" naming problem in prose.
- check-enforcers.sh detects orphan tools only by the `tools/s[0-9]*-*` naming pattern. A second checker for the same rule with a different name would not be flagged, so the one-rule-one-tool guarantee is narrower than the charter's wording suggests.
- The style gate depends on git diffs against `origin/main`. With no git context, the changed list is empty and the gate prints PASS (in check-all.sh, the git errors are suppressed with `2>/dev/null` and `|| true`), so a vacuous pass is possible. This is inferred from reading the script, not from running it.
- S0 "Gaps tested" says source code has no style rule, but the Territory's "each medium the corpus writes in" and the "unscoped medium" fault give no explicit placement for a future source-code rule. Q5's placement is therefore inferred.
- S8 is named "Code-block comments", which a reader could confuse with source-code comment style. It covers only code blocks in markdown.
