### system-boundary.S1
Only the launcher's axioms, which are the floor: A3, A4, A8, A9, A14 (axioms/README.md applicability matrix, `any-system` row; same tags in each axiom's `applies-to`).
The launcher has no traits: one operator watches it (not T4), no state (not T1), no model (not T5), one actor (not T3). E5 Boundaries says "A one-shot script with no traits is a system, bound by the axioms every system carries."
The launcher composes with the service through a declared interface that it honours ("nothing crosses ... except"), and E5 calls exactly this "Compose".
A0: "A system it only composes with, through a contract the change leaves as it was, is not altered, and its axioms do not bind." The service's axioms therefore do not bind this change.

### system-boundary.S2
The launcher's floor axioms plus the service's: A1, A3, A4, A5, A6, A7, A8, A9, A10, A13, A14. A2, A11 and A12 do not bind.
A0: a change answers to "any system whose contract with it the change alters". E5: "changing an unversioned interface alters every consumer at once, so the change answers to all of them immediately."
Service traits: stateful (T1, persistent state; that something acts on it is my inference from "holds persistent state"), multi-agent (T3, work handed between independent actors), autonomous (T4, no human in the synchronous loop). It is not declarative (T2) and not llm-in-the-loop (T5).
Per the T1/T3/T4 entries and the A0 matrix, those traits bring in A1; A5, A6, A7, A10, A13; and A7, A10, A13 (union rule, traits/README.md "Traits bind by union").
E5 also says: "Adding versioning to an interface you are changing moves it toward A3's limit and is encouraged, not required; if it is not done, the gap is recorded."

### system-boundary.S3
The service's full set: A1, A3, A4, A5, A6, A7, A8, A9, A10, A13, A14. The module on its own would carry only the floor, and that is a subset of this set.
E5 Contain: "A module inside a service is a system, and the service contains it, whether or not the module's interfaces are declared. A system has every trait any part it contains has."
A0: a change answers to "the system it modifies, every system containing it". E5 discriminator: "changing a module changes the service it sits in."
E5 "Why precision matters" names the error this rules out: "a stateful system escapes its own axioms by being described as stateless modules".

### system-boundary.S4
Only the library's own axioms, the floor: A3, A4, A8, A9, A14.
The interface and its behaviour do not change, so no consumer's contract is altered. A0: a composing system "is not altered, and its axioms do not bind."
E5: "Publishing a new version of an interface alters no consumer that has not adopted it; each adoption is a change to that consumer, and answers to that consumer's axioms; the component is not altered by being adopted."
E5 "Why precision matters" rejects the other reading: "a small shared library would carry the axioms of every system that uses it".
One caveat from E5: a declared version range ("any 2.x") is "adoption in advance", so a release within it alters every consumer the range binds. The scenario says each consumer adopts as its own separate change, so I read it as having no ranges. GUESS: if any consumer did pin a range that covers this release, that consumer's axioms would bind.

### system-boundary.S5
The launcher and service are one system with the traits of both, so the service's full set binds: A1, A3, A4, A5, A6, A7, A8, A9, A10, A13, A14.
E5 Boundaries: "Where one unit depends on another and nothing declares the boundary between them ... they are one system, with the traits of both." A0 says the same: "the axioms either unit would bring all bind".
Something else is wrong. The undeclared dependency "is itself a fault against A3, which requires units to interact only through declared contracts" (E5; A3 Mechanics, "Air-Gap Principle").
E5 also says this change owns the boundary: "A change that alters what an undeclared neighbour reaches into owns that boundary: declaring and honouring the interface is inside its scope, not optional."
So the fix belongs in this change: declare an interface for what the service takes from the log lines, and move the service onto it. Parsing log output is a "contract in fact, not a declared boundary" (E5).

### system-boundary.S6
It is defined in entities/E5-system.md, Definition: "A system is a unit of engineering with a boundary: what is inside it, and the contracts through which anything outside reaches it."
E5 adds that the boundary separates it from a neighbour "only where it is declared and honoured". Traits describe a system and axioms bind it. Systems relate in exactly two ways, contain and compose.
E5 Boundaries says a system is not by definition a repository, a deployment unit or a process, and it is not defined by size or traits. E5 also says "The organisation doing the work is a system."
E6 defines a component as "a system seen as a part of a larger system that contains it".

### OBSERVATIONS
- E5 says the organisation doing the work is a system with its own traits (stateful records, multi-agent). Its axioms govern how a change is made and recorded, but E5 says they are "not one of the systems the change alters". So the answers above leave out organisation-level axioms. A reader could still argue that A1 or the multi-agent axioms bind the S1/S4 work through the organisation.
- S1/S4: A0's scope rule says a change "touches" any consumer whose contract it alters, and a component it newly depends on. Neither applies here. That conclusion rests on reading "interface and its behaviour unchanged" as meaning no consumer depends on undeclared behaviour (for example timing or log output). If some consumer did, the S5 logic would apply to that pair (E5 "Declared against honoured", which is per pair).
- T1 asks whether anything would act differently if the record were wrong. The prompt says only that the service "holds persistent state", so stateful is a slight inference.
- E5's discriminator also says that, in the A3 sense, a bypass ends after the interface is "evaluated against the component's duty". This could also apply to S5 when choosing between declaring a new interface and adjusting one. NOT SETTLED which of the two is preferred when no interface exists yet.
- Minor: A3's Mandate says "Every module", and its Semantic Bit-Masking mechanic says interfaces are "versioned". E5 says versioning is "encouraged, not required". These are consistent under the asymptote reading in A0, but a pass-or-fail reader could see a conflict.
