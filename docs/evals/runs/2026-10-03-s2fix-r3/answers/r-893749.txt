### system-boundary.S1
Only the launcher's axioms: A3, A4, A8, A9, A14 (the `any-system` floor, axioms/README.md "Applicability matrix"; each axiom's `applies-to` frontmatter agrees).
The launcher has no traits: it holds no state (T1), has one actor (T3), an operator watches it so it is not autonomous (T4 "Not autonomous: an interactive session..."), it is not declarative (T2) and has no model in the loop (T5); E5 Boundaries says "A one-shot script with no traits is a system, bound by the axioms every system carries."
The service is not bound: A0 says "A system it only composes with, through a contract the change leaves as it was, is not altered, and its axioms do not bind", and E5 gives this exact case: "A launcher that hands sessions to a service through a declared interface composes with it."
Per E5, the organisation's own axioms govern how the change is made and recorded, but that is asked separately and is not part of "which systems a change answers to".

### system-boundary.S2
Both the launcher's and the service's axioms: A1, A3, A4, A5, A6, A7, A8, A9, A10, A13, A14 (not A2, A11, A12).
A0: a change answers to "any system whose contract with it the change alters", and E5: "changing an unversioned interface alters every consumer at once, so the change answers to all of them immediately."
The service is stateful (T1 -> A1), multi-agent (T3 -> A5, A6, A7, A10, A13) and autonomous (T4 -> A7, A10, A13); it is not declarative (no A2) and has no model (no A11, A12); add the floor A3, A4, A8, A9, A14.
E5 also says "Adding versioning to an interface you are changing moves it toward A3's limit and is encouraged, not required; if it is not done, the gap is recorded" - so if you do not version it, you must record that gap.

### system-boundary.S3
The service's full set: A1, A3, A4, A5, A6, A7, A8, A9, A10, A13, A14.
E5: "A module inside a service is a system, and the service contains it, whether or not the module's interfaces are declared", and A0: a change answers to "the system it modifies, every system containing it".
That the module holds no state on its own does not help: "A system has every trait any part it contains has" (E5), and E5 "Why precision matters" names the failure "a stateful system escapes its own axioms by being described as stateless modules".
The module itself, as a system with no traits, carries only the floor, which is already inside this set.

### system-boundary.S4
Only the library's axioms: A3, A4, A8, A9, A14 (it has no traits, so only the floor binds).
The ten consumers compose with it through a declared, versioned interface that does not change, so A0 says they are not altered; and E5 says "Publishing a new version of an interface alters no consumer that has not adopted it; each adoption is a change to that consumer, and answers to that consumer's axioms; the component is not altered by being adopted."
E5 "Why precision matters" rejects the opposite reading: "a small shared library would carry the axioms of every system that uses it".
One caveat from the text: "A declared version range - any 2.x - is adoption in advance: a release within it alters every consumer bound by the range". The question says each consumer adopts as its own separate change, so I take it that no consumer has such a range. If one did, the release would alter that consumer, and the change would answer to that consumer's axioms too.

### system-boundary.S5
The full union of both units: A1, A3, A4, A5, A6, A7, A8, A9, A10, A13, A14.
E5 Boundaries: "Where one unit depends on another and nothing declares the boundary between them... they are one system, with the traits of both", and A0 says "the axioms either unit would bring all bind". This holds even though no larger system containing both is declared, because E5 says this case "is not a third way of relating... and are treated as one".
Other things are wrong too. The undeclared dependency "is itself a fault against A3" (E5, A0; A3 Air-Gap Principle: "units interact only through declared adapters and contracts"). Also, E5 says "A change that alters what an undeclared neighbour reaches into owns that boundary: declaring and honouring the interface is inside its scope, not optional".
So this change must declare the interface and move the service onto it. GUESS: changing the format without that will probably break the service's parser at runtime.

### system-boundary.S6
It is defined in entities/E5-system.md: "A system is a unit of engineering with a boundary: what is inside it, and the contracts through which anything outside reaches it."
The boundary separates it from a neighbour "only where it is declared and honoured"; otherwise the two are one system for deciding what a change answers to.
Systems relate only by "Contain" or "Compose"; "Traits describe a system, and axioms bind it". A system is "Not a repository, a deployment unit or a process by definition" and "Not defined by size or by traits".
E6 adds that a component is "a system seen as a part of a larger system that contains it". E5 also says the organisation doing the work is itself a system.

### OBSERVATIONS
- Possible tension between A0 and E5 on S2: A0 says "work that touches a gap closes as much of it as the touch allows", where the touch is "the part the change already alters". A3 (Semantic Bit-Masking) asks for "versioned contracts", and the S2 change alters the interface itself. But E5 says adding versioning there is "encouraged, not required". E5 is the more specific rule, so I followed it, but a reader could argue that A0 requires versioning.
- E5's version-range rule says a release within a range "alters every consumer bound by the range". It does not say whether this still applies when the interface and behaviour are unchanged, as in S4. The text reads as yes, which conflicts with the intuition that nothing observable changed. NOT SETTLED for internals-only releases.
- E5 says a one-shot script is bound by "the axioms every system carries". A9 (Chaos-Validated Deployment) is on that floor, so it formally binds a watched one-shot launcher. The text does not settle what A9 demands of such a launcher.
- The axioms/README.md matrix matched the `applies-to` frontmatter of all fourteen axioms (checked).
