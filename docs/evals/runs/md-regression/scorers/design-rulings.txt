PROBE design-rulings.R1

Question:
In a long-running service operated by several independent agents who hand work to each other, module N calls internal functions of module T; no interface is declared between them. Your change to T alters a function N calls. What must your change do about N's undeclared reach?

Key:
Declare an interface for what N reaches and move N onto it - inside the change's scope, because the change alters what N reaches; it is not merely recorded and not optional. Had the change not touched what N reaches, the gap would be recorded.

Rubric:
2 for declaring and honouring the interface as in scope, with the reason that the change alters what N reaches. 1 for declaring it as optional or recommended, or recording it only. 0 otherwise.

--- answer a-33b6bde0 ---
Your change has to declare and honour the interface between N and T. That work is in your change's scope and is not optional. E5 Boundaries says: "A change that alters what an undeclared neighbour reaches into owns that boundary: declaring and honouring the interface is inside its scope, not optional."
Until that is done, N and T count as "one system, with the traits of both" (E5; A0 "What brings an axiom into force"), so your change answers to N's axioms as well as T's. The undeclared reach is also a fault against A3 (Air-Gap Principle: "no unit reaches into another's internals").
How it ends: first evaluate the interface against T's duty, then either move N onto the interface or adjust the interface to what N legitimately needs (E5 "Declared against honoured"; A3 "Bypass as Signal").
Declaring an interface while N keeps bypassing it "separates nothing" (E5).
Both modules sit inside one service, so your change also answers to the service's axioms, because a change answers to every system that contains what it modifies (A0).

Question:
Three separately deployed services, A, B and C, none containing another: A reaches into B's internals, and B reaches into C's internals, all undeclared. (1) You change something in A that only A uses. Does your change answer to C's axioms? (2) Instead, your change alters data that A takes from B and B itself takes from C. Does it now answer to C's axioms?

Key:
(1) No: the merge chains only through what the change can reach, and this change reaches nothing of C. (2) Yes, or at least it meets the condition under which the merge chains - the change reaches C through B.

Rubric:
2 for both cases with the reach reason (for case 2, 'it meets the chaining condition' counts). 1 for one case. 0 for 'always chains' or 'never chains'.

--- answer a-36f496af ---
(1) No. E5 Boundaries says: "The merge chains only through what a change can reach: if A reaches into B and B into C, a change to A is one system with C only when it alters something B takes from C." A change that only A uses alters nothing B takes from C, so C's axioms do not bind it.
It still answers to B's axioms, because A's undeclared reach into B makes A and B one system with the traits of both (E5; A0).
(2) Yes. The change now alters something B takes from C, which is exactly the condition E5 gives for the merge to chain. So the change is one system with C and answers to C's axioms as well.

Question:

Key:
Yes: a system has a trait if it or any part it contains passes the trait's test, so the service is stateful; the change modifies the service, so A1 binds it.

Rubric:
2 for both, with the contained-part rule (citing that a stateful system cannot escape by being described as stateless modules counts). 1 for the right answer without the rule. 0 otherwise.

--- answer a-e0d6ecc9 ---
Yes, the service is stateful. The module that writes records and later reads them back to act on them passes T1's test ("Does the system write something it will later read back, and would anything act differently if that record were wrong?"). Also, "A system has every trait any part it contains has" (E5 Contain; T0 "How traits compose").
Yes, A1 binds your change (A1 applies-to: [stateful]). A change answers to "the system it modifies, every system containing it" (A0), and the service contains the stateless module you changed.
E5 names the failure this rule prevents: "a stateful system escapes its own axioms by being described as stateless modules".
How much A1 asks of this change depends on its scope (A0): the change must not move the service away from A1's limit, and must close any A1 gap only as far as its own touch allows.

Key:
Yes: the organisation doing the work is itself a system with traits of its own; it holds state - records it writes, reads back and relies on - so A1 binds how the work is recorded, separately from the stateless tool.

Rubric:
2 for A1 binding the organisation's records, with the organisation-is-a-system reason. 1 for binding without the reason. 0 for 'nothing binds'.

The tool itself is stateless, so A1 does not bind it or the changes made to it. A1 governs "how the change is made and recorded", not which product systems the change alters (E5).

PROBE design-rulings.R5

Question:
While adding a small feature to component K, you notice K's internals tangle two concerns, and splitting them would give K's three consumers a cleaner interface. K's interface is not versioned. The split is within K's own duty. What do the axioms ask?

Key:
The new feature arrives as its own unit, composed with K, not bolted onto K. The split is encouraged as opportunistic improvement within K's duty - not mandated - including re-cutting K's seams and recomposing for its consumers; it is made as a change of its own, and since it changes K's interface, it answers to each consumer it alters.

Rubric:
2 for the split encouraged not mandated, and the consumers' axioms binding the interface change. 1 for one of the two. 0 for 'never modify K' or 'the split is required'. Mentioning the feature arriving as its own unit is credited, not required.

--- answer a-d86ee3d3 ---
The axioms encourage the split, and A0 says you are expected to weigh it, but it is not required. A0 limits the required improvement to "the part the change already alters to do its own work; restructuring beyond that, even inside the same component, is the encouraged improvement below, not a requirement." A3 "Composable by Default" encourages this exact move: "within the unit's own duty, fix it, fracture it, re-cut its seams and recompose it so it makes better sense for every consumer downstream - as a change of its own, answering to every consumer whose interface it alters." K's interface is unversioned, so the split "alters every consumer at once" and answers to all three consumers' axioms immediately (E5). E5 also encourages, but does not require, adding versioning, and says "if it is not done, the gap is recorded." Whether or not you split K, record the gap: A0 says "Either way the gap is recorded" and "Passing it silently is what the axiom forbids". If you defer it, record it with evidence and a revival trigger (RU3). The small feature itself must not add to the tangle (A3: "a change short of it adds none of them").

--- answer a-0e998f55 ---
The axioms ask you to weigh the split. They encourage it but do not require it, unless your feature already alters the tangled code. A0 says only "the part the change already alters to do its own work" is required, and "restructuring beyond that, even inside the same component, is the encouraged improvement ... not a requirement". An agent who sees the improvement "is expected to weigh doing it, not merely permitted to".
If you do it, make it a separate change. K's interface is unversioned, so the change alters all three consumers at once and answers to all of them immediately. Adding versioning is encouraged but not required, and if you do not add it, the gap is recorded (E5).
If you do not do it, record the gap with its evidence and a revival trigger (RU3). A0: "Either way the gap is recorded", and passing it silently is forbidden.
Whether to do it now follows A14's tangent test: the payback is near, the yield is captured, and the cost does not distract from the feature (A0).

You must do some things and are encouraged to do others. Required: your feature must not add to the tangle, because A0 says "new work never repeats a gap the axiom names". PROBE design-rulings.R6

Question:
Ten consumers depend on library L with a floating range, 'any 2.x', and use only L's declared interface. L publishes 2.4, which changes the behaviour that interface documents. Which consumers does publishing 2.4 alter?

Key:
All ten: a declared range is adoption in advance, so a release within it alters every consumer bound by the range, and answers to their axioms.

Rubric:
2 for all ten with the adoption-in-advance reason. 1 for all ten without it. 0 for none.

--- answer a-2a57281d ---
All ten consumers. E5 says: "A declared version range - *any 2.x* - is adoption in advance: a release within it alters every consumer bound by the range, whether or not the consumer's own files change." All ten float on any 2.x. Version 2.4 changes behaviour that the declared interface documents, so it alters the contract every one of them depends on. Using only the declared interface does not protect them here, because the interface itself changed. The rule that "Publishing a new version ... alters no consumer that has not adopted it" (E5) does not help them either, since the range counts as adoption. NOT SETTLED: whether a consumer whose lockfile pins an earlier 2.x still counts as "bound by the range". GUESS: if the lock holds a consumer on an earlier version, that consumer has not yet adopted 2.4, and it is altered only when the lock is refreshed.

--- answer a-c5329bce ---
Publishing 2.4 alters all ten consumers. E5 says: "A declared version range - *any 2.x* - is adoption in advance: a release within it alters every consumer bound by the range, whether or not the consumer's own files change."

The rule that "Publishing a new version of an interface alters no consumer that has not adopted it" (E5) does not help here, because the floating range counts as having adopted it already.
So publishing 2.4 answers to all ten consumers' axioms.
