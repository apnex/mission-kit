### component.C1
Your X fix answers to X and to every system that contains X, so it answers to the service (axioms/README.md: "a change answers to every system it alters... every system containing it"). The service "has every trait any part it contains has" (entities/E5-system.md). GUESS: Z's hidden in-memory state makes the service stateful under traits/T1-stateful.md, which would put A1 in force for it. Even so, Z is outside the fix's scope ("code that merely sits beside it, in the same file or module, is not touched"). It is also not adjacent, because X and Z share no declared interface (E6 "Adjacent against nearby"). So the fix only has to avoid moving the service away from A1, for example by adding no new hidden state. The Z gap "is recorded with its evidence and a revival trigger (RU3) rather than closed", since it fails the adjacency test and two days would "displace the goal" (A0). Y is adjacent in the higher-payback direction, because X stands on Y through a declared interface (E6, A0), so A0 says you are "expected to weigh" fixing it "not merely permitted to". It passes the A14 tangent test: near payback (it cost 20 minutes), captured yield, small cost. So the corpus supports closing it opportunistically, but not as a mandate, "as a change of its own" separate from the X fix, answering to every consumer whose interface it alters. "Either way the gap is recorded" (A0).

### component.C2
It is defined in entities/E6-component.md: "A component is a system seen as a part of a larger system that contains it." It "has one duty at the altitude where it appears as a part, and it exposes and consumes interfaces", and its boundary is those declared interfaces. E6 says "Every component is a system; component names its place in a containing system, not a different kind of thing". So the difference is which question you are asking, not what kind of thing it is. Traits, axioms and what a change answers to are questions about a system. Duty, interfaces, neighbours and blast radius are questions about a component, and they only have answers relative to the containing whole (E6 "Component against system"; E5 "A system against a component"). A system that nothing contains is not a component of anything (E6). A component is not a file, module, package, repo or deployable by definition, not a SysML part, and not necessarily registered in components/ (E6 Boundaries).

### component.C3
No. E6 "Boundary against directory": "A component's directory addresses it... Its boundary is its declared interfaces". E5 says a directory "is the boundary of neither the system nor the component". Nothing declares an interface, so nothing separates the two parts. For deciding what a change answers to, parts/thing/ and parts/other/ are "one system, with the traits of both" (E5 Boundaries; E6 Definition). The undeclared dependency "is itself a fault against A3" (E5), against A3's Air-Gap Principle: "no unit reaches into another's internals". Blast radius follows from this: a change to parts/thing/ reaches parts/other/ (E6 table), and a change that alters what other reaches into "owns that boundary: declaring and honouring the interface is inside its scope, not optional" (E5). The fix is to declare the interface and move parts/other/ onto it. The consumer is real, so the exposure is earned under A3's Earned Exposure.

### component.C4
The change answers to P and to every system containing P, including the service (axioms/README.md; E5). The service has the traits of all its parts, Q's included, so axioms that Q's traits bring bind the change through the service (E5 "Contain"). Q is not altered: "A system it only composes with, through a contract the change leaves as it was, is not altered, and its axioms do not bind" (A0). E6's blast radius reaches "an adjacent component only if the interface between them changes". That holds only if Q actually honours the interface. If Q reaches past it, or depends on undeclared behaviour (a "contract in fact", E5), the two are one system for this change. Q is adjacent, because it consumes what P exposes (E6), so it is a candidate for opportunistic improvement under A14 tangent discipline (A0). It sits in the lower-payback direction: "adjacency with less payback, not none" (E6), since your work does not stand on Q.

### OBSERVATIONS
- A0 lists what a change touches as what it modifies, what it newly depends on, and consumers whose contract it alters. An existing dependency the change keeps using (Y in C1) is not named, so whether Y is "touched" depends on whether the fix uses Y in a new way. I read that as not touched, but the text leaves it implicit.
- The corpus does not say whether an error message's text is part of a declared interface. So whether a Y error-message change alters Y's consumers is NOT SETTLED. E5 counts parsing output "the interface does not promise" as a bypass.
- T1 asks for state that "persists beyond a single operation", but does not say whether volatile in-process state that is lost on restart counts. Whether Z makes the service stateful (and brings in A1) is therefore a guess.
- E6 says a detected crossing triggers what A3 states. A3's "Bypass as Signal" is written for reaching past a declared interface. For C3, where no interface exists, the evaluation trigger is implied rather than stated.
- There is a possible tension between A0 ("work that touches a gap closes as much of it as the touch allows") and E5 (adding versioning to an interface you are changing is "encouraged, not required"). E5 carves out an exception that A0 does not mention.
- A14's adjacency wording ("under load-bearing infrastructure the main line will stand on") is one-directional. A0 and E6 define adjacency in both directions. E6 reconciles the two explicitly, but A14 read alone suggests only one direction.
- A3 is phrased in terms of "module", while E6 says a component is not a module by definition. This is minor terminology drift.
