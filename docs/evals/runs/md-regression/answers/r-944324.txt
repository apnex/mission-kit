### design-rulings.R1
Your change must declare an interface between T and N and move N onto it, so the boundary is honoured; this is required, not optional. E5 (entities/E5-system.md, Boundaries) says: "A change that alters what an undeclared neighbour reaches into owns that boundary: declaring and honouring the interface is inside its scope, not optional." Honoured means it is "the only way the neighbour reaches it" (E5 Definition), and "Declaring the boundary, and moving the dependency onto it, is what makes them two again." N is also inside your change's scope because A0 (axioms/README.md) says a change touches "any consumer whose contract it alters", and the undeclared reach "is itself a fault under A3". Before moving N, evaluate the interface against T's duty: the consumer is moved onto the interface, or the interface is adjusted to what N legitimately needs (E5 "Declared against honoured"; A3 "Bypass as Signal"). Until then N and T are one system, and both sit inside the service, so the change answers to the service's axioms. The service has the traits of all its parts (E5 Contain).

### design-rulings.R2
(1) No. E5 Boundaries says: "if A reaches into B and B into C, a change to A is one system with C only when it alters something B takes from C." A change that only A uses alters nothing B takes from C, so C's axioms do not bind it. It still answers to A and B together, because A's undeclared reach into B makes them "one system, with the traits of both" (E5; A0).
(2) Yes. The change alters something B takes from C, which is the condition E5 states, so A, B and C are treated as one system with the traits of all three. Every axiom any of them brings into force binds the change (A0: "the axioms either unit would bring all bind").

### design-rulings.R3
Yes, the service is stateful, and A1 binds your change. The module that writes records it later reads back and acts on passes T1's test (traits/T1-stateful.md: "Does the system write something it will later read back, and would anything act differently if that record were wrong?"). E5 Contain says "A system has every trait any part it contains has", and T0 adds "a service with one stateful module is stateful, so a stateful system cannot escape its axioms by being described as stateless parts". A0 says a change answers to "the system it modifies, every system containing it", so changing the stateless module alters the stateful service. A1 is tagged `applies-to: [stateful]`, so it binds. Following A0's direction rule, the change may not move the service away from A1's limit, and must move toward it as far as its own scope allows.

### design-rulings.R4
Yes: A1 binds the team's records, not the CLI tool. E5 says "The organisation doing the work is a system" that "holds state in its records", and gives this case directly: "A stateless product built by a team that keeps records it relies on has A1 binding the team's records, not the product." The tool is stateless, so it fails T1 and A1 does not bind it or a change to it as a product system. The organisation's axioms "govern how the change is made and recorded, and are not one of the systems the change alters" (E5). So A1 governs the team's work records: the records should be one perceivable, durable source of truth with no private or hidden state (A1 Mandate). The team also hands work between actors, so it is multi-agent (T3), which brings A5, A6, A7, A10 and A13 into force for the organisation as well (A0 matrix).

### design-rulings.R5
The axioms encourage the split, and A0 says you are expected to weigh it, but it is not required. A0 limits the required improvement to "the part the change already alters to do its own work; restructuring beyond that, even inside the same component, is the encouraged improvement below, not a requirement." A3 "Composable by Default" encourages this exact move: "within the unit's own duty, fix it, fracture it, re-cut its seams and recompose it so it makes better sense for every consumer downstream - as a change of its own, answering to every consumer whose interface it alters." K's interface is unversioned, so the split "alters every consumer at once" and answers to all three consumers' axioms immediately (E5). E5 also encourages, but does not require, adding versioning, and says "if it is not done, the gap is recorded." Whether or not you split K, record the gap: A0 says "Either way the gap is recorded" and "Passing it silently is what the axiom forbids". If you defer it, record it with evidence and a revival trigger (RU3). The small feature itself must not add to the tangle (A3: "a change short of it adds none of them").

### design-rulings.R6
Publishing 2.4 alters all ten consumers. E5 says: "A declared version range - any 2.x - is adoption in advance: a release within it alters every consumer bound by the range, whether or not the consumer's own files change." 2.4 changes the behaviour the declared interface documents, so it alters each consumer's contract. The fact that the consumers use only the declared interface does not protect them, because the interface itself changed (E6 Blast radius: an adjacent component is reached "only if the interface between them changes"). So the release answers to every one of the ten consumers' axioms (A0). L is not altered by being adopted (E5). NOT SETTLED: whether a lockfile, or resolution only at the next install, delays the alteration. GUESS: the corpus would count each consumer as altered once its range admits 2.4.

### OBSERVATIONS
- A3's Mandate says a change "removes what it touches" (dual-purpose modules and similar). A0 narrows this to "the part the change already alters". A reader of A3 alone could take R5's split as required. A0 resolves this, but A3 does not point to that narrowing in its Mandate.
- A0's opportunistic-improvement test (tangent discipline, RU3 recording) is written for *adjacent* components. A0 also says restructuring inside the same component is "the encouraged improvement below", but the test in "below" is phrased for adjacent components. Whether the A14 tangent test applies to restructuring inside a component is implied, not stated.
- E5's chaining rule is phrased as "a change to A ... when it alters something B takes from C", but A only reaches into B. It is not explained how a change located in A could alter what B takes from C. R2(2) does not say where the change lands, so I read it as meeting the condition.
- In E5, the rule "owns that boundary" sits in the Boundaries paragraph about units in *different* systems, and "units inside one system need no chaining". It is not explicit that the duty to declare and honour also applies between modules inside one service (R1). I read it as applying, because the sentence is unqualified and E6 says an undeclared part is "one system with whatever reaches into it".
- A3 "Bypass as Signal" is written for reaching past a *declared* interface. Where no interface exists (R1), E5's "Declared against honoured" carries over the evaluation step by analogy.
- E5 says versioning is encouraged and that a new version alters only adopters, but floating ranges make adoption automatic. The corpus does not address semver expectations, for example a behaviour change within a major version.
