### design-rulings.R1
Your change must declare an interface between T and N and get N to use it. This is part of your change's own scope, not an optional extra. entities/E5-system.md (Boundaries) says: "A change that alters what an undeclared neighbour reaches into owns that boundary: declaring and honouring the interface is inside its scope, not optional." Until that is done, N and T are "one system, with the traits of both" (E5), and the undeclared reach is "itself a fault against A3". Both modules are also inside one service, so the change answers to that service's axioms. E5 says "a change to any of them answers to the containing system", and axioms/README.md (A0) says a change answers to "every system containing it". A3's "Bypass as Signal" (axioms/A3-sovereign-composition.md) says how to end the reach: check what N needs against T's duty, then either move N onto the interface or adjust the interface to what N legitimately needs. N is also a consumer "whose contract it alters", so A0 counts N as touched by your change.

### design-rulings.R2
(1) No. E5 Boundaries: "The merge chains only through what a change can reach: if A reaches into B and B into C, a change to A is one system with C only when it alters something B takes from C." A change that only A uses alters nothing B takes from C, so C's axioms do not bind it. A and B are still one system because of their undeclared dependency (E5), so A+B's traits apply, but the question asked only about C. (2) Yes. The change alters something B takes from C, so by the same sentence A, B and C are one system for this change. C's axioms bind it, along with the axioms either other unit brings (A0: "the axioms either unit would bring all bind"). Both undeclared reaches are also A3 faults (E5; A0).

### design-rulings.R3
Yes, the service is stateful, and A1 binds your change. The module that writes records and later acts on them passes the T1 test (traits/T1-stateful.md: "Does the system write something it will later read back, and would anything act differently if that record were wrong?"). The service contains that module, and "A system has every trait any part it contains has" (E5; traits/README.md: "a service with one stateful module is stateful"). A1 applies to stateful systems (axioms/A1-sovereign-state-transparency.md), so it binds the service. A0 says a change answers to "every system containing it", and E5 says units inside one system "need no chaining". So a change to a stateless module still answers to the service's A1. Per A0, the change must not move the service away from A1's limit, and must move it toward that limit as far as the change's scope allows. E5 names this exact escape as forbidden: "a stateful system escapes its own axioms by being described as stateless modules".

### design-rulings.R4
Yes, A1 binds the team's records, not the tool. E5 says: "A stateless product built by a team that keeps records it relies on has A1 binding the team's records, not the product." The organisation is a system in its own right: "it holds state in its records" (E5). The team writes those records and reads them back to act on, which passes the T1 test. The tool has no traits, so only the any-system axioms bind it (A3, A4, A8, A9, A14 per the A0 applicability matrix). E5 also says the organisation's axioms "govern how the change is made and recorded, and are not one of the systems the change alters". So A1 governs how the team keeps its work records, not any change to the tool. The team also hands work between actors, which makes it multi-agent (T3), so A5, A6, A7, A10 and A13 also bind the organisation.

### design-rulings.R5
You must do some things and are encouraged to do others. Required: your feature must not add to the tangle, because A0 says "new work never repeats a gap the axiom names". A dual-purpose module is a gap A3 names (Law of One). Beyond the part your feature already alters, the split is not required. A0 says restructuring beyond that, "even inside the same component, is the encouraged improvement below, not a requirement". It is still encouraged: A3's "Composable by Default" says, within a unit's own duty, "fix it, fracture it, re-cut its seams", and A0 says an agent that sees such an improvement is "expected to weigh doing it, not merely permitted to". If you split K, do it as a change of its own, separate from the feature. Because K's interface is unversioned, that change "alters every consumer at once" (E5) and answers to all three consumers. Adding versioning is "encouraged, not required" (E5); if it is not done, record the gap. If you do not split K, record the gap with its evidence and a revival trigger (A0, RU3); A0 says "Passing it silently is what the axiom forbids".

### design-rulings.R6
All ten consumers. E5 says: "A declared version range - *any 2.x* - is adoption in advance: a release within it alters every consumer bound by the range, whether or not the consumer's own files change." All ten float on any 2.x. Version 2.4 changes behaviour that the declared interface documents, so it alters the contract every one of them depends on. Using only the declared interface does not protect them here, because the interface itself changed. The rule that "Publishing a new version ... alters no consumer that has not adopted it" (E5) does not help them either, since the range counts as adoption. NOT SETTLED: whether a consumer whose lockfile pins an earlier 2.x still counts as "bound by the range". GUESS: if the lock holds a consumer on an earlier version, that consumer has not yet adopted 2.4, and it is altered only when the lock is refreshed.

### OBSERVATIONS
- E5's chaining sentence ("a change to A is one system with C only when ...") calls a change "one system", which is loose wording. It also leaves the A-B merge in R2(1) to be inferred from a different sentence.
- T3's test asks whether work crosses between actors "inside the system". E5 separates the organisation from the product. So for a service "operated by" several agents, it is unclear whether the service itself is multi-agent or only the organisation operating it. The text does not settle this for R1/R3.
- A0's "Either way the gap is recorded" sits in the paragraph about adjacent components. Applying it to a restructuring inside the same component (R5) is my inference. The pointer "the encouraged improvement below" suggests it is intended.
- Two E5 statements need reading together: "publishing alters no consumer that has not adopted it" and "a range is adoption in advance". Lockfiles and resolved-version pinning are not addressed.
- The corpus does not say whether a minor release (2.4) that changes documented behaviour is itself a fault, for example a semver violation, or which axiom such a fault would fall under.
- INDEX.md tells readers to resolve links against a remote URL when no checkout is available. This corpus copy was read locally only.
