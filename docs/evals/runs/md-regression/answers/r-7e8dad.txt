### component.C2
It is defined in entities/E6-component.md: "a system seen as a part of a larger system that contains it", with "one duty at the altitude where it appears as a part", that "exposes and consumes interfaces". Its boundary is those interfaces, and it separates the component from a neighbour "only where they are declared and that neighbour uses them". It is not a different kind of thing: "Every component is a system; component names its place in a containing system". The difference is the question being asked: "Traits, axioms and what a change answers to are questions about a system. Duty, interfaces, neighbours and blast radius are questions about a component" (E6 Discriminators; mirrored in entities/E5-system.md "A system against a component"). "A system nobody contains ... is not a component of anything." E6 Boundaries also says it is "Not a file, module, package, repository or deployable by definition", not a SysML part, and not necessarily shareable or registered in components/.

### component.C3
No. entities/E6-component.md, "Boundary against directory": "A component's directory addresses it ... Its boundary is its declared interfaces", and E5 says a directory "is the boundary of neither the system nor the component". Because nothing is declared, nothing separates the two: code reaching in "stays one system with the component until it uses the interface" (E6), and E5 "Boundaries" says they are "one system, with the traits of both" when deciding what binds a change. What is wrong is an A3 fault: "The undeclared dependency is itself a fault against A3" (E5), breaking A3's Air-Gap Principle, "no unit reaches into another's internals" (axioms/A3-sovereign-composition.md). The fix is "Declaring the boundary, and moving the dependency onto it" (E5), with the interface judged against the component's duty (A3 "Bypass as Signal", E6). parts/other is a real consumer, so under A3's "Earned Exposure" the interface is earned, not speculative. Also, per E5, "A change that alters what an undeclared neighbour reaches into owns that boundary: declaring and honouring the interface is inside its scope, not optional."

### component.C4
Per axioms/README.md (A0), "a change answers to every system it alters": P, which you modify, and "every system containing it", which is the service. A0 continues: "A system it only composes with, through a contract the change leaves as it was, is not altered, and its axioms do not bind", so Q is not altered and does not bind as a separate system. That depends on Q honouring the interface: if Q reaches past it, or relies on behaviour the interface does not promise, E5 makes them one system (entities/E5-system.md, "Declared against honoured", "contract in fact"). The service "has every trait any part it contains has" (E5 "Contain"), so the axioms Q's traits bring can still bind your change through the service; how this fits with "its axioms do not bind" is NOT SETTLED (see OBSERVATIONS). Q is adjacent to P, because they share a declared interface "in either direction" (entities/E6-component.md), so it is a candidate under A0's opportunistic-improvement clause. But it is the weaker direction: payback is "strongest where the work stands on the component", and here Q stands on P, so it is "adjacency with less payback, not none" (E6). It must pass A14's tangent test (near payback, captured yield, no significant distraction), be made "as a change of its own", or else be recorded with a revival trigger (A0, RU3).

### OBSERVATIONS
- A0 says Q's axioms do not bind a composed-with system whose contract is unchanged, yet E5 says a containing system has every trait of its parts and that "units inside one system need no chaining". Inside one service, Q's traits reach your change through the service anyway, so for intra-service neighbours the "does not bind" clause is close to empty. The corpus does not reconcile the two.
- A0 defines "touched" as including "what it newly depends on". It is silent on an existing dependency (X already calling Y) that the fix relies on but does not change. I read that as not touched, but this is inference.
- The corpus does not say whether error messages or other output text belong to a declared interface. This affects whether improving Y alters Y's consumers.
- T1 asks for state that "persists beyond a single operation"; A1's mandate forbids "transient truth". Whether purely in-process state (Z) makes the service stateful is unclear.
- A14 defines adjacency in one direction only ("infrastructure the main line will stand on"), while A0 and E6 allow both directions. E6 reconciles this explicitly, but A14 read alone suggests the narrower meaning.
- INDEX.md line 24 tells readers to fetch from a GitHub URL when no checkout exists. This is not relevant here, but it points outside a self-contained corpus.
