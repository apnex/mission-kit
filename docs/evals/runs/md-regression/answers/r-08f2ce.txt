### component.C2
It is defined in entities/E6-component.md: "A component is a system seen as a part of a larger system that contains it", with "one duty" at that altitude, and it "exposes and consumes interfaces". "Every component is a system; component names its place in a containing system, not a different kind of thing." A system (entities/E5-system.md) is "a unit of engineering with a boundary". What separates the two terms is the question being asked: "Traits, axioms and what a change answers to are questions about a system. Duty, interfaces, neighbours and blast radius are questions about a component" (E6, "Component against system"). A system that nothing contains, such as a whole product seen from outside, "is not a component of anything" (E6). A component does not have to be registered in components/ or be shareable, and a file, module or directory is not a component just by being one (E6, Boundaries).

### component.C3
No. "A component's directory addresses it ... Its boundary is its declared interfaces" (entities/E6-component.md, "Boundary against directory"), and E5 says a directory "is the boundary of neither the system nor the component". No interface is declared, so "nothing separates it yet". For deciding what a change answers to, parts/thing and parts/other are "one system, with the traits of both" (E5, Boundaries; A0). The undeclared dependency "is itself a fault against A3" (Air-Gap Principle: "no unit reaches into another's internals"; axioms/A3-sovereign-composition.md). To fix it, declare the interface and move parts/other onto it: "Declaring the boundary, and moving the dependency onto it, is what makes them two again" (E5). A change that alters what parts/other reaches into "owns that boundary: declaring and honouring the interface is inside its scope, not optional" (E5).

### component.C4
Your change answers to the systems it alters: P itself, "every system containing it" (the service and anything that contains the service), and any system whose contract with P the change alters (axioms/README.md, "What brings an axiom into force"). Q is not altered: "A system it only composes with, through a contract the change leaves as it was, is not altered, and its axioms do not bind". The blast-radius row in entities/E6-component.md agrees: an adjacent component is reached "only if the interface between them changes". One qualification is that the service contains Q and "has every trait any part it contains has" (E5). So the traits Q contributes still bind your change, through the service, though Q itself is not changed. That holds only if Q honours the interface: if Q reaches past it or relies on undeclared behaviour, the two are one system (E5, "Declared against honoured"). Q shares a declared interface with P, so it is adjacent and a candidate for opportunistic improvement (A0, A14). Because Q stands on P rather than P on Q, it is "adjacency with less payback, not none" (E6, "Adjacent against nearby"), and any improvement goes in a change of its own.

### OBSERVATIONS
- The corpus does not say whether an error message's text is part of a module's declared interface. That gap decides whether improving Y (C1) alters Y's consumers.
- T1 requires state that "persists beyond a single operation". So state held only in process memory may make the service non-stateful, and then A1 would not bind it. Yet A1 calls exactly that state ("transient truth", "Hidden State Problem") a fault. It is unclear whether A1 reaches the Z case in C1.
- A3's mandate says a change "removes what it touches", which reads stronger than A0's "closes as much of it as the touch allows" and A0's statement that restructuring beyond that is not required. A0 governs ("How an axiom binds a change is stated in A0"), but the A3 wording could mislead.
- A0 says improvement beyond scope is "never mandated" but also that an agent "is expected to weigh doing it". These are consistent if "weigh" is the duty and "do" is optional, but a reader could take them as being in tension.
- INDEX.md tells readers to resolve links against a remote URL when no local checkout exists. In this eval only the local corpus was used.
