### system-boundary.S1
Only the launcher's axioms: A3, A4, A8, A9, A14 - the `any-system` floor (axioms/README.md applicability matrix; each axiom's `applies-to` frontmatter agrees).
The launcher passes none of the trait tests: no state it reads back (T1), no declaration it reconciles toward (T2), one actor (T3), a watching operator (T4), no model (T5), and E5 says "A one-shot script with no traits is a system, bound by the axioms every system carries."
The launcher and the service compose: "A launcher that hands sessions to a service through a declared interface composes with it" (entities/E5-system.md, Contain/Compose).
A0 says "A system it only composes with, through a contract the change leaves as it was, is not altered, and its axioms do not bind", so the service's A1, A5, A6, A7, A10 and A13 do not bind this change.
Nothing contains the launcher, so no containing system adds axioms.
Separately, the organisation doing the work is a system whose axioms govern how the change is made and recorded, but E5 says that is "not one of the systems the change alters".

### system-boundary.S3
The service's full set: A1, A3, A4, A5, A6, A7, A8, A9, A10, A13, A14.
E5 says "A module inside a service is a system, and the service contains it, whether or not the module's interfaces are declared", and a change answers to "every system containing it" (A0).
On its own the module is stateless, but that does not let it escape: "a stateful system cannot escape its axioms by being described as stateless parts" (traits/README.md; also E5 "Why precision matters").
The module itself adds only the floor, which is already in the set.

### system-boundary.S4
Only the library's own axioms: the floor A3, A4, A8, A9, A14 (A0: "a plain library takes `any-system`").
The interface and its behaviour are unchanged, so no consumer's contract is altered. E5 also says "Publishing a new version of an interface alters no consumer that has not adopted it; each adoption is a change to that consumer, and answers to that consumer's axioms".
E5 names this exact case as the error to avoid: otherwise "a small shared library would carry the axioms of every system that uses it".
One caveat from E5: "A declared version range - any 2.x - is adoption in advance". If any consumer pinned a range that the new release falls in, that consumer is altered too.
The question says each adoption is a separate change, so I read it as having no such ranges; the question does not state this outright.

### system-boundary.S5
No boundary is declared, and the service depends on the launcher's output, so for this change the two are "one system, with the traits of both" (E5 Boundaries; A0 "What brings an axiom into force").
The axioms are therefore the service's union: A1, A3, A4, A5, A6, A7, A8, A9, A10, A13, A14.
Something else is wrong: "The undeclared dependency is itself a fault against A3", whose Air-Gap Principle requires units to "interact only through declared adapters and contracts".
Fixing it is not optional for you. E5 says "A change that alters what an undeclared neighbour reaches into owns that boundary: declaring and honouring the interface is inside its scope".
Under A3 "Bypass as Signal", the interface is evaluated against the launcher's duty. That ends either with the service moved onto a declared interface or with the interface adjusted to what the service legitimately needs.
In practice, changing the format may also break the service's parsing. That risk is the "Logic Leakage" fault A3 names (that it would break is my inference).

### system-boundary.S6
It is defined in entities/E5-system.md: "A system is a unit of engineering with a boundary: what is inside it, and the contracts through which anything outside reaches it."
The boundary separates it from a neighbour "only where it is declared and honoured". Where a dependency crosses an undeclared or bypassed boundary, "the two are one system for deciding what a change answers to".
Systems relate in exactly two ways: they contain (a system made of systems, which has every trait its parts have) or they compose (through a declared contract, with neither containing the other).
Traits describe a system and axioms bind it. A system is not a repository, a deployment unit or a process by definition, and it is not defined by size or by traits.
E6 adds that a component is "a system seen as a part of a larger system that contains it".

### axiom-direction.Q1
The service is stateful, multi-agent and autonomous, so A1 binds it. A1's mandate says "No functional unit possesses private, opaque, or transient truth", and its faults include "Hidden State Problem - state lives inside a process". A5 (multi-agent) also concerns agents seeing the same reality.
For your feature, A0 says "new work never repeats a gap the axiom names". So the feature must keep its own state durable and queryable by the other agents, not in process memory. It must also not build on the component's hidden state.
If your feature touches that component (modifies it, newly depends on it, or alters its contract), the gap is in scope: you must close "as much of it as the touch allows" (A0).
If it does not touch the component, closing the gap is "encouraged, never mandated". You are "expected to weigh" it, and if the component is adjacent and A14's tangent discipline supports it, you may close it as a separate change.
Otherwise, record the gap with its evidence and a revival trigger (RU3; A14 capture-on-discovery), because "Passing it silently is what the axiom forbids" (A0).
NOT SETTLED: whether the component is "adjacent" (which needs a declared interface, E6) and what the service's state backplane is. The scenario does not give either.

### axiom-direction.Q2
An axiom is a limit, an "asymptote", that the system is built toward. It is not a pass/fail test (axioms/README.md, "Standing commitment"; the CORRECTION banner there retracts the invariant reading).
When you change a system it binds, it pulls in two directions at once: "No change may move the system away from the limit, and each change moves it toward the limit as far as the change's own scope allows."
So it rules out regression, and it obliges you to improve whatever your change touches. Beyond that scope, improvement is encouraged and any gap you see is recorded rather than passed silently.
It is not something to trade against deadlines or against other axioms ("no axiom may be traded against another"). A gate can check whether the change "moved the system no further from any limit in force, and repeated no gap it touched".
The A0 Faults section explains why: under "the conformance reading", the gaps the axioms name become permanent.

### OBSERVATIONS
- A0 line 78 says a component "the change newly depends on through a declared interface is touched but not altered ... its axioms do not bind the change". That reads clearly for a separate system. Inside one containing service, though, the service's axioms bind anyway, so in Q1 the sentence's "its axioms do not bind" is easy to misapply. The corpus does not separate the two cases explicitly.
- S4 depends on whether any consumer pinned a version range (E5). The scenario implies no ranges but does not say so.
- The INDEX tells readers with no local checkout to fetch from GitHub, which conflicts with a read-only-the-corpus constraint. I did not fetch.
- A0 says the organisation's axioms are asked separately (E5). The questions do not say whether to include them, so I left them out of the per-change sets.
- Whether the Q1 component is "adjacent" depends on a declared interface, and the scenario does not specify one.
