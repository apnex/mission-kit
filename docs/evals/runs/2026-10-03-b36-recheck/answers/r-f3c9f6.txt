### design-rulings.R1
N reaches T with no declared boundary, so for deciding what your change answers to, N and T are "one system, with the traits of both" (entities/E5-system.md, Boundaries; axioms/README.md, "What brings an axiom into force"). Your change alters something N reaches into, and E5 says outright: "A change that alters what an undeclared neighbour reaches into owns that boundary: declaring and honouring the interface is inside its scope, not optional." So the change must declare an interface for T and get N using it ("honoured"). E5 Discriminators ("Declared against honoured") and A3 "Bypass as Signal" say how: first evaluate the interface against T's duty, then either move N onto the interface or adjust the interface "to what the consumer legitimately needs". Until that happens the change also answers to N's axioms, because N is a consumer whose contract (in fact) it alters (A0: a change touches "any consumer whose contract it alters"). The undeclared reach is itself an A3 fault (E5; A3 "Air-Gap Principle"). NOT SETTLED: whether the interface work must land in the same commit/PR as the T change or in a separate change. GUESS: within the same unit of work, since E5 says it is "inside its scope".

### design-rulings.R2
(1) Not as one merged system with C. E5 Boundaries: "The merge chains only through what a change can reach: if A reaches into B and B into C, a change to A is one system with C only when it alters something B takes from C". A change only A uses alters nothing B takes from C. But a catch: A, B and C are all modules inside the service. A0 says a change answers to "every system containing it", and E5 says "A system has every trait any part it contains has". So any axiom that C's traits bring into force also binds your change through the service. (2) Yes: the change now alters something B takes from C, so by the same E5 sentence it is one system with C and answers to C's axioms. By E5's last sentence it also owns the undeclared boundaries it crosses, so declaring and honouring those interfaces is in scope.

### design-rulings.R3
Yes, the service is stateful. That module meets T1's test: it "write[s] something it will later read back", and the service acts on it (traits/T1-stateful.md, Test). E5 and T0 ("How traits compose") both say a system has every trait of any part it contains: "a service with one stateful module is stateful". A1 is tagged `applies-to: [stateful]` (axioms/A1-sovereign-state-transparency.md), so it binds the service. Your change to a stateless module alters the module and "every system containing it" (A0), which includes the service. So A1 binds your change, under A0's direction rule: you must not move the service away from A1's limit, and you must move it toward that limit as far as the change's scope allows. E5 "Why precision matters" names the opposite reading as the fault: "a stateful system escapes its own axioms by being described as stateless modules". NOT SETTLED: what A1 concretely asks of a module that holds no state. GUESS: in practice, that it adds no private or hidden state (A1 Mechanics: acting components "are stateless: they read, transform, and write back").

### design-rulings.R4
Yes. A1 binds the organisation's records, not the tool. E5 states this case directly: "A stateless product built by a team that keeps records it relies on has `A1` binding the team's records, not the product." The organisation (agents, director, records, checks) is itself a system, and it is stateful because it reads back and relies on its records (T1 test). Being stateless with no model, the tool itself gets only the `any-system` floor (A3, A4, A8, A9, A14), plus any T2/T4 axioms if it were declarative or autonomous, which the question does not say (axioms/README.md applicability matrix). E5 keeps the two questions apart: a change to the tool answers to the tool's systems, while "the organisation's axioms govern how the change is made and recorded". By the same passage the organisation is also multi-agent ("work passes between actors"), so the multi-agent axioms bind how the team works too.

### design-rulings.R5
First, the direction rule (A0): your feature must not make the tangle worse. "New work never repeats a gap the axiom names", and A3's Law of One forbids dual-purpose modules. Whether you must split K depends on whether your change "touches" the tangle. A0 says "code that merely sits beside it, in the same file or module, is not touched". If the feature modifies the tangled code, you must close "as much of it as the touch allows". If not, the split is outside your scope, so it is "encouraged, never mandated", and you are "expected to weigh doing it, not merely permitted to". A3 "Composable by Default" endorses this exact move ("fracture it, re-cut its seams and recompose it ... within the unit's own duty"), "as a change of its own". Because K's interface is not versioned, that separate change alters all three consumers and answers to each one's axioms (A0; E5 versioned-contract discriminator). Decide by A14's tangent discipline (near payback, yield captured, little distraction from the goal). If you do not split, record the gap with evidence and a revival trigger (RU3), because "Either way the gap is recorded."

### design-rulings.R6
All ten. E5 (Discriminators, versioned contract): "A declared version range - *any 2.x* - is adoption in advance: a release within it alters every consumer bound by the range, whether or not the consumer's own files change." All ten float on 2.x, and 2.4 changes the documented behaviour of the interface they use, so their contract is altered. The interface-only usage does not shield them, because the declared contract itself changed (A0: a change answers to "any system whose contract with it the change alters"). So publishing 2.4 answers to all ten consumers' axioms. NOT SETTLED: how lockfiles or cached resolutions affect this. GUESS: a consumer whose lockfile still resolves an older 2.x is bound by the range in declaration but has not yet been altered in fact. Also NOT SETTLED: whether changing documented behaviour inside a minor version is itself a fault; the corpus does not discuss semver.

### OBSERVATIONS
- R2 (containment against the chaining rule): E5's chaining limit ("a change to A is one system with C only when it alters something B takes from C") sits uneasily beside containment. When A, B and C share a containing service, the service has C's traits and A0 binds a change to "every system containing it". So C's trait-driven axioms reach a change to A anyway, and the chaining limit only matters when there is no shared container. Neither E5 nor A0 states how the two interact.
- R5 (A0 scope rule): A0 covers "touched" scope and "adjacent" components, but not untouched code inside the same component the change modifies. It only says code beside the change "in the same file or module, is not touched". So whether K's own tangle falls under the mandatory or the encouraged rule depends on line-level detail the corpus leaves open.
- R1 (timing of boundary work): E5 says declaring and honouring the interface is "inside [the change's] scope, not optional". A3/E5 also require evaluating the interface against the component's duty before choosing a remedy. Neither says whether this must land in the same change or can come first as its own change.
- R6 (lockfiles): E5's "adoption in advance" rule does not mention lockfiles or pinned resolutions.
- Corpus INDEX.md line 24 tells the reader to fetch from a remote URL when no local checkout exists. In this exercise only the local corpus copy was used.
