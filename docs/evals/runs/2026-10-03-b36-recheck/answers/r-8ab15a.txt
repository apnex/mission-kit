### system-boundary.S1
Only the launcher's axioms apply: A3, A4, A8, A9 and A14. Those are the axioms tagged `any-system` (axioms/README.md applicability matrix; each file's `applies-to`). The launcher has none of the five traits: it holds no state (T1), has one operator (T3), has a human watching (T4) and has no model in the loop (T5), and no declared specification is mentioned (T2). E5 Boundaries says "A one-shot script with no traits is a system, bound by the axioms every system carries". A0 says "a change answers to every system it alters", and adds "A system it only composes with, through a contract the change leaves as it was, is not altered, and its axioms do not bind". The launcher composes with the service through the declared session interface (E5 *Compose*: "A launcher that hands sessions to a service through a declared interface composes with it"). That interface is unchanged and no system containing both is declared, so the service's axioms do not bind this change.

### system-boundary.S2
The launcher's axioms and the service's axioms both apply, and together they make A1, A3, A4, A5, A6, A7, A8, A9, A10, A13 and A14. A2, A11 and A12 do not apply. A0 says a change answers to "any system whose contract with it the change alters", and changing the declared interface alters that contract. The service is stateful (T1, which brings A1), multi-agent (T3, which brings A5, A6, A7, A10 and A13) and autonomous (T4, which brings A7, A10 and A13). It also carries the `any-system` floor of A3, A4, A8, A9 and A14. It is not declarative and has no model in the loop, so A2, A11 and A12 stay out. One caveat: if the interface is versioned, E5 says "Publishing a new version of an interface alters no consumer that has not adopted it". The service is then altered only when it adopts the new version, and that adoption answers to the service's axioms. The prompt does not say whether the interface is versioned (NOT SETTLED).

### system-boundary.S3
The service's axioms apply: A1, A3, A4, A5, A6, A7, A8, A9, A10, A13 and A14. The module having no state of its own does not lower that set. E5 *Contain* says "A module inside a service is a system, and the service contains it, whether or not the module's interfaces are declared". A0 says the systems a change alters include "every system containing it". E5 Discriminators gives the same example: "changing a module changes the service it sits in". E5 "Why precision matters" names the failure this guards against: "a stateful system escapes its own axioms by being described as stateless modules, each of which passes on its own". So the stateless module's own floor (A3, A4, A8, A9, A14) is covered by the service's larger set.

### system-boundary.S4
Only the library's axioms apply: A3, A4, A8, A9 and A14, the `any-system` floor. A0's matrix says "a plain library takes `any-system`". The ten consumers compose with the library through a declared, versioned interface that this change leaves alone. A0 says "A system it only composes with, through a contract the change leaves as it was, is not altered, and its axioms do not bind". E5 adds "each adoption is a change to that consumer, and answers to that consumer's axioms; the component is not altered by being adopted". E5 "Why precision matters" names the opposite reading as the error: "a small shared library would carry the axioms of every system that uses it". A caveat from E5: a declared version range such as "any 2.x" counts as adoption in advance. The prompt says each consumer adopts as its own separate change, so no range applies here. Even when a consumer does adopt the release, that adoption is a separate change under the consumer's axioms, not this one.

### system-boundary.S5
The axioms either unit brings all apply, so the change answers to A1, A3, A4, A5, A6, A7, A8, A9, A10, A13 and A14. The service depends on the launcher's output and no boundary between them is declared. E5 Boundaries: "for deciding what binds a change they are one system, with the traits of both". A0 says the same: "the two are one system with the traits of both, and the axioms either unit would bring all bind". Two other things are wrong. First, A0 and E5 both say the undeclared dependency "is itself a fault under A3", against A3's Air-Gap Principle ("units interact only through declared adapters and contracts"). Second, E5 says "A change that alters what an undeclared neighbour reaches into owns that boundary: declaring and honouring the interface is inside its scope, not optional". This change therefore has to declare the interface and move the service onto it, or adjust the interface after evaluating it against the component's duty (E5, *Declared against honoured*; A3, *Bypass as Signal*). GUESS: the new log format will probably break the service's parsing at runtime, which is the A3 "Logic Leakage" fault. The corpus does not say that will happen.

### system-boundary.S6
It is defined, in entities/E5-system.md. The definition reads: "A system is a unit of engineering with a boundary: what is inside it, and the contracts through which anything outside reaches it." The boundary separates it from a neighbour "only where it is declared and honoured - written down, and the only way the neighbour reaches it". E5 says that traits describe a system, that axioms bind it, and that systems relate in exactly two ways: they contain one another or compose with one another. A system is not a repository, a deployment unit or a process by definition, and it is not defined by size or by traits. E5 also says the organisation doing the work is itself a system, but one asked about separately: its axioms govern how a change is made, and it is not one of the systems the change alters. E6 defines a component as "a system seen as a part of a larger system that contains it".

### axiom-direction.Q1
A1 binds the service because the service is stateful (T1, A0 matrix). Process-only state hidden from the other agents is A1's named fault, "Hidden State Problem - state lives inside a process; other actors reason about a different reality". A0's direction rule shapes your own feature: "new work never repeats a gap the axiom names". So the feature must keep its own state in the shared backplane that other agents can see, not in process memory, and must stay A5-compatible by not acting on state it derived. Whether you must fix the component depends on scope. If your change modifies the component, newly depends on it, or alters a consumer's contract with it, then it is touched, and "work that touches a gap closes as much of it as the touch allows". If you only depend on it through a declared interface, then "its gaps must not be built on" (A0), so the feature must not read or rely on that hidden state. Otherwise the fix is "encouraged, never mandated": close it as a separate change if it is adjacent and passes A14's tangent discipline, or record it with evidence and a revival trigger under RU3. Whatever you choose, "the gap is recorded. Passing it silently is what the axiom forbids" (A0).

### axiom-direction.Q2
An axiom is a limit the system is steered toward, not a pass-or-fail test. A0 calls it "a load-bearing asymptote - a limit a system is built toward to stay aligned with its architecture's intent". When you change a system the axiom binds, it pulls the change in two directions at once: "No change may move the system away from the limit, and each change moves it toward the limit as far as the change's own scope allows". A system falling short of the limit is not wrong. What is wrong is a change that moves away from the limit, or that touches a gap and passes it silently. A0 names the opposite reading as a fault, "The conformance reading". Under that reading a system short of the limit is either already failed, so nothing is owed, or passing, so nothing moves, and the gaps become permanent. The axioms are also conjunctive, so none may be traded against another (A0, "How the set composes"). A gate checks only the direction rule: that the change "moved the system no further from any limit in force, and repeated no gap it touched".

### OBSERVATIONS
- A0 line 78 says a component the change "newly depends on through a declared interface is touched but not altered ... its axioms do not bind the change". For a component inside the same containing system (Q1) this makes no difference, because the containing service's axioms bind through containment anyway. The sentence reads as if it is about separate systems, and A0 does not say so.
- A0 line 55 says thirteen of the fourteen axioms can bind a lone agent. That only holds if the lone agent is autonomous or has a model in the loop, since A7, A10 and A13 need multi-agent or autonomous and A5 needs multi-agent or llm-in-the-loop. The statement is accurate but depends on traits it does not name.
- S2: the prompt does not say whether the session interface is versioned. E5's adoption rule changes when the service counts as altered, so the answer is conditional.
- S5: E5 lets a bypass end two ways, by moving the consumer onto the interface or by adjusting the interface. E5 line 83 says the change "owns that boundary", but neither file says which of the two endings the change owner must pick.
- The prompt's launcher "does not restart anything that dies". That is relevant only to T4, which is about recovering without a human, and a human is watching the launcher. So it is not autonomous, and no ambiguity results.
