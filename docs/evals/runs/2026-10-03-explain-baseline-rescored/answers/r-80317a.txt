### explain.X4
Subject: Before you add the new payment event type - how we avoid charging twice

The one idea you need for this change is idempotency.
An operation is idempotent if doing it twice has the same effect as doing it once.
Pressing a lift call button twice is idempotent: the lift still comes once.
Charging a card is not idempotent on its own: do it twice and the customer pays twice.

Why it matters here:
The system that sends us payment events can deliver the same event more than once.
That is normal for this kind of system, not a bug we can fix on our side.
So our code has to make processing an event idempotent, even though the charge inside it is not.

How the current code does it:
1. Every event carries a unique id.
2. When we process an event, we record its id in the database, in the same database transaction as the charge.
3. Before processing, we check whether that id is already recorded. If it is, we skip the event.

Why "the same transaction" matters:
A transaction means either everything in it is saved, or nothing is.
So we can never end up with the charge saved but the id missing (which would let a redelivery charge again), or the id saved but the charge missing (which would skip a real payment).
If you record the id in a separate step, a crash between the two steps breaks this.

What your new event type must do:
1. Go through the same check: look up the id, skip if seen, and record the id in the same transaction as the charge. Reuse the existing check rather than writing a new one.
2. Have an id that is the same every time that event is delivered. This is the part that is easy to get wrong. The id must come from the event itself, as the sender sent it. Do not generate it when the event arrives, for example a random id or the time we received it, because then every redelivery looks like a new event and the check never catches it.

A good test for your change: deliver the same event of the new type twice and check that exactly one charge happens.

If you are not sure whether the new event type has an id that stays the same across deliveries, ask before building on it.
