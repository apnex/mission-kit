### explain.X4
Subject: Before you add the new payment event type - how we avoid charging customers twice

Hi,

Before you add the new event type, there is one idea you need to understand, because getting it wrong can charge a customer twice. The idea is called idempotency.

The problem it solves:
The system that sends us payment events sometimes delivers the same event more than once. That is normal for this kind of system, not a bug we can fix on our side. If our code charged the customer every time an event arrived, a duplicate delivery would mean a duplicate charge.

What idempotency means:
An operation is idempotent if doing it twice has the same effect as doing it once. Pressing a lift button five times still calls the lift once. We need event handling to work like that: however many times the same event arrives, the customer is charged once.

How our code does it:
Every event carries a unique id. When we process an event, we do two things in the same database transaction:
1. make the charge, and
2. record the event's id.
Before processing, we check whether that id is already recorded. If it is, we have handled this event before, so we skip it.

Why "same transaction" matters:
A transaction means both steps happen, or neither does. If we charged in one step and recorded the id in another, a crash between the two would leave a charge with no record. The next delivery of that event would not be recognised as a duplicate and would charge again. Keeping both in one transaction closes that gap.

What this means for your new event type - two rules:

1. It must go through the same check. Do not give it its own path to the charge. It has to use the existing "is this id already recorded?" check, and its id has to be recorded in the same transaction as its charge.

2. Its id must be the same every time that event is delivered. This is the easy one to get wrong. The id has to come from the event itself, as sent to us, so that a second delivery of the same event carries the same id. If the id is something we create when the event arrives, such as a freshly generated random id or the time we received it, every delivery gets a different id, the check never finds a match, and duplicates get charged. If you are not sure the new event type has a field that stays the same across deliveries, stop and ask before going further.

A good test for your change: deliver the same new event twice and check that there is exactly one charge.

Happy to go through the existing code with you before you start.
