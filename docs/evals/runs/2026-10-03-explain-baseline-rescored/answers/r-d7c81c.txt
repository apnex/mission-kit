### explain.X4
Subject: Before you add the new payment event type - idempotency, and the one check you must not skip

Hi,

Before you change the payment event handler, you need one idea: idempotency. It is what stops us from charging a customer twice.

The idea

An operation is idempotent if doing it twice has the same effect as doing it once. Pressing a lift call button is idempotent: press it five times and one lift comes. Paying a bill is not: pay it twice and you have paid twice.

Why it matters here

Our system can deliver the same payment event to us more than once. This is normal. Message systems often redeliver when they are not sure the first delivery got through. If we simply processed every event we received, a redelivered event would charge the customer a second time. So we have to make handling an event idempotent ourselves.

How our code does it

Every event has a unique id. When we process an event, we:
1. Check whether that event's id is already recorded. If it is, we skip the event. It is a repeat.
2. If not, we make the charge and record the id, in the same database transaction.

The "same transaction" part is essential. A transaction either fully happens or does not happen at all. If the charge and the id record were saved separately, a crash between the two could leave a charge with no id record. The next delivery of the same event would then charge again. Because both are saved together, there is either a charge and its id, or neither.

What this means for your new event type

Two rules:

1. It must go through the same check. Do not write a separate path that charges without checking and recording the id in the same transaction. A new path that skips this check is exactly how double charges happen.

2. Its id must be the same every time that event is delivered. The check only works if a repeat delivery has the same id as the first one. So the id must come from the event itself, as set by whoever sends it. Do not create it when we receive the event. A random id, a timestamp, or a counter made on our side would be different on each delivery. Every repeat would then look new, and the customer would be charged again. If you are not sure where your event type's id comes from, ask before you continue.

How to check your change

Write a test that delivers the same new event twice and confirms that only one charge is made. If that test passes, your change is safe against redelivery.

Ask me if anything here is unclear. It is much cheaper to ask now than to refund a customer later.
