### explain.X4
Subject: Before you add the new payment event type - the idea of idempotency

You'll be adding a new event type to the code that handles incoming payment events. There's one idea you need first, because getting it wrong means charging customers twice. It's called idempotency.

The idea
An operation is idempotent if doing it twice has the same effect as doing it once. Pressing a lift's call button is idempotent: pressing it five times still brings one lift. "Charge this customer 10 pounds" is not idempotent on its own: run it twice and they pay 20.

Why it matters here
Our system can deliver the same event to us more than once. This isn't a bug we can fix. It's normal for systems like this: if a delivery times out, the sender re-sends it, even if we already got the first one. So our code must assume any event may arrive twice. If we processed each delivery blindly, a repeated event would charge the customer a second time.

How our code makes it safe
Every event carries a unique id. When we process an event, in a single database transaction we:
1. Check whether that id is already recorded. If it is, we skip the event - we've already handled it.
2. Otherwise, make the charge and record the id.

Two details matter:
- The charge and the id record are in the same transaction, so either both happen or neither does. If they were separate, a crash between them would break things. Charge saved but id not recorded means the re-delivery charges again. Id recorded but charge not saved means the charge is lost.
- The check only works if a repeated delivery carries the same id as the first one.

What this means for your change
1. Your new event type must go through the same check as the existing types. Don't add a separate path that charges without it.
2. Its id must be identical every time that same event is delivered. Use the id that comes with the event from the sender, or one derived only from fields that never change between deliveries. Don't generate a fresh id when we receive it (for example a new random id or a timestamp). A fresh id makes every re-delivery look like a new event, and the check silently stops protecting us.
3. Keep any charge or other side effect inside the same transaction as the id record.

How to check you got it right
Write a test that delivers the same event of your new type twice and asserts the customer is charged exactly once. If that test passes and your event goes through the existing check, you've done it safely.
