### layer-charters.H5
From schemas/catalog-entry/v1alpha1/catalog-entry.schema.json: an entry with category `rule` and an id matching `^RU[1-9][0-9]*$` must also declare `trace`, a string of at least 20 characters described as "the observable trace a check could test - what in the record shows the rule was kept or broken".
A `practice` (`PC`) entry has no such requirement ("a practice leaves none").
Optionally, a rule may declare `enforced-by` (a path matching `^tools/`): the description says "Naming a tool that checks it is enforced-by's job, and is optional", and tools/check-enforcers.sh checks `rules/RU*.md` so that any enforcer a rule names must exist.
Both share the common required fields (`id`, `category`, `title`, `status`, `hydrate-when`) and the common optional ones such as `related` and `supersedes`.
schemas/tests/catalog-entry/catalog-entry.test.mjs confirms this behaviour: a rule with no trace is refused, and so is a trace of "short".
Caveat: rules/ and practices/ do not exist in this corpus, so this is the schema contract only, with no charter behind it.

### layer-charters.H6
NOT SETTLED: no file gives one ordered decision procedure over all five kinds, and no charter for rules or practices exists.
Fragments the text does give: axioms/README.md and methodology/README.md separate an axiom (a "standing commitment", "not declinable") from a "situated move"; methodology/README.md separates style from method by "what a reviewer would inspect" (the output means style, how you arrived means methodology); and the schema `trace` field separates a rule (leaves an observable trace) from a practice (leaves none).
VISION.md adds that procedures "carry ... out" the work, while "rules and practices ... hold inside" units of work.
GUESS at the order: (1) Is it always in force, whatever the task? If so, axiom. (2) Is it judged by reading the artifact alone? If so, style. (3) Is it a named sequence of steps you follow when you are in a stated situation? If so, method. (4) Otherwise it holds inside the work: does it leave an observable trace a check could test? If so, rule; if not, practice.

### OBSERVATIONS
- The schema (`rule`, `practice`, `method`, the `RU`/`PC` prefixes, `trace`), tools/check-enforcers.sh (`rules/RU*.md`, "from Delta-1") and schemas/tests/catalog-entry/catalog-entry.test.mjs (`methods`, `rules`, `practices`) all refer to layers that do not exist: there is no directory, no `<prefix>0` charter, no row in the README.md Mechanics table and no INDEX.md section for any of them. The questions about rules/ and practices/ can therefore be answered only from the schema.
- The schema's own top-level description lists "axiom, style, methodology, role, pattern, domain, work-type or mission-required", which is stale against its enum (that enum also includes skill, contract, entity, component, artifact, trait, rule, practice and method).
- The schema `id` pattern `^(AR|MREQ|SC|RU|PC|A|S|M|R|K|W|D|P|C|E)-?[0-9]+$` has no `T`, yet traits/T1-T5 declare `id: T1`, etc. and `category: trait`. traits/ is not in the test's CATALOGUE_DIRS, so this is never checked. (Inferred: those entries would fail validation.)
- The discriminator in methodology/README.md ("read the output -> style") would file a non-writing repository rule such as "no credentials committed" under style/, which conflicts with style/README.md's scope of "Doc, commit, and naming conventions".
- methodology/README.md calls a traceless procedure a fault ("it is advice"), while the schema reserves traceless guidance for `practice`. That overlap between methodology and the planned practices layer is not resolved anywhere.
- M1's title says "minimum 4", but its body says "sometimes 3 is enough".
- README.md calls INDEX.md "the flat ledger across every category", but INDEX.md is grouped by layer.
- The corpus is in a transitional state: methodology/ is due to be renamed to methods/ under "Delta-1", per the test comment.
