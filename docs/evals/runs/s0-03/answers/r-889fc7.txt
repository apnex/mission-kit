### s0.Q3
No. By default it checks only the markdown files that changed.
style/README.md: "Style is gated on changed files rather than on the whole corpus. The corpus carries debt that predates the checkers, so gating the diff blocks new debt and converts the rest opportunistically as sections are edited."
tools/check-all.sh does this. It collects `.md` files from four sources: files changed against `origin/main` (or `--since REF`), unstaged changes, staged changes, and untracked files. Deleted files are excluded (`--diff-filter=d`). If no markdown changed, the style step reports PASS.
A whole-corpus run is opt-in with `tools/check-all.sh --all`. A per-rule tool run with no file arguments also defaults to every markdown file (`style_files` in tools/lib/style-common.sh).
The non-style gates (structure, enforcers, index, schemas and others) run on every invocation, and the tools' `*.test.sh` behaviour tests run "unconditionally".
Not every file is checked by every rule: a file can opt out of one rule with `<!-- style-check: allow SN -->`, and a file with a "GENERATED FILE" marker opts out of all of them (style_exempt).

### s0.Q5
There is no style rule for comments in source code.
The nearest rule is S8 (style/S8-code-block-comments-not-prose.md). It covers comments "inside code blocks" in documents, and its examples are all fenced blocks in markdown. Its tool reads only markdown fences, and check-all.sh passes only `.md` files to the style tools.
Source-code doc comments are covered by a skill, not by a style rule: K27, skills/write-discoverable-code/SKILL.md ("One-line doc comment on every export", "Write the plain-words phrase in the doc comment").
Where a new rule would go: the M0 placement test (methods/README.md), question 3, "Does it govern how an artifact is written - its form, whatever the work was? Style, in `style/`". S0 also says style covers "Doc, commit, and naming conventions" and "Rules about the artifact itself".
To be accepted it must meet S0's "What earns an entry" test (a real defect, shown to a reader), and S0 prefers a rule a script can hold.
NOT SETTLED: whether style/ is meant to cover source files. S0 says only that "The artifact is usually a document", and the current gate would never check a source file.
GUESS: if a team wants a rule only for its own codebase, S0's exclusion of "a rule that only holds inside one document" suggests it belongs in that project rather than in this corpus.

### s0.Q7
style/README.md, "Faults", lists four population faults:
an unfalsifiable convention ("be clear", "be concise", no predicate, so it is cited only when someone already disagrees);
an orphaned rule (nobody enforces it and nobody reviews it, "which teaches readers that the layer is decorative");
a forked enforcer (two tools hold one rule and disagree at the edges);
a corpus-wide sweep (all legacy debt converted in one commit, "hiding a real change inside it").
The "What earns an entry" section adds two more signs: entries that rest on aesthetic preference, or rules that hold only inside one document.
methods/README.md adds the reverse misfiling: "The style rule in process clothing", meaning a convention about the artifact filed in methods/.
check-enforcers.sh adds two mechanical signs: a rule naming a tool that does not exist ("a broken promise") and an unclaimed tool ("orphaned").

### OBSERVATIONS
1. There is a live forked enforcer for S13. tools/s13-plain-ascii.sh exempts the Box Drawing block: its grep skips U+2500-257F, matching S13's "Box drawing" exception. tools/check-standing-context.sh (the "plain ASCII (S13)" section) flags every non-ASCII character with `[^\x00-\x7F]`. The two tools disagree on box drawing, which is exactly S0's forked-enforcer fault. check-enforcers.sh cannot detect it, because it only pairs tools named `tools/s[0-9]*-*`. The one-tool-per-rule guarantee is therefore enforced only for tools that follow that naming convention.
2. S0 says check-enforcers verifies that "a tool no rule claims is orphaned". The script only checks tools/s[0-9]*-*, and only against style/S*.md, even though it also scans rules/RU*.md for `enforced-by`. A tool that enforces an RU rule could therefore never be detected as orphaned.
3. check-all.sh's comment block repeats one passage almost word for word ("Committed against the base, plus staged, plus unstaged ..." appears twice), which looks like an edit residue. The style gate also checks only `.md`, so the scope of style/ beyond markdown is unclear (see Q5).
4. check-all.sh notes that check-charter-shape.sh is suspended (tracked as B17), so charter shape is not gated at present.
