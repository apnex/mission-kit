### system-boundary.S1
A3, A4, A8, A9, A14 only - the `any-system` floor (axioms/README.md, Applicability matrix: "`any-system` | A3 ... A4 ... A8 ... A9 ... A14").
The launcher has none of the five traits: no state (T1), it is a one-shot script, not a reconciler (T2), there is no second independent actor (T3), an operator watches it, so a human would see a failure (T4 test), and there is no model (T5); entities/E5-system.md says "A one-shot script with no traits is a system, bound by the axioms every system carries."
The launcher and service compose: "A launcher that hands sessions to a service through a declared interface composes with it" (E5, Contain/Compose).
axioms/README.md: "A system it only composes with, through a contract the change leaves as it was, is not altered, and its axioms do not bind." So none of the service's axioms (A1, A5, A6, A7, A10, A13) bind.
Separately, the organisation's axioms govern how the change is made and recorded, and the organisation is not one of the systems the change alters (E5, "The organisation doing the work is a system").

### system-boundary.S2
The union of both systems: A1, A3, A4, A5, A6, A7, A8, A9, A10, A13, A14 (not A2, A11, A12).
axioms/README.md: a change answers to "any system whose contract with it the change alters", and E5 says "changing an unversioned interface alters every consumer at once, so the change answers to all of them immediately."
The service is stateful (T1 -> A1), multi-agent (T3 -> A5, A6, A7, A10, A13) and autonomous (T4 -> A7, A10, A13), plus the floor; it is not declarative (no A2) and has no model (no A11, A12).
The launcher adds nothing beyond the floor.
E5 also says: "Adding versioning to an interface you are changing moves it toward A3's limit and is encouraged, not required; if it is not done, the gap is recorded."

### system-boundary.S3
The service's full set: A1, A3, A4, A5, A6, A7, A8, A9, A10, A13, A14.
E5: "A module inside a service is a system, and the service contains it ... A system has every trait any part it contains has." axioms/README.md: a change answers to "the system it modifies, every system containing it".
The module being stateless on its own does not help, because the change answers to the containing service. E5 warns against exactly that escape: "a stateful system escapes its own axioms by being described as stateless modules, each of which passes on its own."
The module on its own adds only the floor, which the service's set already includes.

### system-boundary.S4
A3, A4, A8, A9, A14 only - the library's own floor, because it has no traits.
The ten consumers compose with the library through a declared, versioned interface that this change leaves as it was, so they are not altered (axioms/README.md, as in S1).
E5: "Publishing a new version of an interface alters no consumer that has not adopted it; each adoption is a change to that consumer, and answers to that consumer's axioms; the component is not altered by being adopted."
E5 states the intended outcome: otherwise "a small shared library would carry the axioms of every system that uses it, and the most-reused code would carry the most obligations."
A caveat: if a consumer had declared a version range, "a release within it alters every consumer bound by the range" (E5), but the question says each consumer adopts as its own change, so this does not apply.

### system-boundary.S5
The service's full set: A1, A3, A4, A5, A6, A7, A8, A9, A10, A13, A14.
No boundary is declared, and the service depends on the log lines, so E5 applies: "for deciding what binds a change they are one system, with the traits of both" (also axioms/README.md: "the axioms either unit would bring all bind").
Two other things are wrong.
First, the undeclared dependency is itself a fault under A3: "The undeclared dependency is itself a fault against A3, which requires units to interact only through declared contracts" (E5 Boundaries).
Second, your change owns fixing it: "A change that alters what an undeclared neighbour reaches into owns that boundary: declaring and honouring the interface is inside its scope, not optional" (E5).
Also, the service treats log output as a contract in fact: "Behaviour another unit depends on without any declaration is a contract in fact, not a declared boundary - and a change to it reaches across" (E5). So the format change can break the service.

### system-boundary.S6
It is defined in entities/E5-system.md: "A system is a unit of engineering with a boundary: what is inside it, and the contracts through which anything outside reaches it."
The boundary separates it from a neighbour "only where it is declared and honoured"; otherwise the two units "are one system for deciding what a change answers to."
"Traits describe a system, and axioms bind it." Systems relate in exactly two ways, contain and compose.
E5 also states what a system is not: it is "Not a repository, a deployment unit or a process by definition", it is "Not defined by size or by traits", and the organisation doing the work is also a system.
entities/E6-component.md adds that a component is "a system seen as a part of a larger system that contains it."

### OBSERVATIONS
- I inferred the launcher's traits by applying the T1-T5 tests to the scenario; the corpus does not classify it directly. The closest calls are T4 (an operator watching means a human would see a failure, so not autonomous) and T3 (an operator running a deterministic script is not two independent actors handing work across).
- The version-range clause in E5 ("a release within it alters every consumer bound by the range, whether or not the consumer's own files change") does not obviously fit A0's rule that a change binds only systems "whose contract with it the change alters". It is NOT SETTLED whether a release that changes only internals, inside a declared range, alters the consumers bound by that range. This did not decide S4, because S4 rules out ranges.
- E5 and A0 separate the organisation-as-system from the product's systems. I left the organisation's axioms out of every answer above, following E5's statement that they "are not one of the systems the change alters".
- In S5 the service, or the larger merged system, may also have an A7 concern, since a format change can silently break the service's parsing. That is my inference. The corpus only says A7 binds, not what it demands here.
- INDEX.md says to resolve links against a GitHub fallback when no local checkout exists. I used only the local corpus files, as instructed.
