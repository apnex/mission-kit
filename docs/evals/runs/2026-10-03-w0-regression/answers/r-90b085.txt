### system-boundary.S1
Only the launcher's axioms apply: the floor, A3, A4, A8, A9 and A14.
axioms/README.md says "a change answers to every system it alters" and "A system it only composes with, through a contract the change leaves as it was, is not altered, and its axioms do not bind."
entities/E5-system.md gives this exact case as composition: "A launcher that hands sessions to a service through a declared interface composes with it". The boundary is also honoured here, because nothing else crosses it.
The launcher has no traits. E5 says "A one-shot script with no traits is a system, bound by the axioms every system carries". Per the matrix in axioms/README.md and the applies-to fields I checked, those are the `any-system` axioms: A3, A4, A8, A9 and A14.
The service's axioms (A1, A5, A6, A7, A10, A13) do not bind this change.

### system-boundary.S2
The union of both systems' axioms applies: A1, A3, A4, A5, A6, A7, A8, A9, A10, A13 and A14. Only A2, A11 and A12 do not apply.
axioms/README.md says a change answers to "any system whose contract with it the change alters". E5 says "changing an unversioned interface alters every consumer at once, so the change answers to all of them immediately."
The service has these traits:
- Stateful (T1), which brings in A1.
- Multi-agent (T3), which brings in A5, A6, A7, A10 and A13.
- Autonomous (T4, "no human in the synchronous loop"), which brings in A7, A10 and A13.
It is not declarative (T2, so no A2) and has no model in the loop (T5, so no A11 or A12; A5 still binds through multi-agent).
E5 also says "Adding versioning to an interface you are changing ... is encouraged, not required; if it is not done, the gap is recorded."

### system-boundary.S3
The service's full set applies: A1, A3, A4, A5, A6, A7, A8, A9, A10, A13 and A14.
axioms/README.md says a change answers to "the system it modifies, every system containing it". E5 says "A module inside a service is a system, and the service contains it, whether or not the module's interfaces are declared. A system has every trait any part it contains has."
The module having no state of its own changes nothing. E5 warns against "a stateful system escapes its own axioms by being described as stateless modules", and traits/README.md says the same.
If the change also altered a neighbouring module's contract, that neighbour would be altered too. The question does not say it does.

### system-boundary.S4
Only the library's axioms apply: the floor, A3, A4, A8, A9 and A14.
The library has no state and no model. axioms/README.md: "a plain library takes `any-system`."
None of the ten consumers is altered, for two reasons:
- The contract is unchanged ("A system it only composes with, through a contract the change leaves as it was, is not altered").
- The interface is versioned. E5: "Publishing a new version of an interface alters no consumer that has not adopted it; each adoption is a change to that consumer, and answers to that consumer's axioms; the component is not altered by being adopted."
E5 names the opposite reading as a known error: "a small shared library would carry the axioms of every system that uses it".
One caveat comes from E5: "A declared version range ... is adoption in advance: a release within it alters every consumer bound by the range". The question says each consumer adopts separately, so no range applies here.

### system-boundary.S5
The union applies: A1, A3, A4, A5, A6, A7, A8, A9, A10, A13 and A14. Something else is also wrong: the undeclared dependency is itself an A3 fault, and your change has to fix it.
E5: "Where one unit depends on another and nothing declares the boundary between them ... they are one system, with the traits of both". It also says "Behaviour another unit depends on without any declaration is a contract in fact, not a declared boundary - and a change to it reaches across." axioms/README.md says the same.
So the launcher plus the service count as one system that is stateful, multi-agent and autonomous.
What is wrong: E5 says "The undeclared dependency is itself a fault against A3". A3's Air-Gap Principle says "units interact only through declared adapters and contracts".
E5 also says "A change that alters what an undeclared neighbour reaches into owns that boundary: declaring and honouring the interface is inside its scope, not optional." So this change must declare an interface and move the service's parsing onto it.
GUESS: as written, the change will probably break the service's log parser, which is the Logic Leakage fault A3 names.

### system-boundary.S6
It is defined in entities/E5-system.md under "Definition". A system is "a unit of engineering with a boundary: what is inside it, and the contracts through which anything outside reaches it."
"The boundary separates it from a neighbour only where it is declared and honoured". Where a boundary is undeclared or bypassed, "the two are one system for deciding what a change answers to."
Systems relate in exactly two ways: "Contain" and "Compose". "Traits describe a system, and axioms bind it."
Under Boundaries, E5 says a system is "Not a repository, a deployment unit or a process by definition" and "Not defined by size or by traits." It also says "The organisation doing the work is a system."
entities/E6-component.md adds that a component is "a system seen as a part of a larger system that contains it".

### OBSERVATIONS
- Possible conflict over versioning. axioms/README.md says work that touches a gap "closes as much of it as the touch allows". A3's mechanics expect "explicit, versioned contracts". But for S2, E5 says adding versioning "is encouraged, not required". It is NOT SETTLED whether changing an unversioned interface "touches" the missing-versioning gap closely enough to make versioning mandatory.
- Possible conflict over version ranges. E5 says a release inside a declared range "alters every consumer bound by the range" even when the consumer's own files do not change. axioms/README.md says a system composed with "through a contract the change leaves as it was, is not altered". For an internals-only release inside a range, these two point in different directions. NOT SETTLED.
- T4 requires the system to be expected to "operate, and to recover from failure" without a human. The prompt does not say whether the service is expected to recover. My answers do not depend on this, because multi-agent already brings in A7, A10 and A13.
- E5 says the organisation doing the work is a system whose axioms "govern how the change is made and recorded". In S1-S5 I answered only for the product systems, which is what E5 says the question is about.
