### system-boundary.S1
A3, A4, A8, A9, A14 - the `any-system` floor only (axioms/README.md, Applicability matrix; the same tags appear in each axiom's `applies-to`).
The launcher has no traits: it is not stateful (T1 test fails, it holds no state), not multi-agent (one operator using a tool; T3: "One actor using several tools is not multi-agent"), not autonomous (an operator watches it, so T4's test "would a human see it" is yes), not declarative, and has no model (T5). E5 Boundaries says "A one-shot script with no traits is a system, bound by the axioms every system carries".
The service is not bound: A0 says "a change answers to every system it alters ... A system it only composes with, through a contract the change leaves as it was, is not altered, and its axioms do not bind". E5 uses this exact case: "A launcher that hands sessions to a service through a declared interface composes with it."
No containing system is declared, so there is no containing system to add.
The organisation's axioms govern how the change is made and recorded, but they are a separate question from which systems the change answers to (E5, "The organisation doing the work is a system").

### system-boundary.S2
The launcher's floor (A3, A4, A8, A9, A14) plus every axiom the service brings into force: A1, A3, A4, A5, A6, A7, A8, A9, A10, A13, A14. A2, A11 and A12 do not bind.
A0: a change answers to "any system whose contract with it the change alters". E5: "changing an unversioned interface alters every consumer at once, so the change answers to all of them immediately."
The service's traits are stateful (T1, persistent state), multi-agent (T3, independent actors handing work), and autonomous (T4, no human in the synchronous loop). It is not declarative (no T2) and has no model (no T5). Traits bind by union (T0, "How traits compose").
That gives A1 (stateful); A5, A6, A7, A10, A13 (multi-agent, and also autonomous for A7/A10/A13); and the floor.
E5 also says adding versioning to the interface "is encouraged, not required; if it is not done, the gap is recorded" (see OBSERVATIONS for a possible tension with A0).

### system-boundary.S3
The service's full set: A1, A3, A4, A5, A6, A7, A8, A9, A10, A13, A14 (not A2, A11, A12).
E5: "A module inside a service is a system, and the service contains it, whether or not the module's interfaces are declared. A system has every trait any part it contains has."
A0: a change answers to "the system it modifies, every system containing it". So the module being stateless on its own does not matter.
E5 "Why precision matters" names the failure this rule prevents: "a stateful system escapes its own axioms by being described as stateless modules".
The module's own floor axioms (A3, A4, A8, A9, A14) are already in the service's set.

### system-boundary.S4
A3, A4, A8, A9, A14 - the `any-system` floor only. A0's matrix says "a plain library takes `any-system`".
The library has no traits, and the change leaves the declared, versioned interface and its behaviour unchanged. So no consumer's contract is altered, and A0 says composing systems "are not altered, and [their] axioms do not bind".
E5: "Publishing a new version of an interface alters no consumer that has not adopted it; each adoption is a change to that consumer, and answers to that consumer's axioms; the component is not altered by being adopted."
E5 "Why precision matters" rejects the opposite reading: "a small shared library would carry the axioms of every system that uses it".
Caveat from E5: a declared version range ("any 2.x") is "adoption in advance", so a release would alter any consumer bound by a range. The question says each consumer adopts as its own separate change, so I take it that no ranges are in play. GUESS: that reading is what the question intends. The text does not settle it.

### system-boundary.S5
The same set as the service: A1, A3, A4, A5, A6, A7, A8, A9, A10, A13, A14 (not A2, A11, A12). This is because the launcher and service are now one system for binding.
E5: "where one unit depends on another across a boundary nobody declared ... the two are one system"; "for deciding what binds a change they are one system, with the traits of both". A0 says the same thing: "the axioms either unit would bring all bind".
Something else is wrong. E5 says "The undeclared dependency is itself a fault against A3", whose Air-Gap Principle says "units interact only through declared adapters and contracts".
Your change also owns fixing that fault. E5 Boundaries says "A change that alters what an undeclared neighbour reaches into owns that boundary: declaring and honouring the interface is inside its scope, not optional."
Declaring the boundary and moving the service's parsing onto it "is what makes them two again" (E5).

### system-boundary.S6
It is defined in entities/E5-system.md: "A system is a unit of engineering with a boundary: what is inside it, and the contracts through which anything outside reaches it."
The boundary separates it from a neighbour "only where it is declared and honoured - written down, and the only way the neighbour reaches it".
"Traits describe a system, and axioms bind it". Systems relate in exactly two ways, contain and compose.
E5 also says what a system is not: it is "Not a repository, a deployment unit or a process by definition" and "Not defined by size or by traits".
entities/E6-component.md adds that a component is "a system seen as a part of a larger system that contains it". axioms/README.md (A0) points to E5 for these terms.

### OBSERVATIONS
- Possible tension between A0 and E5 on S2. A0 says "work that touches a gap closes as much of it as the touch allows", where the touch is "the part the change already alters to do its own work". A3's Semantic Bit-Masking says "interfaces are explicit, versioned contracts", so an unversioned interface is a gap A3 names, and an S2 change alters exactly that interface. Yet E5 says adding versioning "is encouraged, not required; if it is not done, the gap is recorded". I followed E5, since it speaks to this case directly. Whether A0's direction rule makes versioning mandatory here is NOT SETTLED.
- S4: the corpus does not say whether the consumers declare version ranges. That decides whether a release alters them (E5's "adoption in advance").
- Launcher traits: the T4 test is about whether a human would see a failure before the system acted on it. "One operator watches it" answers this. "Does not restart anything that dies" is irrelevant to T4 once a human is watching. I read the launcher as having no traits.
- S5: there is no declared interface, so the session handoff itself is also undeclared. The merge into one system holds either way.
