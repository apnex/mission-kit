### component.C1
Y: your fix modifies X, and X already depended on Y, so Y is not "touched" (axioms/README.md: "A change touches what it modifies, what it newly depends on, and any consumer whose contract it alters"). But Y is adjacent to X, because they share a declared interface and X "stands on" Y, which is the closer direction (entities/E6-component.md, "Adjacent against nearby"). So fixing Y is "encouraged, never mandated", and you are "expected to weigh doing it, not merely permitted to". It may be closed opportunistically under A14 tangent discipline: payback is near, the yield is captured, and the cost "does not significantly distract" (axioms/README.md; axioms/A14-compounding-learning.md, "Friction -> root cause, never workaround"). A five-minute fix for friction that cost twenty minutes appears to pass that test (GUESS: on these numbers it does). If you fix it, do it "as a change of its own" that answers to every system it alters, including Y's consumers if the error text is part of Y's contract. Z: X does not use Z, so Z is nearby, not adjacent, and a two-day fix "displace[s] the goal". So Z is "recorded with its evidence and a revival trigger (RU3) rather than closed", and the director makes the larger choice (axioms/README.md; rules/RU3-anti-amnesia-deferral.md). Hidden in-process state is A1's "Hidden State Problem" (axioms/A1-sovereign-state-transparency.md), and whatever you choose, "Either way the gap is recorded. Passing it silently is what the axiom forbids."

### component.C2
It is defined in entities/E6-component.md: "A component is a system seen as a part of a larger system that contains it", with "one duty" at that altitude, and it "exposes and consumes interfaces". So it is not a different kind of thing: "Every component is a system; component names its place in a containing system". The difference is which question you are asking. "Traits, axioms and what a change answers to are questions about a system. Duty, interfaces, neighbours and blast radius are questions about a component" (E6, "Component against system"; also entities/E5-system.md, "A system against a component"). A system that nothing contains, such as a whole product seen from outside, "is not a component of anything". E5 defines system as "a unit of engineering with a boundary" that "traits describe and axioms bind". A component is also not a file, module, package, repository or deployable by definition, not a SysML part, and not necessarily a registered or shareable unit (E6, Boundaries).

### component.C3
No. "A component's directory addresses it... Its boundary is its declared interfaces" (entities/E6-component.md, "Boundary against directory"). E5 agrees: a directory "is the boundary of neither the system nor the component" (entities/E5-system.md). Nothing declares an interface here, so nothing separates the two. For deciding what a change answers to, parts/thing and parts/other are "one system, with the traits of both" (E5, Boundaries; E6, Definition: a part with undeclared interfaces "is still a component, but nothing separates it yet"). What is wrong: the undeclared dependency "is itself a fault against A3", which breaks the Air-Gap Principle: "no unit reaches into another's internals" (axioms/A3-sovereign-composition.md). The remedy is to declare thing's interface and move other onto it. A change that alters what other reaches into "owns that boundary: declaring and honouring the interface is inside its scope, not optional" (E5). E6's blast-radius row also says a change to thing reaches "any unit that reaches it... with no declared interface". So a change to thing's internals answers to other as well.

### component.C4
Your change answers to the systems it alters: P, which it modifies, and "every system containing it", which is the service. It does not alter "any system whose contract with it the change alters", because no contract changed (axioms/README.md, "What brings an axiom into force"). Q is not altered. Q composes with P "through a contract the change leaves as it was", so "its axioms do not bind" as Q's own (axioms/README.md; entities/E6-component.md blast radius: an adjacent component is reached "only if the interface between them changes"). There is a caveat: the service contains Q, and "A system has every trait any part it contains has" (entities/E5-system.md, Contain; also line 85). So the service's axioms, which you do answer to, include those brought in by Q's traits. Yes, Q is a candidate for opportunistic improvement, because it is adjacent: "one that stands on it, through a declared interface" (axioms/README.md). The direction matters: Q stands on P, but your work does not stand on Q, so this is "adjacency with less payback, not none" (E6, "Adjacent against nearby"). If you do it, it is a separate change, subject to the A14 tangent test and recorded either way. This assumes Q honours the interface and does not reach past it. If Q bypassed the interface, Q and P would be one system (E5, "Declared against honoured").

### OBSERVATIONS
- C1/Z: T1 requires state that "persists beyond a single operation" and that something treats as authoritative. "Hidden in process memory" may not count as persistent, so it is NOT SETTLED whether Z makes the service stateful and so brings A1 into force (A1 binds only `stateful`). A1's mandate does forbid "transient truth", but that matters only if A1 is in force. This does not change the answer about Z: it is not adjacent, and it is not in the change's scope.
- C1/Y: the corpus does not say whether an error message is part of a declared interface. That decides whether fixing Y alters its consumers' contracts and so answers to them.
- C4: two statements pull against each other. A0 says Q's axioms "do not bind" when Q is not altered. E5 line 85 says a change inside one system answers to the containing system, which has the traits of every part, Q included. Read together, Q's traits bind indirectly through the service. A cold reader could take A0's sentence as saying they do not bind at all.
- A0's "touched" list (modifies, newly depends on, contract altered) does not cover a component the change already depended on and still depends on, as Y does in C1. So Y falls to adjacency rather than scope, which seems intended but is not stated.
