### design-rulings.R1
Your change must declare the interface between T and N and have N honour it; this is not optional. entities/E5-system.md, Boundaries: "A change that alters what an undeclared neighbour reaches into owns that boundary: declaring and honouring the interface is inside its scope, not optional." Until that happens, N and T are "one system, with the traits of both" for deciding what binds the change (E5 Boundaries; axioms/README.md "What brings an axiom into force"), and the undeclared reach is itself an A3 fault (A3 Air-Gap Principle). How it ends: the interface is evaluated against T's duty, and then either N is moved onto the interface or the interface is adjusted to what N legitimately needs (E5 "Declared against honoured"; A3 "Bypass as Signal"). Because N and T sit inside one service, the change also answers to the containing service and all its traits (E5 "Contain"; A0 "a change answers to every system it alters"). If the new interface is not versioned, adding versioning is encouraged but not required, and the gap must be recorded if you do not add it (E5, "A versioned contract...").

### design-rulings.R3
Yes, the service is stateful. The module passes T1's test ("Does the system write something it will later read back, and would anything act differently if that record were wrong?" traits/T1-stateful.md), and "A system has every trait any part it contains has" (E5 "Contain"; traits/README.md "How traits compose": "a service with one stateful module is stateful"). A1 applies-to [stateful], so it binds the service. Your change to a stateless module answers to "the system it modifies, every system containing it" (axioms/README.md), so A1 binds your change through the containing service, even though the module you touch holds no state. E5 states the reason: otherwise "a stateful system escapes its own axioms by being described as stateless modules". In practice the change must not move the service further from A1's limit, and must move it closer as far as the change's own scope allows (A0 "Standing commitment").

### design-rulings.R4
Yes: A1 binds the organisation's records of its work, not the tool. entities/E5-system.md: "The organisation doing the work is a system... A stateless product built by a team that keeps records it relies on has `A1` binding the team's records, not the product." The tool is stateless and has no model, so the stated facts give it no trait that brings in A1 (A1 applies-to [stateful]). The team writes records and reads them back to rely on them, which passes T1's test. E5 keeps the two questions separate: the organisation's axioms "govern how the change is made and recorded, and are not one of the systems the change alters." (Because work passes between actors, the organisation is also multi-agent and has A5, A6, A7, A10 and A13 (T3), but the question asks only about A1.)

### design-rulings.R5
The split is encouraged and you are expected to weigh it, but it is not required. The exception: any part your feature already alters must not repeat the tangle, and must close as much of it as that touch allows (axioms/README.md: "new work never repeats a gap the axiom names... *As much as the touch allows* means the part the change already alters to do its own work; restructuring beyond that, even inside the same component, is the encouraged improvement below, not a requirement"). A3 "Composable by Default" encourages this kind of fracture "within the unit's own duty... as a change of its own, answering to every consumer whose interface it alters." If you make the split, make it a separate change. K's interface is unversioned, so the split "alters every consumer at once" and answers to all three consumers immediately (E5); adding versioning is encouraged, and if you do not add it the gap is recorded. If you decline the split, record the gap with its evidence and a revival trigger (A0; RU3), because "Passing it silently is what the axiom forbids." NOT SETTLED: whether the tangent-discipline test (A0/A14) is the bar for restructuring inside the touched component itself, because the text applies it explicitly only to adjacent components.

### design-rulings.R6
All ten. entities/E5-system.md: "A declared version range - *any 2.x* - is adoption in advance: a release within it alters every consumer bound by the range, whether or not the consumer's own files change." Using only the declared interface does not protect them here, because 2.4 changes the behaviour that interface documents, so each consumer's contract with L is altered (A0: a change answers to "any system whose contract with it the change alters"). Publishing 2.4 therefore answers to all ten consumers' axioms. NOT SETTLED: whether a consumer whose lockfile pins an earlier 2.x counts as "bound by the range"; the corpus does not mention lockfiles. GUESS: a lockfile is a narrower declared version, so the release would not alter that consumer until the lockfile is updated.

### OBSERVATIONS
- E5 says declaring and honouring an undeclared neighbour's interface is "not optional", but A0 limits a change's mandatory scope to "the part the change already alters". The two can be reconciled (the interface N reaches is part of what the change alters), but neither text says so.
- A0's tangent-discipline test is stated for adjacent components. Its rule for restructuring beyond the touch inside the same component points to "the encouraged improvement below" without saying whether the same adjacency/payback/cost test applies.
- E5 treats a floating range as adoption in advance, but does not address lockfiles or resolved versions, which decide in practice whether a consumer actually receives the release.
- R2(1): E5's chaining sentence talks about C, but does not say outright that the A-B merge (B's traits) still applies to a change only A uses. I inferred it from the general undeclared-dependency rule.
