### component.C2
It is defined in entities/E6-component.md: "A component is a system seen as a part of a larger system that contains it", with "one duty at the altitude where it appears as a part", and it "exposes and consumes interfaces". "Every component is a system; component names its place in a containing system, not a different kind of thing." The difference is which question you ask: "Traits, axioms and what a change answers to are questions about a system. Duty, interfaces, neighbours and blast radius are questions about a component" (E6, Discriminators). A system is defined in entities/E5-system.md as "a unit of engineering with a boundary", which traits describe and axioms bind. E6 adds: "A system nobody contains ... is not a component of anything", and a component's boundary is its declared interfaces, not its directory (E5, E6). E6 also says a component is not a file, module, package, repository, deployable, SysML part, or necessarily a registered (components/) unit.

### component.C3
No. "A component's directory addresses it ... Its boundary is its declared interfaces" (E6, "Boundary against directory"), and E5 agrees: a directory "is the boundary of neither the system nor the component". parts/thing/ is still a component, but "nothing separates it yet": for deciding what a change answers to, thing and other are "one system with whatever reaches into it" (E6 Definition; E5 Boundaries: "one system, with the traits of both"). What is wrong is that the undeclared dependency "is itself a fault against A3" (E5), breaking A3's Air-Gap Principle ("no unit reaches into another's internals"). The fix is to declare the interface and move other onto it: "Declaring the boundary, and moving the dependency onto it, is what makes them two again" (E5). A change that alters what other reaches into "owns that boundary: declaring and honouring the interface is inside its scope, not optional" (E5). other is a real consumer, so under A3's Earned Exposure the interface is earned and not speculative.

### component.C4
The change answers to P (the system it modifies) and every system containing P, here the service (A0: "the system it modifies, every system containing it, and any system whose contract with it the change alters"). Q only composes with P "through a contract the change leaves as it was", so it "is not altered, and its axioms do not bind" (A0; E6 blast radius: "an adjacent component only if the interface between them changes"). One subtlety: the service "has every trait any part it contains has" (E5, T0), so Q's traits still reach the change through the service, even though Q itself is not altered. This depends on Q honouring the interface; a Q that reaches past it would be one system with P (E5, "Declared against honoured"). Q is not touched, but it is adjacent, because it consumes what P exposes (E6). So it is a candidate for opportunistic improvement under A0/A14's tangent test, in "the other direction", which is "adjacency with less payback, not none" (E6), because Q stands on P rather than P on Q. If you pursue it, make it a change of its own; if not, record the gap with a revival trigger (A0, RU3).

### OBSERVATIONS
- E6 ("A detected crossing ... A3 states what it triggers") and A3's "Bypass as Signal" cover reaching past a declared interface; for the no-interface case (C3), the remedy is stated only in E5 Boundaries, so routing from E6 to A3 alone is incomplete.
- The corpus does not say whether error-message text is part of a declared interface, and that decides whether changing Y alters Y's other consumers.
- T1 says "persists beyond a single operation", but A1 demands durability "across any infrastructure restart". So it is unclear whether state held only in process memory makes a system stateful.
- E6 says a directory is "where its code and documents live", while E5 says a directory "places a component's documents". This is minor wording drift.
