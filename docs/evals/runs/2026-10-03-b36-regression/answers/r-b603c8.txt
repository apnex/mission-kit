### component.C2
It is defined in entities/E6-component.md: "A component is a system seen as a part of a larger system that contains it", with "one duty at the altitude where it appears as a part", and it "exposes and consumes interfaces". It is not a different kind of thing: "Every component is a system; component names its place in a containing system, not a different kind of thing." The difference lies in the question you ask. "Traits, axioms and what a change answers to are questions about a system", while "Duty, interfaces, neighbours and blast radius are questions about a component", which "only have answers relative to the whole it is part of" (E6 Discriminators; also entities/E5-system.md "A system against a component"). A system that nothing contains, such as a whole product seen from outside, "is not a component of anything until it is part of some larger whole". A component's boundary is its declared interfaces, and it is not a file, module, package, repository, deployable, SysML part or registered entry in components/ by definition (E6 Boundaries; "A component against a registered component").

### component.C3
No. "A component's directory addresses it ... Its boundary is its declared interfaces", and "A directory places a component's documents; it is the boundary of neither the system nor the component" (entities/E6-component.md "Boundary against directory"; entities/E5-system.md). With no declared interface, parts/thing/ "is still a component, but nothing separates it yet", so for deciding what a change answers to it is "one system with whatever reaches into it" (E6 Definition). So parts/other/ and parts/thing/ are "one system, with the traits of both", and the axioms either would bring all bind (E5 Boundaries; axioms/README.md). What is wrong: "The undeclared dependency is itself a fault against A3", which requires that "no unit reaches into another's internals" (A3 "Air-Gap Principle"). The fix is "Declaring the boundary, and moving the dependency onto it" (E5). A3's "Bypass as Signal" says the crossing should also prompt a check of what interface the component's duty should offer, and the answer may be to adjust that interface rather than only to correct the consumer (E6, A3). A change that alters what parts/other/ reaches into "owns that boundary: declaring and honouring the interface is inside its scope, not optional" (E5 Boundaries).

### component.C4
Your change answers to "the system it modifies, every system containing it, and any system whose contract with it the change alters" (axioms/README.md). Here that is P and the service that contains it. Q is not altered: it composes with P through a contract the change "leaves as it was", so "its axioms do not bind" (axioms/README.md; entities/E5-system.md "Contains against composes"; E6 "Blast radius": an adjacent component is reached "only if the interface between them changes"). Q is not in the change's mandatory scope either, because only a consumer "whose contract it alters" counts as touched (axioms/README.md). Q is still adjacent, because it shares a declared interface with P, and A0's opportunistic rule covers a component "that stands on it" as well as one the change stands on. So Q is a candidate, but in the direction of "adjacency with less payback, not none", because Q stands on P rather than P on Q (E6 "Adjacent against nearby"). Any improvement to Q must pass the tangent-discipline test and be made "as a change of its own" (axioms/README.md, A14). GUESS: if Q in fact depends on P behaviour that the interface does not promise, then E5 "Declared against honoured" applies, Q and P are one system for that pair, and Q could be altered; the question rules this out by saying behaviour is unchanged.

### OBSERVATIONS
- A14 "Tangent discipline" defines adjacency as one-directional ("infrastructure the main line will stand on"). A0 and E6 define it in both directions. E6 reconciles the two by calling A14's direction the "closer" one, but A14 alone would mislead a reader on C4.
- A0 says a component the change "newly depends on" is touched. It does not say whether an existing dependency (X on Y) is touched, so I inferred from the wording that it is not.
- E5 says a directory "places a component's documents", and E6 says it holds "its code and documents". These differ a little.
- No entry says whether error text is part of a declared interface. That decides whether a fix to Y alters Y's consumers.
- In C1, whether the service is stateful (and so whether A1 binds it) depends on facts the scenario does not give.
