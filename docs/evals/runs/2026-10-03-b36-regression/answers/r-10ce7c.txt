### layer-charters.H5
A rule must declare `trace` in frontmatter: "the observable in the record that shows it was kept or broken, required by the catalogue contract" (`rules/README.md`, "Member shape").
The schema enforces this. `schemas/catalog-entry/v1alpha1/catalog-entry.schema.json` makes `trace` required when `category` is `rule` and the id matches `^RU[1-9][0-9]*$`, with `minLength` 20.
A practice "declares no `trace`; if it acquires one, it is a rule and moves" (`practices/README.md`).
The optional field is `enforced-by`, naming the tool that checks the rule (pattern `^tools/`). RU0 says it is used "when a tool checks it", and `tools/check-enforcers.sh` checks that the named tool exists.
The schema's `trace` description says: "Naming a tool that checks it is enforced-by's job, and is optional". A rule with no tool "is still a rule, and is checked by reading the trace."

### layer-charters.H6
`methods/README.md` (M0, "Placement") gives the order. RU0 and PC0 cite it ("axiom, procedure, style, rule, practice, asked in that order"). Ask in order and stop at the first yes:
1. Is it a limit a system is built toward, in force for every system with the traits it names? If yes, it is an axiom (`axioms/`).
2. Does following it produce a result of its own, such as a verdict, an artifact or a record? If yes, it is a method (`methods/`). Guidance that only requires a record to carry something is not a method; it is a rule.
3. Does it govern how an artifact is written, its form whatever the work was? If yes, it is style (`style/`).
4. Does it leave a trace in the record of the work that a check could test? If yes, it is a rule (`rules/`).
5. Otherwise, it is a practice (`practices/`).
