### system-boundary.S1
The change answers only to the launcher's axioms: A3, A4, A8, A9, A14, the `any-system` floor (axioms/README.md applicability matrix; entities/E5-system.md Boundaries: "A one-shot script with no traits is a system, bound by the axioms every system carries").
The launcher has no traits: it holds no state (T1), is one operator with a tool (T3: "One actor using several tools is not multi-agent"), is watched (T4), and has no model (T5).
The launcher and the service compose through a declared interface that is honoured ("Nothing crosses ... except") and left unchanged, and A0 says "A system it only composes with, through a contract the change leaves as it was, is not altered, and its axioms do not bind" (axioms/README.md, "What brings an axiom into force").
So the service's axioms (A1, A5, A6, A7, A10, A13) do not bind this change.
A2, A11 and A12 bind neither system.
GUESS: separately, E5 says the organisation doing the work is a system whose axioms "bind how the work is done, separately from what is built", but that is not a system this change alters.

### system-boundary.S2
The change answers to the launcher's axioms and the service's, because A0 says a change answers to "any system whose contract with it the change alters" (axioms/README.md); the declared interface is that contract.
Launcher: A3, A4, A8, A9, A14 (floor only).
Service: stateful (T1) brings A1, multi-agent (T3) brings A5, A6, A7, A10, A13, and autonomous (T4) adds no new axioms beyond those; plus the floor.
Union: A1, A3, A4, A5, A6, A7, A8, A9, A10, A13, A14; not A2 (not declarative) and not A11/A12 (no model).
NOT SETTLED: the prompt does not say whether the interface is versioned; if it is, E5 says "Publishing a new version of an interface alters no consumer that has not adopted it", so the service's axioms would bind the service's adoption rather than the publishing change (entities/E5-system.md, "A versioned contract...").
GUESS: it is not versioned, so the service is altered directly.

### system-boundary.S3
It answers to the service's axioms: A1, A3, A4, A5, A6, A7, A8, A9, A10, A13, A14.
A0: a change answers to "the system it modifies, every system containing it" (axioms/README.md), and E5: "A module inside a service is a system, and the service contains it, whether or not the module's interfaces are declared" (entities/E5-system.md, Contain).
The module being stateless on its own does not matter; E5 "Why precision matters" names the error of "a stateful system escap[ing] its own axioms by being described as stateless modules, each of which passes on its own".
The module's own traits (none) would give only the floor, but the containing service is also altered.
NOT SETTLED: whether the change also alters a contract with a sibling module or outside system; if so, that system's axioms bind too.

### system-boundary.S4
Only the library's own axioms: A3, A4, A8, A9, A14 (the floor; A0 matrix: "a plain library takes `any-system`").
The consumers compose with the library through a declared, versioned interface that is unchanged, so they are not altered (axioms/README.md: "A system it only composes with, through a contract the change leaves as it was, is not altered").
Each consumer adopting the new version is a change to that consumer, and "answers to that consumer's axioms; the component is not altered by being adopted" (entities/E5-system.md, "A versioned contract...").
E5 "Why precision matters" names the opposite reading as the error: "a small shared library would carry the axioms of every system that uses it".
Caveat from E5: a declared version range is "adoption in advance", which would alter consumers bound by it; the prompt says each adopts separately, so none applies here.
GUESS: this assumes no consumer reaches past the interface into internals; any that did would be one system with the library (E5, "Declared against honoured").

### system-boundary.S5
With no declared interface and the service depending on launcher output, the two are "one system, with the traits of both" for this change (entities/E5-system.md, Boundaries; axioms/README.md: "the axioms either unit would bring all bind").
So the change answers to A1, A3, A4, A5, A6, A7, A8, A9, A10, A13, A14.
Something else is wrong: "The undeclared dependency is itself a fault against A3", which requires units "interact only through declared adapters and contracts" (E5 Boundaries; A3 Air-Gap Principle).
E5 also says "A change that alters what an undeclared neighbour reaches into owns that boundary: declaring and honouring the interface is inside its scope, not optional" - so if the log lines are part of what the service parses, the change must declare the interface and move the service onto it (or adjust the interface per A3 Bypass as Signal).
In practice the format change may also break the service's parsing (A3 Logic Leakage).
NOT SETTLED: whether the log lines are among the "some" output the service parses; if not, the two are still one system for binding, but the corpus does not clearly say whether declaring the boundary is then mandated or only expected under A0's beyond-scope rule.

### system-boundary.S6
It is defined in entities/E5-system.md: "A system is a unit of engineering with a boundary: what is inside it, and the contracts through which anything outside reaches it."
The boundary separates it from a neighbour "only where it is declared and honoured"; otherwise dependent units "are one system for deciding what a change answers to".
"Traits describe a system, and axioms bind it"; systems relate only by Contain or Compose.
E5 says it is not a repository, deployment unit or process "by definition", and not defined by size or traits; the organisation doing the work is also a system.
entities/E6-component.md adds that a component is "a system seen as a part of a larger system that contains it".

### axiom-direction.Q1
The service is stateful, so A1 binds it: "No functional unit possesses private, opaque, or transient truth" (axioms/A1-sovereign-state-transparency.md); the component is A1's "Hidden State Problem" fault, and as the service is multi-agent, A5's Perceptual Parity is relevant too.
A0's direction rule: inside your change's scope, "new work never repeats a gap the axiom names", so any state your feature holds must be durable and queryable by other agents, not in process memory (axioms/README.md).
If your feature touches the component, "work that touches a gap closes as much of it as the touch allows"; if you only newly depend on it, it is "touched but not altered, so its gaps must not be built on" - do not make your feature rely on its hidden state.
Beyond scope, fixing it is "encouraged, never mandated"; if it is adjacent (shares a declared interface, entities/E6-component.md), you may fix it as a separate change under A14 tangent discipline, if the payback is near and it does not distract much from your goal.
Otherwise record it with evidence and a revival trigger (RU3), because "Passing it silently is what the axiom forbids" and "Either way the gap is recorded."
The service is not wrong for being short of the limit; it would be wrong only if your change moved it further away (A0, "Standing commitment").

### axiom-direction.Q2
An axiom is "a load-bearing asymptote - a limit a system is built toward" (axioms/README.md, "Standing commitment, not situated move").
In my words: it tells each change which way to point, not whether the system passes a test.
It binds in two directions: "No change may move the system away from the limit, and each change moves it toward the limit as far as the change's own scope allows."
A system is "not wrong for being short of it; it is wrong for moving away from it."
A0's correction banner rejects the pass/fail reading, and its "conformance reading" fault explains why: with that reading, "no change advances the system, and the gaps the axioms name become permanent."
A gate only checks the direction rule: that the change "moved the system no further from any limit in force, and repeated no gap it touched."

### OBSERVATIONS
- INDEX.md tells the reader to resolve links against a checkout or fetch from GitHub `main`; I used only the local corpus as instructed, so I did not check if it matches `main`.
- E5 says the organisation doing the work is a system with its own axioms, but neither A0 nor E5 says whether a given change "alters" the organisation; per-change binding lists therefore leave it out, and this is ambiguous.
- S2 depends on whether the interface is versioned, which the prompt does not state; E5's versioned-contract rule would move the service's binding to its adoption.
- S5: "some of the launcher's output" does not say whether log lines are included. E5's "owns that boundary" clause applies only if they are, but the one-system merge applies either way, so the mandate to declare the interface is unclear.
- A3's mandate is phrased about "modules", but A3 is tagged any-system and is applied to whole systems such as a one-shot launcher; the fit is loose but not contradictory.
- A9 (Chaos-Validated Deployment) binds a one-shot, watched script's log-format change by the floor rule; this is consistent with the text but A0 itself calls A9 the least exercised axiom.
