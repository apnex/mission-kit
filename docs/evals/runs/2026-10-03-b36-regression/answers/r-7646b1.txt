### system-boundary.S3
The service's axioms: A1, A3, A4, A5, A6, A7, A8, A9, A10, A13, A14 (every axiom except A2, A11, A12).
A0: a change answers to "the system it modifies, every system containing it".

The module alone has no traits, so its own axioms are only the floor. The service that contains it is stateful, multi-agent and autonomous, and its axioms bind too.
E5 "Why precision matters" names the alternative reading as the failure: "a stateful system escapes its own axioms by being described as stateless modules, each of which passes on its own." T0 says the same: "a stateful system cannot escape its axioms by being described as stateless parts".

### system-boundary.S4
A3, A4, A8, A9 and A14 only: the library's own floor axioms.
The library has no traits (no state, no model; nothing in the prompt suggests multi-agent, autonomous or declarative), so A0's matrix gives it `any-system`: "a plain library takes `any-system`".
The consumers compose with it through a declared, versioned interface that the change leaves unchanged. A0: such a system "is not altered, and its axioms do not bind".
E5: "Publishing a new version of an interface alters no consumer that has not adopted it; each adoption is a change to that consumer, and answers to that consumer's axioms."
E5 names the opposite reading as the error: "a small shared library would carry the axioms of every system that uses it, and the most-reused code would carry the most obligations."
Caveat: E5 says a declared version range "is adoption in advance". The prompt says each consumer adopts as a separate change, so no ranges apply here.

### system-boundary.S6
It is defined in entities/E5-system.md: "A system is a unit of engineering with a boundary: what is inside it, and the contracts through which anything outside reaches it."
The boundary separates it from a neighbour "only where it is declared and honoured"; with an undeclared or bypassed boundary, "the two are one system for deciding what a change answers to".
Systems relate in exactly two ways: contain ("A module inside a service is a system, and the service contains it") and compose (they work together through a declared contract).
"Traits describe a system, and axioms bind it". A system is "Not a repository, a deployment unit or a process by definition" and "Not defined by size or by traits".
E6 adds that a component "is a system seen as a part of a larger system that contains it", and E5 notes that "The organisation doing the work is a system."

### axiom-direction.Q1
The component sits inside a stateful, multi-agent service, so A1 binds and so does A5 (via multi-agent). The component is short of both limits. A1: "No functional unit possesses private, opaque, or transient truth"; its faults are "Hidden State Problem - state lives inside a process" and "Ephemeral Truth Loss".
What you owe it depends on scope (A0). Your change "touches what it modifies, what it newly depends on, and any consumer whose contract it alters", and "code that merely sits beside it ... is not touched".
If you touch the component, you must close "as much of [the gap] as the touch allows". If you depend on it, "its gaps must not be built on".
If you do not touch it, "improvement is encouraged, never mandated". If it is adjacent and A14's tangent discipline supports it, you may close it as a change of its own. Otherwise you record it with evidence and a revival trigger (RU3), because what work happens next is the director's call (R4, AR3).
Either way "the gap is recorded", and "Passing it silently is what the axiom forbids".
For your feature: "new work never repeats a gap the axiom names". So any state the feature holds goes where every authorised actor can query it and where it survives a restart, not in process memory. The other axioms in force (A3, A4, A6, A7, A8, A9, A10, A13, A14) bind it at the same time (A0: "conjunctive in force").

### axiom-direction.Q2
An axiom is a direction, not a pass/fail test. A0 calls it "a load-bearing asymptote - a limit a system is built toward to stay aligned with its architecture's intent", and a system "is not wrong for being short of it; it is wrong for moving away from it."
So when I change a bound system, the axiom tells me two things at once: "No change may move the system away from the limit, and each change moves it toward the limit as far as the change's own scope allows."
In practice: do not repeat a gap the axiom names, close what my change touches as far as the touch allows, and record (not silently pass) gaps beyond my scope.
A0 names the opposite reading as a fault: "The conformance reading", under which "no change advances the system, and the gaps the axioms name become permanent". The CORRECTION banner in A0 records the director ruling for the asymptote reading.
Every axiom in force binds every change, and none can be traded against another: "a regression with thirteen consolations, not partial progress".
A gate checks the reachable part of this: "that the change moved the system no further from any limit in force, and repeated no gap it touched."

### OBSERVATIONS
- E5 says a declared version range means "a release within it alters every consumer bound by the range, whether or not the consumer's own files change". A0 says a consumer whose contract a change leaves as it was "is not altered". These conflict when a release inside a range leaves the interface and its behaviour unchanged, as in S4 if ranges had been used. The corpus does not say which wins.
- E5 says "The organisation doing the work is a system" and that its axioms bind how work is done "separately from what is built". A0's rule ("a change answers to every system it alters") never says how that organisational binding combines with the product binding when answering "which axioms does your change answer to". I listed product-system axioms only.
- For a launcher watched by one operator, the traits are judgement calls. T4's test ("would a human see it before the system acted on the failure") makes it non-autonomous. T3 says "a human reviewing an agent's output" is multi-agent but "one actor using several tools" is not, so a script is a tool, not an actor. Neither trait entry addresses a watched script directly.
- In S5, E5's "owns that boundary" clause depends on whether the change "alters what an undeclared neighbour reaches into". The merge rule applies either way. The corpus gives no rule for the case where it is unknown whether the parsed output includes the changed lines.
- A0 states that A6 is the only axiom that cannot bind a lone agent, yet A5, A7, A10 and A13 are also tagged multi-agent. They can bind a lone agent only through their other tags (llm-in-the-loop or autonomous). The claim holds, but how it holds is not obvious.
