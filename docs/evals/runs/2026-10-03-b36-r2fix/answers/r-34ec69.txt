### system-boundary.S1
The launcher's floor axioms only: A3, A4, A8, A9, A14 (axioms tagged `any-system`, axioms/README.md applicability matrix). The launcher has no traits: it holds no state (T1), has one actor (T3), has an operator watching it (T4), and has no model (T5). E5 Boundaries says "A one-shot script with no traits is a system, bound by the axioms every system carries". The launcher and the service compose through a declared, unchanged interface (E5 "Compose": "A launcher that hands sessions to a service through a declared interface composes with it"). A0 says "A system it only composes with, through a contract the change leaves as it was, is not altered, and its axioms do not bind". So the service's axioms (A1, A5, A6, A7, A10, A13) do not bind this change.

### system-boundary.S2
A1, A3, A4, A5, A6, A7, A8, A9, A10, A13, A14. These are the launcher's floor plus the service's axioms. A0 says "a change answers to every system it alters... and any system whose contract with it the change alters", so changing the declared interface alters the service as well as the launcher. The service is stateful (T1, giving A1), multi-agent (T3, giving A5 A6 A7 A10 A13) and autonomous (T4, giving A7 A10 A13). It is not declarative and has no model in the loop, so A2, A11 and A12 do not bind (applicability matrix). Caveat: E5 says "A versioned contract changes only for the systems that adopt the new version". If this interface is versioned, the service is altered only when it adopts the new version, and the question does not say whether it is versioned (NOT SETTLED).

### system-boundary.S3
The service's axioms: A1, A3, A4, A5, A6, A7, A8, A9, A10, A13, A14. E5 "Contain": "A module inside a service is a system, and the service contains it, whether or not the module's interfaces are declared. A system has every trait any part it contains has." A0: a change answers to "the system it modifies, every system containing it". E5 Boundaries adds that "a change to any of them answers to the containing system, which has the traits of every part it contains". It does not matter that the module holds no state on its own. E5 "Why precision matters" names the error this prevents: "a stateful system escapes its own axioms by being described as stateless modules". A2, A11 and A12 do not bind, because the service is neither declarative nor llm-in-the-loop.

### system-boundary.S4
Only the library's axioms, which are the floor: A3, A4, A8, A9, A14 (A0: "a plain library takes `any-system`"). The interface and its behaviour are unchanged, so no consumer's contract is altered. Under A0, a system you only compose with through an unchanged contract is not bound. E5: "Publishing a new version of an interface alters no consumer that has not adopted it; each adoption is a change to that consumer, and answers to that consumer's axioms; the component is not altered by being adopted." E5 "Why precision matters" rejects the other reading: "a small shared library would carry the axioms of every system that uses it". Caveat from E5: a declared version range (for example "any 2.x") is "adoption in advance", meaning a release within the range alters every consumer bound by it. The question says each consumer adopts separately, so that caveat does not apply here.

### system-boundary.S5
A1, A3, A4, A5, A6, A7, A8, A9, A10, A13, A14. With no declared boundary and the service depending on the launcher's output, E5 says "they are one system, with the traits of both". This also follows from A0: "the two are one system with the traits of both, and the axioms either unit would bring all bind". The merged system is stateful, multi-agent and autonomous, but not declarative or llm-in-the-loop, so A2, A11 and A12 still do not bind. Something else is wrong: "the undeclared dependency is itself a fault against A3" (E5 Boundaries; A3 Air-Gap Principle: "units interact only through declared adapters and contracts"). E5 also says "A change that alters what an undeclared neighbour reaches into owns that boundary: declaring and honouring the interface is inside its scope, not optional." NOT SETTLED: whether the log lines are part of the output the service parses ("some of the launcher's output"). GUESS: if they are, this change must declare the interface and move the service onto it. If they are not, the merge into one system still holds, but declaring the boundary is not clearly inside this change's scope.

### system-boundary.S6
It is defined in entities/E5-system.md. "A **system** is a unit of engineering with a **boundary**: what is inside it, and the contracts through which anything outside reaches it." The boundary separates it from a neighbour "only where it is **declared and honoured**". Where a unit depends on another across an undeclared boundary, or reaches past a declared one, "the two are one system". Traits describe a system and axioms bind it. Systems relate only by "contain" or "compose" (E5 Definition). A system is not a repository, deployment unit or process, and is not defined by size or traits (E5 Boundaries). E6 defines a component as "a system seen as a part of a larger system that contains it".

### OBSERVATIONS
- INDEX.md links work-types W1-W26 (for example work-types/W1-build-a-slice.md), but the corpus `work-types/` directory holds only README.md, so those links do not resolve. INDEX.md line 9 says the ledger is "the complete list" of entries.
- E5 "Contains against composes" says two units with no declared contract "do neither", and E5 Boundaries says they are "treated as one" system. These are consistent, but the reader has to read both passages to see that.
- S2: the corpus does not say whether an interface with no stated version counts as versioned. It also does not say which side owns the launcher-service interface, so whether the service is altered "on adoption" or straight away is unclear.
- S5: the merge rule is unconditional, but the "owns that boundary" duty depends on whether the change alters what the neighbour reaches into. The question does not settle that.
- E5 says the organisation doing the work is also a system whose axioms govern how a change is made and recorded. Those axioms are kept separate from the systems a change alters, and I excluded them from the answers above.
- A9 (Chaos-Validated Deployment) is on the `any-system` floor, so it binds even the one-shot launcher. This follows from the text but is odd in practice, and A0 itself calls A9 "the least exercised axiom".
