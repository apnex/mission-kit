### design-rulings.R1
Your change must declare the interface N relies on and move N onto it; it cannot leave the reach-in as it is. E5 (entities/E5-system.md, Boundaries) says: "A change that alters what an undeclared neighbour reaches into owns that boundary: declaring and honouring the interface is inside its scope, not optional." Until then N and T are "one system, with the traits of both" for deciding what binds the change, and the undeclared dependency "is itself a fault against A3" (E5; axioms/README.md, "What brings an axiom into force"). E5 calls N's reach "a contract in fact, not a declared boundary - and a change to it reaches across". So your change also touches N, a "consumer whose contract it alters" (A0). There are two ways to end a reach-in. One is that N "is moved onto the interface". The other is that "the interface is adjusted to what the consumer legitimately needs". The choice comes after you check the interface against T's duty (E5 "Declared against honoured"; A3 "Bypass as Signal"). Both modules sit inside one service, so the change also answers to that service, which is multi-agent by T3's test ("agents handing work along a pipeline").

### design-rulings.R2
(1) No. E5 Boundaries: "if A reaches into B and B into C, a change to A is one system with C only when it alters something B takes from C". A change that only A uses alters nothing B takes from C, so C's axioms do not bind it. A and B are still one system because of the undeclared reach (E5: "one system, with the traits of both"), so B's axioms do bind. (2) Yes. The change alters data that B takes from C, which is exactly the case where E5 merges the change with C. So C's traits and axioms bind it, and the undeclared reaches are A3 faults the change owns (E5: "owns that boundary"). GUESS: if the change is made inside C itself, it also binds C directly, because C is "the system it modifies" (A0).

### design-rulings.R3
Yes, the service is stateful. The module that writes records, reads them back and acts on them passes T1's test (traits/T1-stateful.md: "write something it will later read back, and would anything act differently if that record were wrong?"). A0 and E5 say "A system has every trait any part it contains has". Yes, A1 binds your change. A0 says a change answers to "the system it modifies, every system containing it", and E5 says "units inside one system need no chaining, because a change to any of them answers to the containing system". E5 names the failure this blocks: "a stateful system escapes its own axioms by being described as stateless modules". A0 limits how far the change must move toward A1's limit to its scope: it must not move away from that limit, and it must close any A1 gap it touches as far as the touch allows.

### design-rulings.R4
Yes. A1 binds the team's records, meaning the organisation as a system, and not the tool. E5 says: "A stateless product built by a team that keeps records it relies on has `A1` binding the team's records, not the product." The organisation is a system: "it holds state in its records, and is multi-agent where work passes between actors". So axioms "bind how the work is done, separately from what is built" (E5). A change to the tool answers to the tool's systems. The tool is stateless and has no model in the loop, so only the floor axioms bind it (A3, A4, A8, A9, A14 per the A0 matrix). The organisation's axioms "govern how the change is made and recorded, and are not one of the systems the change alters" (E5). GUESS: the team is also multi-agent (T3), so A5, A6, A7, A10 and A13 bind it too.

### design-rulings.R5
The axioms require your feature not to deepen the tangle. They encourage the split but do not require it, and if you do not split, the gap must be recorded. A0 says "new work never repeats a gap the axiom names, and work that touches a gap closes as much of it as the touch allows". The tangle is an A3 Law of One gap. A0 also says "code that merely sits beside it, in the same file or module, is not touched". So whether the split is required depends on whether the feature modifies the tangled code. The corpus does not settle that from this description: NOT SETTLED. Beyond scope, "improvement is encouraged, never mandated", and you are "expected to weigh doing it, not merely permitted to" (A0). A3 "Composable by Default" endorses exactly this ("within the unit's own duty, fix it, fracture it, re-cut its seams ... as a change of its own, answering to every consumer whose interface it alters"). K's interface is unversioned, so the split alters all three consumers directly and answers to their axioms. If you do not split, record the gap with its evidence and a revival trigger (RU3), because "Either way the gap is recorded" (A0).

### design-rulings.R6
All ten. E5 says: "A declared version range - *any 2.x* - is adoption in advance: a release within it alters every consumer bound by the range, whether or not the consumer's own files change." 2.4 changes the behaviour the declared interface documents, so it changes the interface itself. E6's blast radius covers that case: it reaches adjacent components "if the interface between them changes". So publishing 2.4 answers to each of the ten consumers' axioms. That the consumers use only the declared interface does not protect them, because the interface's own contract is what changed. GUESS: a consumer that resolves through a lockfile pinned to an earlier 2.x might not be "bound by the range" until it re-resolves. The corpus does not address lockfiles: NOT SETTLED.

### OBSERVATIONS
- E5 (Boundaries) says the chaining limit "governs units in different systems". The next sentence ("owns that boundary") reads as general, but the text does not say outright whether it applies to two modules inside one containing service (R1).
- E5 says publishing a new version "alters no consumer that has not adopted it" and also that a range is "adoption in advance". These are consistent, but nothing covers lockfiles or resolved-but-pinned consumers, which decide R6 in practice.
- A0 defines scope as "the parts of the system it touches", but code beside the change "in the same file or module, is not touched". That leaves it unclear whether a structural gap in the component you are modifying is in scope (R5). Its opportunistic-improvement text is phrased for *adjacent* components, not for the touched component's own untouched internals.
- R2(2) is ambiguous about where the change is made (in A, B or C). The answer is the same either way.
