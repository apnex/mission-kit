### design-rulings.R1
Your change must take ownership of the boundary between N and T. E5 Boundaries says: "A change that alters what an undeclared neighbour reaches into owns that boundary: declaring and honouring the interface is inside its scope, not optional."
Until that happens, N and T are "one system, with the traits of both" for deciding what binds the change (E5; A0 "What brings an axiom into force"). Both modules also sit inside the service, which contains them, so the change answers to the service's axioms in any case (E5 "Contain").
The reach is itself a fault under A3 ("Air-Gap Principle": "no unit reaches into another's internals").
How the bypass ends: first evaluate T's interface against T's duty, then either move N onto the declared interface or adjust the interface to what N legitimately needs (E5 "Declared against honoured"; A3 "Bypass as Signal").
So the change must declare T's interface and leave N using it. It may not simply change the function and leave the undeclared reach in place.

### design-rulings.R2
(1) No. E5 Boundaries: "The merge chains only through what a change can reach: if A reaches into B and B into C, a change to A is one system with C only when it alters something B takes from C." A change only A uses alters nothing B takes from C, so C's axioms do not bind it. A and B are still one system because of A's undeclared reach, so B's traits count (E5: "one system, with the traits of both").
(2) Yes. The change alters something B takes from C, so the chain reaches C and the change answers to C's axioms. It also owns the undeclared boundaries it alters, so declaring and honouring those interfaces is inside its scope (E5 Boundaries).

### design-rulings.R3
Yes, the service is stateful. T0 "How traits compose": a system "has every trait any part it contains has: a service with one stateful module is stateful". E5 says the same. The module that writes records and acts on them meets T1's test ("write something it will later read back, and would anything act differently if that record were wrong").
Yes, A1 (applies-to: stateful) binds your change. A0 says a change answers to "the system it modifies, every system containing it". E5 adds that "a change to any of them answers to the containing system, which has the traits of every part it contains."
E5 "Why precision matters" names the escape this blocks: a stateful system "escapes its own axioms by being described as stateless modules".

### design-rulings.R4
Yes, A1 binds the organisation's records. It does not bind the tool. E5: "The organisation doing the work is a system... it holds state in its records". E5 also says: "A stateless product built by a team that keeps records it relies on has `A1` binding the team's records, not the product."
The team writes records, reads them back and relies on them, so it meets T1's test. The tool does not meet that test, and no other trait of A1 (it has only `stateful`) applies to the tool.
E5 asks the two questions separately: the organisation's axioms "govern how the change is made and recorded, and are not one of the systems the change alters." So A1 governs how the team keeps its work records, not the design of the CLI tool.

### design-rulings.R5
The feature itself must not move K further from A3's limit. It may not add to the tangle, and A3 says a change "removes what it touches" (A0: "new work never repeats a gap the axiom names, and work that touches a gap closes as much of it as the touch allows").
The full split is encouraged, and you are expected to weigh it, not merely permitted to. A3 "Composable by Default": "within the unit's own duty, fix it, fracture it, re-cut its seams and recompose it so it makes better sense for every consumer downstream". A0: an agent that sees such an improvement "is expected to weigh doing it".
If you do it, make it "as a change of its own, answering to every consumer whose interface it alters" (A3; A0). K's interface is not versioned, so there is no adoption step: all three consumers are altered, and the split answers to each consumer's axioms (E5; E6 blast-radius row).
If you do not do it, record the gap with its evidence and a revival trigger (RU3). A0: "Either way the gap is recorded".
NOT SETTLED: whether the split counts as inside the feature's scope (K is touched) or beyond it (the split alters an interface that the feature did not need to change). GUESS: it is beyond scope, so it is encouraged rather than mandated.

### design-rulings.R6
All ten. E5: "A declared version range - *any 2.x* - is adoption in advance: a release within it alters every consumer bound by the range, whether or not the consumer's own files change."
2.4 changes the behaviour that the declared interface documents, so the contract each consumer relies on is altered. A0: a change answers to "any system whose contract with it the change alters".
Using only the declared interface does not shield the consumers here. That protects them only when the contract stays unchanged ("a contract the change leaves as it was", A0).
So publishing 2.4 answers to all ten consumers' axioms, and to L's own.

### OBSERVATIONS
- R5: A0 says improvement "beyond the scope" is encouraged and "inside the scope" a touched gap must be closed "as much ... as the touch allows". The corpus does not say clearly which applies when the tangle is inside the touched component K but closing it would alter K's interface for its consumers. A0's "adjacent" wording covers neighbours, not the touched component itself.
- R2(1): E5 limits the C-chain, but it does not say outright whether a change to A that alters nothing A takes from B still answers to B's axioms. The general "one system, with the traits of both" rule suggests it does, so I read it that way.
- A1's Rationale talks about "multi-actor system" hazards, but its applies-to is only [stateful]. Being multi-agent alone does not bring A1 into force.
