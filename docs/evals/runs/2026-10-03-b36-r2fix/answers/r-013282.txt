### design-rulings.R1
N reaches into T with no declared boundary, so for deciding what binds your change, N and T are "one system, with the traits of both" (entities/E5-system.md, Boundaries), and that undeclared dependency is itself an A3 fault (axioms/README.md, "What brings an axiom into force"). Your change alters something N reaches into, so it "owns that boundary: declaring and honouring the interface is inside its scope, not optional" (E5, Boundaries, last sentence). Also, A0 says a change touches "any consumer whose contract it alters", and work that touches a gap "closes as much of it as the touch allows" (axioms/README.md, "Standing commitment"). So the change must declare an interface on T and end the bypass in one of two ways, after evaluating that interface against T's duty: move N onto it, or adjust the interface to what N legitimately needs (E5, "Declared against honoured"; A3 Mechanics, "Bypass as Signal"). Until that is done, your change answers to the axioms of both T and N, and also to those of the service that contains them both (A0: "every system containing it").

### design-rulings.R2
(1) No. E5 says "The merge chains only through what a change can reach: if A reaches into B and B into C, a change to A is one system with C only when it alters something B takes from C" (entities/E5-system.md, Boundaries). A change used only by A alters nothing B takes from C, so C's axioms do not bind it. (A's undeclared reach into B still merges A and B for this change, but the question did not ask about that.)
(2) Yes. The change now alters something B takes from C, so by the same sentence it is one system with C and C's axioms bind it ("the axioms either unit would bring all bind", axioms/README.md). By E5's last sentence it also owns the undeclared boundaries it alters, so declaring and honouring those interfaces is inside its scope.

### design-rulings.R3
Yes, the service is stateful. One module writes records that it reads back and acts on, which passes the T1 test (traits/T1-stateful.md, Test), and "A system has every trait any part it contains has" (E5 Contain; traits/README.md, "How traits compose"). A1 is tagged `stateful` (axioms/A1-sovereign-state-transparency.md frontmatter), so it is in force for the service. Yes, A1 binds your change: "a change answers to every system it alters ... the system it modifies, every system containing it" (axioms/README.md), and the service contains the stateless module you change. E5 rules out the opposite reading: otherwise "a stateful system escapes its own axioms by being described as stateless modules" (E5, Why precision matters). What A1 asks of this particular change is limited by the change's scope: it must not move the service away from A1's limit, and it must move toward it as far as its touch allows (axioms/README.md, "Standing commitment").

### design-rulings.R4
Yes, A1 binds the organisation (the team, its records and its work), not the tool. E5 says: "A stateless product built by a team that keeps records it relies on has `A1` binding the team's records, not the product" (entities/E5-system.md). The team is a system that "holds state in its records". Because work passes between its actors, it is also multi-agent, so A5, A6, A7, A10 and A13 bind how the team does its work too (E5; traits/T3-multi-agent.md). The tool is stateless, has no model in the loop, and has no actors inside it, so on the stated facts it has no traits and only the floor binds it: A3, A4, A8, A9 and A14 (axioms/README.md matrix; E5: "A one-shot script with no traits is a system, bound by the axioms every system carries"). E5 keeps the two questions apart: a change to the tool answers to the tool's systems, while "the organisation's axioms govern how the change is made and recorded".

### design-rulings.R5
A3 encourages this kind of improvement: "within the unit's own duty, fix it, fracture it, re-cut its seams and recompose it so it makes better sense for every consumer downstream - as a change of its own, answering to every consumer whose interface it alters" (axioms/A3-sovereign-composition.md, "Composable by Default"). A dual-purpose module is an A3 gap. Your feature modifies K, so it must not add to the tangle, and wherever it touches the tangled code it must close as much of the gap as that touch allows (A3 Mandate; axioms/README.md: "new work never repeats a gap ... work that touches a gap closes as much of it as the touch allows"). The interface split itself alters three consumers' contracts, which is beyond what the feature was undertaken to do. A0 treats that as encouraged rather than mandated: you are "expected to weigh doing it", and if you do it, you do it as a separate change. K's interface is not versioned, so that separate change alters, and answers to the axioms of, all three consumers (axioms/README.md; E5 versioned-contract discriminator). If you do not do the split, you must record the gap with its evidence and a revival trigger (RU3), because "Either way the gap is recorded" and passing it silently is forbidden. NOT SETTLED: whether the split becomes mandatory depends on whether your feature actually modifies the tangled code, and the question does not say.

### design-rulings.R6
All ten. E5 says: "A declared version range - *any 2.x* - is adoption in advance: a release within it alters every consumer bound by the range, whether or not the consumer's own files change" (entities/E5-system.md, versioned-contract discriminator). It does not matter that the consumers use only L's declared interface. The release changes the behaviour that interface documents, which alters their contract, and A0 says a change answers to "any system whose contract with it the change alters" (axioms/README.md). So publishing 2.4 answers to the axioms of every one of the ten consumers. NOT SETTLED: the corpus does not say whether a lockfile that pins a resolved version changes this. GUESS: a lockfile pin would count as not having adopted 2.4 until the lock is updated.

### OBSERVATIONS
- E5's chaining sentence (Boundaries) speaks only of whether a change to A is one system with C. It leaves implicit whether an A-only change is still one system with B, though E5's general rule (an undeclared dependency means one system) implies that it is.
- R2(2) is phrased ambiguously: the change could be made in A, B or C. If it modifies C directly, C's axioms bind simply because the change modifies C, without any chaining. Either way the answer is yes.
- A0's opportunistic-improvement text (tangent discipline, "expected to weigh") is framed around *adjacent* components. R5 involves improving the very component the change touches, beyond the feature's goal. The corpus covers this through A3 "Composable by Default" and the scope rule, but the boundary between "touched" and "beyond scope" inside a single component is not drawn precisely, apart from the line that "code that merely sits beside it, in the same file or module, is not touched".
- E5 treats any declared range as adoption in advance. It does not mention lockfiles, and it does not say whether changing documented behaviour within a minor range is itself a fault (GUESS: A3 "Semantic Bit-Masking" would make it one).
