### system-boundary.S1
Only the launcher's axioms, and the launcher has no traits, so it takes only the floor: A3, A4, A8, A9, A14, the `any-system` row in axioms/README.md ("Applicability matrix"). I checked this against each axiom's `applies-to` frontmatter. It has no trait: it holds no state (T1), one watched operator is not multi-agent (T3) and not autonomous (T4: "a human see it before the system acted"), "a script run once" is not declarative (traits/T2-declarative.md, Boundaries), and it has no model in the loop (T5). The launcher and service compose through a declared contract (entities/E5-system.md, "Compose ... A launcher that hands sessions to a service through a declared interface composes with it"). axioms/README.md says: "A system it only composes with, through a contract the change leaves as it was, is not altered, and its axioms do not bind." So the service's axioms (A1, A5, A6, A7, A10, A13) do not apply. Separately, the organisation's own axioms govern how the change is made and recorded, but the organisation "is not one of the systems the change alters" (E5, "The organisation doing the work is a system").

### system-boundary.S2
Both systems: the change answers to "any system whose contract with it the change alters" (axioms/README.md, "What brings an axiom into force"). The launcher brings the floor (A3, A4, A8, A9, A14). The service is stateful (A1), multi-agent (A5, A6, A7, A10, A13) and autonomous (A7, A10, A13), and it is not declarative and has no model. The union is A1, A3, A4, A5, A6, A7, A8, A9, A10, A13, A14, and A2, A11 and A12 do not bind. They stay two composed systems, so this is not a merge. The change binds both because it alters the contract between them. NOT SETTLED: whether the interface is versioned. If it is, E5 says the service is altered only when it adopts the new version ("A versioned contract changes only for the systems that adopt the new version"), and that adoption is the service's own change. GUESS: the question means an unversioned interface, so the full union applies to this change.

### system-boundary.S3
The service's full set: A1, A3, A4, A5, A6, A7, A8, A9, A10, A13, A14. A change answers to "the system it modifies, every system containing it" (axioms/README.md). E5 says "A module inside a service is a system, and the service contains it, whether or not the module's interfaces are declared". The module's own statelessness does not help. E5 "Why precision matters" names that escape route: "a stateful system escapes its own axioms by being described as stateless modules". The module on its own carries only the floor axioms (A3, A4, A8, A9, A14), which are already in the service's set. Sibling modules are altered only if the change alters an interface they consume (entities/E6-component.md, Blast radius row).

### system-boundary.S4
Only the library's axioms, which are the floor: A3, A4, A8, A9, A14 ("a plain library takes `any-system`", axioms/README.md). E5 says "Publishing a new version of an interface alters no consumer that has not adopted it; each adoption is a change to that consumer, and answers to that consumer's axioms; the component is not altered by being adopted". Here even the interface is unchanged, so no consumer's contract is altered. E5 "Why precision matters" rejects the opposite reading: "a small shared library would carry the axioms of every system that uses it". Caveat from E5: "A declared version range ... is adoption in advance: a release within it alters every consumer bound by the range". The question says each system adopts as its own separate change, so I take it that no ranges are declared. If any consumer used a range, or reached past the interface into internals, that consumer's axioms would bind too (E5, "Declared against honoured").

### system-boundary.S5
The launcher and service are treated as one system with the traits of both, so all of A1, A3, A4, A5, A6, A7, A8, A9, A10, A13, A14 bind. The rule: "Where one unit depends on another and nothing declares the boundary between them ... they are one system, with the traits of both" (E5, Boundaries; same in axioms/README.md). Also wrong: "The undeclared dependency is itself a fault against A3" (E5), against A3's Air-Gap Principle ("units interact only through declared adapters and contracts"). If the log lines are among the output the service parses, E5 says the change "owns that boundary: declaring and honouring the interface is inside its scope, not optional". NOT SETTLED: whether the log lines are part of what the service parses. GUESS: treat them as parsed until shown otherwise, because nothing shows the change is contained. Practically, the change may also break the service's parser silently, which is the A3 fault "Logic Leakage".

### system-boundary.S6
It is defined in entities/E5-system.md: "A system is a unit of engineering with a boundary: what is inside it, and the contracts through which anything outside reaches it." A boundary separates two systems "only where it is declared and honoured"; otherwise they are "one system for deciding what a change answers to". Systems relate in exactly two ways, contain and compose. "Traits describe a system, and axioms bind it." A system is not a repository, deployment unit or process, and it is not defined by size ("A one-shot script with no traits is a system"). entities/E6-component.md adds that a component is "a system seen as a part of a larger system that contains it".

### OBSERVATIONS
- The question does not say whether the launcher is declarative. I inferred it is not from T2 ("a script run once" is not declarative) and from E5's "one-shot script with no traits".
- E5's version-range rule ("a release within it alters every consumer bound by the range, whether or not the consumer's own files change") seems to conflict with E5's own warning that a small shared library should not carry every consumer's axioms. Under ranges, an internals-only library release would bind every ranged consumer's axioms even when behaviour is unchanged.
- E5 uses "answers to" for the product's systems and "govern how the change is made" for the organisation, so there are two separate binding questions. A reader could easily merge them or leave the second one out.
- In S5, the merge into one system and the "owns that boundary" duty have different triggers. The merge applies to any undeclared dependency. The duty applies only when the change alters what the neighbour reaches into. The scenario does not say which output the service parses.
- INDEX.md's links resolve against a remote URL as a fallback. I used only the local corpus.
- I checked the A0 applicability matrix against each axiom's frontmatter `applies-to` and they match.
