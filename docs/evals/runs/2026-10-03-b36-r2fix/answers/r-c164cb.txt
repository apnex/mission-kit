### design-rulings.R1
No interface is declared between N and T, so for deciding what binds your change they are "one system, with the traits of both" (entities/E5-system.md, Boundaries; axioms/README.md, "What brings an axiom into force"). That means your change answers to every axiom either N or T brings into force. The undeclared reach is "itself a fault against A3" (E5; A3 Mechanics, "Air-Gap Principle"). Your change alters a function N reaches into, so E5 says it "owns that boundary: declaring and honouring the interface is inside its scope, not optional." In practice the change must declare an interface for what N uses and get N to honour it. E5 ("Declared against honoured") and A3 ("Bypass as Signal") say how: first judge the interface against T's duty, then either move N onto it or adjust the interface to "what the consumer legitimately needs". Declaring the interface while leaving the bypass in place "separates nothing" (E5).

### design-rulings.R2
(1) No. E5 Boundaries: "The merge chains only through what a change can reach: if A reaches into B and B into C, a change to A is one system with C only when it alters something B takes from C." A change only A uses alters nothing B takes from C, so C's axioms do not bind it. The question does not ask about B: A's undeclared reach into B still makes A and B one system under E5, and that reach is still an A3 fault.
(2) Yes. The change alters something B takes from C, which is exactly the condition E5 names, so the merge chains through to C and C's axioms bind. The change also alters what undeclared neighbours reach into, so declaring and honouring those interfaces (A-B and B-C) is "inside its scope, not optional" (E5).

### design-rulings.R3
Yes, the service is stateful. The module that writes records and later reads them back and acts on them passes the T1 test (traits/T1-stateful.md, Test). E5 then says "A system has every trait any part it contains has", and T0 says "a service with one stateful module is stateful" (traits/README.md, "How traits compose"). A1 is tagged `applies-to: [stateful]`, so it is in force for the service. A0 says "a change answers to every system it alters. That is the system it modifies, every system containing it...". Your change alters the stateless module and so alters the service that contains it, which means A1 binds the change. E5 adds that a stateful system must not "escape its own axioms by being described as stateless modules". What A1 asks is set by the change's scope (A0): do not move the service away from A1's limit, and move it toward the limit as far as the change's own scope allows.

### design-rulings.R4
Yes, A1 binds, but it binds the team's records, not the tool. E5 states it almost word for word: "A stateless product built by a team that keeps records it relies on has A1 binding the team's records, not the product." The organisation doing the work is a system, and it "holds state in its records" (E5). Records the team writes, reads back and relies on pass the T1 test. The tool writes nothing it later reads back, so T1 does not hold for it and A1 does not bind it. E5 also says the two questions are asked separately: A1 governs how changes are made and recorded, and the organisation is "not one of the systems the change alters".

### design-rulings.R5
Splitting K is encouraged, and you are expected to weigh it, but it is not mandated. A0 says "code that merely sits beside it, in the same file or module, is not touched", so the tangle is outside the feature's scope unless the feature modifies the tangled code. Beyond the scope, "improvement is encouraged, never mandated", and an agent who sees how to bring a component nearer its limit "within that component's duty, is expected to weigh doing it" (A0). A3 "Composable by Default" encourages exactly this ("fix it, fracture it, re-cut its seams and recompose it so it makes better sense for every consumer downstream"). If you do it, make it "a change of its own". K's interface is not versioned, so the split alters all three consumers and answers to each consumer's axioms (A3; A0; E5). Whatever you decide, the feature itself must not add to the tangle ("new work never repeats a gap the axiom names", A0), and the gap must be recorded: if you do not close it, record it with its evidence and a revival trigger (A0, RU3). NOT SETTLED: if the feature does modify the tangled code, the scope rule would require closing "as much of it as the touch allows"; the question does not say which case applies.

### design-rulings.R6
All ten. E5 says "A declared version range - any 2.x - is adoption in advance: a release within it alters every consumer bound by the range, whether or not the consumer's own files change." Release 2.4 changes the behaviour the declared interface documents, so it alters each consumer's contract. So publishing 2.4 is a change that answers to each of the ten consumers' axioms (A0: "any system whose contract with it the change alters"). The fact that they use only the declared interface does not protect them, because the declared interface itself changed. NOT SETTLED: whether a behaviour change inside 2.x should have been a 3.0 under semver; the corpus does not cover versioning policy.

### OBSERVATIONS
- E5's chaining sentence ("a change to A is one system with C only when it alters something B takes from C") is hard to read in R2(2). A change that alters data B takes from C would usually be made in B or C rather than in A, and E5 does not say which system the change is "in" for this case.
- E5 merges A and B for any undeclared dependency, but its chaining sentence limits only C. It is not stated whether a change in A that alters nothing B exposes still answers to B's axioms. A literal reading of "one system, with the traits of both" says yes.
- A0's scope rule ("code that merely sits beside it, in the same file or module, is not touched") sits awkwardly with its opportunistic-improvement text, which talks about "adjacent components". A gap in the same component, in code the change does not modify, is neither inside the scope nor adjacent in E6's sense, and R5 depends on which reading applies.
