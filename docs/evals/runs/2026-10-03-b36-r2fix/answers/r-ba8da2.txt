### system-boundary.S1
A3, A4, A8, A9 and A14: the floor (`any-system`) axioms only (axioms/README.md matrix: "`any-system` | A3 ... A4 ... A8 ... A9 ... A14").
The launcher has no traits: no persistent state (T1), one operator using a tool rather than independent actors (T3), a human watching it (T4 "Not autonomous"), no model (T5), and no declared spec (T2), and E5 says "A one-shot script with no traits is a system, bound by the axioms every system carries".
The service is not altered: A0 says "A system it only composes with, through a contract the change leaves as it was, is not altered, and its axioms do not bind", and E5 gives this exact case: "A launcher that hands sessions to a service through a declared interface composes with it".
The boundary is declared and honoured, because the declared interface is the only thing that crosses (E5: separated "only where it is declared and honoured").
Nothing contains the launcher (stated in the setup), so no containing system is added (A0: "every system containing it").
The organisation's own axioms govern how the change is made and recorded, but E5 says they "are not one of the systems the change alters".

### system-boundary.S2
A1, A3, A4, A5, A6, A7, A8, A9, A10, A13 and A14, but not A2, A11 or A12.
A0: "a change answers to every system it alters. That is the system it modifies, every system containing it, and any system whose contract with it the change alters". Changing the declared session interface alters the launcher and the service, so the change answers to both.
The launcher contributes the floor (A3 A4 A8 A9 A14).
The service is stateful (T1 -> A1), multi-agent (T3 -> A5 A6 A7 A10 A13) and autonomous (T4 -> A7 A10 A13), and traits bind by union (T0 "Traits bind by union").
It is not declarative and has no model in the loop, so A2 (declarative) and A11/A12 (llm-in-the-loop) do not bind.
Caveat: if the interface were versioned, E5 says a new version alters the service only when the service adopts it ("each adoption is a change to that consumer"). The question does not say the interface is versioned, so I read it as an unversioned contract change.

### system-boundary.S3
The service's full set: A1, A3, A4, A5, A6, A7, A8, A9, A10, A13 and A14 (not A2, A11, A12).
E5: "A module inside a service is a system, and the service contains it, whether or not the module's interfaces are declared", and A0 says a change answers to the system it modifies "and every system containing it".
The module being stateless on its own does not reduce this. The module alone would carry only the floor, but the containing service is also altered, and it is stateful, multi-agent and autonomous (T0: "It has every trait any part it contains has").
E5 names the failure this rule prevents: "a stateful system escapes its own axioms by being described as stateless modules, each of which passes on its own".
Scope (A0) then limits how far the change must move the service toward each limit, but every one of these axioms is in force.

### system-boundary.S4
A3, A4, A8, A9 and A14: the floor only (A0: "a plain library takes `any-system`").
The library has no traits, and the ten consumers are not altered because the interface and its behaviour are unchanged (A0: a system it "only composes with, through a contract the change leaves as it was, is not altered, and its axioms do not bind").
Even a new version alters no consumer until it adopts it. E5: "Publishing a new version of an interface alters no consumer that has not adopted it; each adoption is a change to that consumer, and answers to that consumer's axioms; the component is not altered by being adopted".
E5 rejects the opposite reading by name: otherwise "a small shared library would carry the axioms of every system that uses it".
Two conditions would change this answer. A consumer that declared a version range ("any 2.x") is altered by a release within that range (E5: "adoption in advance"). A consumer that reaches past the interface stays one system with the library (E5 "Declared against honoured").
The question rules out the first ("each adopts a new version as its own separate change") and does not mention the second.

### system-boundary.S5
A1, A3, A4, A5, A6, A7, A8, A9, A10, A13 and A14 (not A2, A11, A12): the union of both systems.
With no declared interface and the service depending on the launcher's output, the two are "one system, with the traits of both" (E5 Boundaries). A0 says the same: "the axioms either unit would bring all bind".
Something else is wrong. A0 and E5 say "the undeclared dependency is itself a fault under A3", and E5 calls the parsed output "a contract in fact, not a declared boundary - and a change to it reaches across".
E5 also makes fixing it part of this change: "A change that alters what an undeclared neighbour reaches into owns that boundary: declaring and honouring the interface is inside its scope, not optional".
E5 gives the way out: declare the boundary, then either move the service onto the interface or adjust the interface to what the service legitimately needs (A3).
NOT SETTLED: the corpus does not say whether the merge applies when the service parses other output but not the log lines. GUESS: it applies, because E5 merges wherever "nothing shows that a change to one leaves the other unchanged", and with nothing declared, nothing shows that.

### system-boundary.S6
Defined in entities/E5-system.md: "A system is a unit of engineering with a boundary: what is inside it, and the contracts through which anything outside reaches it."
The boundary separates two units "only where it is declared and honoured - written down, and the only way the neighbour reaches it". Otherwise the two are "one system for deciding what a change answers to".
Systems relate in exactly two ways, contain and compose. Traits describe a system and axioms bind it.
E5 Boundaries says a system is not a repository, deployment unit or process by definition, and is not defined by size or by traits.
A0 defers to it ("System, contain and compose are defined in E5"), and E6 defines a component as "a system seen as a part of a larger system that contains it".

### OBSERVATIONS
- The launcher's lack of the multi-agent trait is my inference. The setup says "one operator runs it and watches it" but does not say "not multi-agent". T3 counts "a human reviewing an agent's output" as multi-agent, while "one actor using several tools" is not. I read a script run by one person as a tool, not an independent actor.
- S2 depends on whether the session interface is versioned (E5's adoption rule), and the question does not say.
- E5 treats the organisation as a system too. I left its axioms out of every answer, following E5's statement that they govern how a change is made, not which systems it alters. A reader who folded them in would get different lists.
