PROBE sc0.Q3

Question:
In what order must a consumer validate a resource, and why?

Key:
Structural validation by JSON Schema first, then the semantic validator. The semantic validator checks invariants JSON Schema cannot express, and assumes input that has already passed the structural check.

Rubric:
2 for the order with either reason - two stages because some invariants are beyond JSON Schema, or semantic checks assume structurally valid input. 1 for the order alone. 0 otherwise.

--- answer a-96498c73 ---
Structural validation (JSON Schema) comes first, then semantic validation (the kind's semantic validator named in `catalog.json`).
schemas/README.md (Validation): "A consumer must run structural validation before semantic validation, because each semantic validator assumes the shape the schema guarantees - it reads fields without first checking they exist."
The semantic validators check invariants that JSON Schema Draft 2020-12 cannot express, such as unique option IDs and cardinality bounds for Question, and duplicate or contradictory scope for ContextFrame.
The README also says consumers can preload every schema in `catalog.json` so absolute URN references resolve.

--- answer a-4bae6a5f ---
Structural (JSON Schema) validation first, then semantic validation.
schemas/README.md "Validation": "A consumer must run structural validation before semantic validation, because each semantic validator assumes the shape the schema guarantees - it reads fields without first checking they exist."
JSON Schema validates structure; the semantic validators (e.g. `question.validator.mjs`, `context-frame.validator.mjs`, mapped in `catalog.json`) check invariants Draft 2020-12 cannot express, such as unique option IDs or min <= max selections.
The README also notes consumers can preload every schema in `catalog.json` to resolve absolute URN references, and that `default` annotations do not mutate instances, so nothing should rely on defaults being filled in.

--- answer a-25dfd21a ---
Structural validation (JSON Schema) comes first, then semantic validation (the per-kind `*.validator.mjs`).
SC0 "Validation" gives the reason: "each semantic validator assumes the shape the schema guarantees - it reads fields without first checking they exist."
