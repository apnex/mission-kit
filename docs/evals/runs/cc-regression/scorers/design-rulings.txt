PROBE design-rulings.R1

Question:
In a long-running service operated by several independent agents who hand work to each other, module N calls internal functions of module T; no interface is declared between them. Your change to T alters a function N calls. What must your change do about N's undeclared reach?

Key:
Declare an interface for what N reaches and move N onto it - inside the change's scope, because the change alters what N reaches; it is not merely recorded and not optional. Had the change not touched what N reaches, the gap would be recorded.

Rubric:
2 for declaring and honouring the interface as in scope, with the reason that the change alters what N reaches. 1 for declaring it as optional or recommended, or recording it only. 0 otherwise.

--- answer a-65e365c8 ---
N and T have no declared boundary, so for deciding what binds your change they are one system with the traits of both (entities/E5-system.md, Boundaries: "for deciding what binds a change they are one system, with the traits of both"). Your change alters what N reaches into, so it owns that boundary. E5 says: "A change that alters what an undeclared neighbour reaches into owns that boundary: declaring and honouring the interface is inside its scope, not optional."
So the change must declare an interface on T and get N onto it. Declaring the interface and leaving the bypass in place "separates nothing" (E5, Declared against honoured).
The undeclared reach is an A3 fault (axioms/A3-sovereign-composition.md, Air-Gap Principle). Under A3 "Bypass as Signal", you first evaluate the interface against T's duty. Then either N moves onto the interface, or the interface is adjusted to what N legitimately needs (E5; A3).
Your change also answers to N, as a consumer whose contract it alters (axioms/README.md: a change touches "any consumer whose contract it alters"). Both modules are inside the service anyway, so the change answers to the service's axioms too.

Both modules sit inside one service, so the change answers to that service's axioms, and the service has every trait of every module in it (E5 *Contain*; A0 "every system containing it").

Does it now answer to C's axioms?

Key:
(1) No: the merge chains only through what the change can reach, and this change reaches nothing of C. (2) Yes, or at least it meets the condition under which the merge chains - the change reaches C through B.

Rubric:
2 for both cases with the reach reason (for case 2, 'it meets the chaining condition' counts). 1 for one case. 0 for 'always chains' or 'never chains'.

--- answer a-4bccd4b7 ---

A change that only A uses alters nothing B takes from C, so C's axioms do not bind it. (A and B are still one system for this change, because of A's undeclared reach into B.)
(2) Yes. The change alters something B takes from C, which is exactly the condition E5 states. So A's change is one system with C and answers to C's axioms. The undeclared reaches are A3 faults, and the change owns the boundaries it alters (E5: "declaring and honouring the interface is inside its scope, not optional").

Question:
In a long-running service operated by several independent agents who hand work to each other, one module writes records it later reads back and acts on; every other module is stateless. You change a stateless module. Is the service stateful, and does A1 bind your change?

Key:
Yes: a system has a trait if it or any part it contains passes the trait's test, so the service is stateful; the change modifies the service, so A1 binds it.

Rubric:
2 for both, with the contained-part rule (citing that a stateful system cannot escape by being described as stateless modules counts). 1 for the right answer without the rule. 0 otherwise.

--- answer a-0b63bef9 ---
Yes, the service is stateful, and A1 binds your change. The module that writes records and later reads them back to act on them passes T1's test ("write something it will later read back, and would anything act differently if that record were wrong?"). E5 says "A system has every trait any part it contains has", and T0 says "a service with one stateful module is stateful". A change answers to "every system containing it" (A0), and E5 adds: "units inside one system need no chaining, because a change to any of them answers to the containing system". So A1 (applies-to: stateful) binds the change even though the module you touch is stateless. In practice that means the change must not move the service away from A1's limit, and must move it toward that limit as far as the change's own scope allows (A0). E5 "Why precision matters" names the alternative reading as the error: "a stateful system escapes its own axioms by being described as stateless modules".

Question:
While adding a small feature to component K, you notice K's internals tangle two concerns, and splitting them would give K's three consumers a cleaner interface. K's interface is not versioned. The split is within K's own duty. What do the axioms ask?

Key:
The new feature arrives as its own unit, composed with K, not bolted onto K. The split is encouraged as opportunistic improvement within K's duty - not mandated - including re-cutting K's seams and recomposing for its consumers; it is made as a change of its own, and since it changes K's interface, it answers to each consumer it alters.

Rubric:
2 for the split encouraged not mandated, and the consumers' axioms binding the interface change. 1 for one of the two. 0 for 'never modify K' or 'the split is required'. Mentioning the feature arriving as its own unit is credited, not required.

--- answer a-5eb463a4 ---
You must build the small feature itself so that it does not repeat or worsen the tangle. Where the feature already alters the tangled code to do its own work, it must reduce the tangle as far as that touch allows (A0; A3 Mandate: "a change short of it adds none of them, and removes what it touches"). The full split goes beyond what the feature needs, so it is "the encouraged improvement ... not a requirement" (A0: "restructuring beyond that, even inside the same component"). A3 "Composable by Default" encourages the split within K's duty ("fix it, fracture it, re-cut its seams"). A0 says an agent who sees such an improvement "is expected to weigh doing it, not merely permitted to". If you do the split, make it a separate change of its own. K's interface is unversioned, so that change alters all three consumers at once and answers to all of their axioms (E5; A0). Adding versioning while you are there is encouraged, not required; if you do not add it, record the gap (E5). If you do not do the split, record the gap with its evidence and a revival trigger (A0; RU3), because passing it silently is what A0 forbids.

Because K's interface is unversioned, the split would change all three consumers at once and answer to all three of their axioms (E5: "changing an unversioned interface alters every consumer at once"). Adding versioning at the same time is encouraged.
If you do not split, record the gap with its evidence and a revival trigger (A0; RU3): "Either way the gap is recorded. Passing it silently is what the axiom forbids."

PROBE design-rulings.R6

Question:
Ten consumers depend on library L with a floating range, 'any 2.x', and use only L's declared interface. L publishes 2.4, which changes the behaviour that interface documents. Which consumers does publishing 2.4 alter?

Key:
All ten: a declared range is adoption in advance, so a release within it alters every consumer bound by the range, and answers to their axioms.

Rubric:
2 for all ten with the adoption-in-advance reason. 1 for all ten without it. 0 for none.

--- answer a-e70407f9 ---
Publishing 2.4 alters all ten consumers. E5 says "A declared version range - *any 2.x* - is adoption in advance: a release within it alters every consumer bound by the range, whether or not the consumer's own files change." All ten use the floating 2.x range, and 2.4 falls inside it. Using only L's declared interface does not protect them, because 2.4 changes the behaviour that interface documents. The usual rule, that a published version alters no consumer until it adopts it, does not help here: the range is adoption already given. So publishing 2.4 answers to all ten consumers' axioms (A0: "any system whose contract with it the change alters"). NOT SETTLED: whether something like a lockfile, which delays resolution until the next build, changes when the alteration happens. The corpus does not address this. It also does not address whether 2.4 should have been a major version under semantic versioning.
