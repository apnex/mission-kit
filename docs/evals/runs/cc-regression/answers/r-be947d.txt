### system-boundary.S1
Only the launcher's axioms, which are the floor: A3, A4, A8, A9 and A14 (axioms/README.md applicability matrix, row `any-system`).
The launcher has no traits (T1/T3/T4/T5 tests all fail, and it is watched by its operator, so it is not autonomous per T4), and E5 says "A one-shot script with no traits is a system, bound by the axioms every system carries".
The launcher composes with the service through a declared contract (E5: "A launcher that hands sessions to a service through a declared interface composes with it").
A0 states "A system it only composes with, through a contract the change leaves as it was, is not altered, and its axioms do not bind", so the service's axioms (A1, A5, A6, A7, A10, A13) do not apply.
Separately, E5 says the organisation doing the work is itself a system whose axioms govern "how the change is made and recorded", but that is not one of the systems the change alters.

### system-boundary.S2
The launcher's axioms plus the service's: A1, A3, A4, A5, A6, A7, A8, A9, A10, A13, A14. Not A2, A11 or A12.
A0: a change answers to "any system whose contract with it the change alters", and E5: "changing an unversioned interface alters every consumer at once, so the change answers to all of them immediately."
The service is stateful (T1 -> A1), multi-agent (T3 -> A5, A6, A7, A10, A13) and autonomous (T4 -> A7, A10, A13), plus the floor; it is not declarative (no A2) and has no model (no A11, A12, and A5 arrives via multi-agent anyway).
E5 also says adding versioning while you change the interface "is encouraged, not required; if it is not done, the gap is recorded" (A3's Semantic Bit-Masking names versioned contracts as the limit).

### system-boundary.S3
The service's full set: A1, A3, A4, A5, A6, A7, A8, A9, A10, A13, A14.
E5: "A module inside a service is a system, and the service contains it, whether or not the module's interfaces are declared", and A0: a change answers to "the system it modifies, every system containing it".
That the module holds no state on its own does not exempt it; E5 says the opposite reading lets "a stateful system escape its own axioms by being described as stateless modules", and T0 says "a stateful system cannot escape its axioms by being described as stateless parts".
E5 adds that "units inside one system need no chaining, because a change to any of them answers to the containing system".

### system-boundary.S4
Only the library's own axioms, the floor: A3, A4, A8, A9, A14.
The library has no traits, and A0 says "a plain library takes `any-system`".
The ten consumers compose with it through a declared, versioned interface that the change leaves unchanged, so they are not altered (A0); E5: "Publishing a new version of an interface alters no consumer that has not adopted it; each adoption is a change to that consumer, and answers to that consumer's axioms; the component is not altered by being adopted."
E5's "Why precision matters" names this exact case as the error to avoid: otherwise "a small shared library would carry the axioms of every system that uses it".
Caveat from the text: E5 says a declared version range ("any 2.x") "is adoption in advance" and a release within it alters every consumer bound by the range; the question says each consumer adopts separately, so I read no ranges as present.

### system-boundary.S5
The launcher and service are one system for binding, so the change answers to the full union: A1, A3, A4, A5, A6, A7, A8, A9, A10, A13, A14.
E5: "Where one unit depends on another and nothing declares the boundary between them ... they are one system, with the traits of both"; A0 says the same and that "the axioms either unit would bring all bind".
Also wrong: "The undeclared dependency is itself a fault against A3" (E5, A0), which breaks A3's Air-Gap Principle ("units interact only through declared adapters and contracts").
And your change owns that fault: E5 says "A change that alters what an undeclared neighbour reaches into owns that boundary: declaring and honouring the interface is inside its scope, not optional."
So the change must declare the interface (logs or a proper session contract) and move the service onto it. Per A3's Bypass as Signal, that also means checking the interface against the launcher's duty.

### system-boundary.S6
It is defined in entities/E5-system.md: "A system is a unit of engineering with a boundary: what is inside it, and the contracts through which anything outside reaches it."
The boundary separates it from a neighbour "only where it is declared and honoured"; otherwise the two are "one system for deciding what a change answers to".
Systems relate in exactly two ways, contain and compose; "Traits describe a system, and axioms bind it."
E5 Boundaries: a system is not a repository, deployment unit or process by definition, and not defined by size or traits. E6 adds that a component is "a system seen as a part of a larger system that contains it".

### axiom-direction.Q1
The service is stateful, so A1 binds it, and in-process private state is A1's named "Hidden State Problem" ("No functional unit possesses private, opaque, or transient truth"). A5 also binds, because the service is multi-agent.
If your feature does not touch that component (A0 scope: what the change modifies, newly depends on, or whose contract it alters), you are not required to fix it, because "Beyond the scope, improvement is encouraged, never mandated". But A0 says you are "expected to weigh" it, and "Passing it silently is what the axiom forbids".
So you either close it as a separate change, if it is adjacent (E6: it shares a declared interface with what you touch) and A14 tangent discipline supports doing so, or you record it with evidence and a revival trigger (RU3). "Either way the gap is recorded."
For your own feature, A0 says "new work never repeats a gap the axiom names": keep your feature's state where other agents can perceive it and where it survives a restart, not in process memory.
If the feature newly depends on that component, "its gaps must not be built on". If it modifies that component, it must close "as much of it as the touch allows".
NOT SETTLED: whether the service already has a shared state backplane to put that state in.

### axiom-direction.Q2
An axiom is a limit (an "asymptote") that the system is built toward. It is not a pass/fail test (axioms/README.md, "Standing commitment, not situated move").
When you change a bound system, it gives the change a direction in two parts: "No change may move the system away from the limit, and each change moves it toward the limit as far as the change's own scope allows."
A system is not wrong for being short of the limit, only for moving away from it. The CORRECTION banner in A0 records that the earlier pass/fail ("invariant") reading was replaced by the director's asymptote ruling, and A0's "conformance reading" fault explains why the pass/fail reading leaves gaps permanent.
A gate can still give a yes/no answer, because what it checks is the direction: that the change "moved the system no further from any limit in force, and repeated no gap it touched".
Axioms are conjunctive, so no axiom can be traded against another.
