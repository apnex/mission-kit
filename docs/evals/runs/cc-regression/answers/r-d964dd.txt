### component.C1
Y: X stands on Y through Y's declared interface, so Y is adjacent to what your change touches, and it is the "closer" direction (entities/E6-component.md: "the one the other stands on is the closer for compounding learning"). Y is not touched: axioms/README.md (A0) says a change "touches what it modifies, what it newly depends on, and any consumer whose contract it alters", and X already depended on Y. So fixing Y is "encouraged, never mandated", but A0 says an agent "is expected to weigh doing it". A0 allows closing an adjacent gap opportunistically when A14's tangent discipline supports it: "the payback is near... the yield is captured; and the cost does not significantly distract". A five-minute fix that would have saved twenty minutes plausibly meets that. If you do it, A0 says it is "made as a change of its own" and "answers to every system it alters"; if it changes Y's interface, Y's consumers are altered too. Whether an error message's text is part of Y's declared interface is NOT SETTLED (A3's "bit-perfect message formats" hints it might be). Z: Z is not adjacent (X does not use it, and E6 says being nearby is not adjacency), and two days of work would likely displace the goal. So per A0 it "is recorded with its evidence and a revival trigger (RU3) rather than closed", because choosing what work happens next is the director's call (R4, AR3). Either way, A0 says "the gap is recorded. Passing it silently is what the axiom forbids." Also, Z makes the containing service stateful, and your change to X answers to that service (E5: "a system has every trait any part it contains has"). So A1 binds the change in the sense that it must not move the service further from A1, for example by adding hidden state. It does not require you to fix Z.

### component.C2
It is defined in entities/E6-component.md: "A component is a system seen as a part of a larger system that contains it", with "one duty at the altitude where it appears as a part", and it "exposes and consumes interfaces". E6: "Every component is a system; component names its place in a containing system, not a different kind of thing." What tells them apart is the question being asked. Traits, axioms and "what a change answers to are questions about a system". "Duty, interfaces, neighbours and blast radius are questions about a component", which only have answers relative to the containing whole. entities/E5-system.md defines a system as "a unit of engineering with a boundary", and covers this difference under "A system against a component". A system that nothing contains "is not a component of anything" (E6). A component does not have to be registered in components/ or be shareable (E6 Boundaries).

### component.C3
No. E6 ("Boundary against directory"): "A component's directory addresses it... Its boundary is its declared interfaces". E5 agrees: "A directory... is the boundary of neither the system nor the component." What is wrong: no interface is declared, so nothing separates the two. E6: "A part whose interfaces are undeclared is still a component, but nothing separates it yet". For deciding what a change answers to, parts/thing and parts/other are "one system, with the traits of both" (E5 Boundaries). E5 also says the undeclared dependency "is itself a fault against A3", whose Air-Gap Principle says "no unit reaches into another's internals". The remedy (E5): "Declaring the boundary, and moving the dependency onto it, is what makes them two again". A3's "Bypass as Signal" adds that the crossing should prompt an evaluation of what interface the component's duty calls for, not only a correction of the consumer. Under E5, a change that alters what parts/other reaches into "owns that boundary: declaring and honouring the interface is inside its scope, not optional."

### component.C4
Your change answers to P and to every system that contains P, including the service. A0 says "a change answers to every system it alters... the system it modifies, every system containing it, and any system whose contract with it the change alters." Q is not altered. A0: "A system it only composes with, through a contract the change leaves as it was, is not altered, and its axioms do not bind". E6's blast-radius row reaches "an adjacent component only if the interface between them changes". One nuance: the service has every trait Q has (E5), so axioms brought in by Q's traits still bind your change through the containing service, though not as Q's own axioms. This all assumes Q uses only the declared interface. Under E5, if Q relies on undeclared behaviour of P, that is "a contract in fact" and Q is one system with P. Q is a candidate for opportunistic improvement, because it shares a declared interface with P and so is adjacent "in either direction" (E6; A0: "one it stands on, or one that stands on it"). But Q stands on P, not the other way round, so per E6 this is "adjacency with less payback, not none", and the A14 test (near payback, yield captured, no significant distraction) still has to be weighed. If you do not close a gap you saw in Q, record it with a revival trigger (A0, RU3).

### OBSERVATIONS
- A14's tangent discipline defines adjacency in one direction only ("infrastructure the main line will stand on"). A0 allows both directions. E6 reconciles them by saying the other direction has "less payback, not none". That is consistent, but you only see it by reading all three.
- A3 ("Semantic Bit-Masking") calls interfaces "explicit, versioned contracts", while E5 says adding versioning is "encouraged, not required". That is a mild tension, and the asymptote reading of A0 probably resolves it.
- No file says whether error-message text belongs to a declared interface. That decides whether fixing Y in C1 alters Y's consumers.
- A0 says Z-type gaps that fail the test are "recorded... rather than closed", but it does not say who owns recording a gap in a component the change neither touches nor stands on. C1 assumes the agent that saw it records it.
