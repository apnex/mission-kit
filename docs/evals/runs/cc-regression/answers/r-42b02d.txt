Trait classification used throughout (applied from traits/T1-T5 tests):
- Launcher: no traits. Not stateful (holds no state, T1), not declarative (T2: "a script run once" is not declarative), not multi-agent (one operator, T3), not autonomous (operator watches it, T4), no model (T5). So only the floor binds: A3, A4, A8, A9, A14 (axioms/README.md applicability matrix, `any-system` row; confirmed against each axiom's applies-to frontmatter).
- Service: stateful (T1), multi-agent (T3), autonomous (T4); not declarative, not llm-in-the-loop. Axioms in force = floor + A1 (stateful) + A5, A6, A7, A10, A13 (multi-agent; A7/A10/A13 also via autonomous) = A1, A3, A4, A5, A6, A7, A8, A9, A10, A13, A14. Not A2, A11, A12.

### system-boundary.S1
Only the launcher's axioms: A3, A4, A8, A9, A14. axioms/README.md: "a change answers to every system it alters ... A system it only composes with, through a contract the change leaves as it was, is not altered, and its axioms do not bind." entities/E5-system.md gives this exact case as composition: "A launcher that hands sessions to a service through a declared interface composes with it." The launcher has no traits, so only the `any-system` floor applies ("A one-shot script with no traits is a system, bound by the axioms every system carries", E5 Boundaries). The service's axioms (A1, A5, A6, A7, A10, A13) do not bind. Separately, E5 says the organisation doing the work is its own system whose axioms govern how the change is made and recorded, but it "is not one of the systems the change alters".

### system-boundary.S2
The union of launcher and service axioms: A1, A3, A4, A5, A6, A7, A8, A9, A10, A13, A14 (not A2, A11, A12). The change alters the service's contract, and A0 says a change answers to "any system whose contract with it the change alters". E5: "changing an unversioned interface alters every consumer at once, so the change answers to all of them immediately." E5 also says "Adding versioning to an interface you are changing moves it toward A3's limit and is encouraged, not required; if it is not done, the gap is recorded."

### system-boundary.S3
The service's full set: A1, A3, A4, A5, A6, A7, A8, A9, A10, A13, A14. A0: a change answers to "the system it modifies, every system containing it". E5 Contain: "A module inside a service is a system, and the service contains it, whether or not the module's interfaces are declared. A system has every trait any part it contains has." That the module holds no state on its own changes nothing. E5 "Why precision matters" names this escape as the error: "a stateful system escapes its own axioms by being described as stateless modules, each of which passes on its own." traits/README.md says the same: "a stateful system cannot escape its axioms by being described as stateless parts".

### system-boundary.S4
Only the library's own axioms: the floor, A3, A4, A8, A9, A14. The library has no traits. The versioned interface and its behaviour are unchanged, so no consumer's contract is altered and the ten dependents only compose with it (A0, E5 Compose). E5: "Publishing a new version of an interface alters no consumer that has not adopted it; each adoption is a change to that consumer, and answers to that consumer's axioms; the component is not altered by being adopted." E5 "Why precision matters" rejects the opposite reading: "a small shared library would carry the axioms of every system that uses it". One caveat from E5: "A declared version range - any 2.x - is adoption in advance". If any consumer pinned a range, a release within it would alter that consumer. The question says each consumer adopts separately, so I took it that no range applies.

### system-boundary.S5
The union of both systems' axioms: A1, A3, A4, A5, A6, A7, A8, A9, A10, A13, A14. No boundary is declared and the service depends on the launcher's log lines, so E5 Boundaries applies: "they are one system, with the traits of both". A0 says the same: "the two are one system with the traits of both, and the axioms either unit would bring all bind". Something else is wrong. "the undeclared dependency is itself a fault under A3" (A0, E5; A3 Air-Gap Principle: "units interact only through declared adapters and contracts"). Your change owns fixing it: "A change that alters what an undeclared neighbour reaches into owns that boundary: declaring and honouring the interface is inside its scope, not optional" (E5). ### system-boundary.S6
It is defined in entities/E5-system.md (entry E5): "A system is a unit of engineering with a boundary: what is inside it, and the contracts through which anything outside reaches it." The boundary separates it from a neighbour "only where it is declared and honoured". Where a dependency crosses an undeclared or bypassed boundary, "the two are one system for deciding what a change answers to." "Traits describe a system, and axioms bind it". Systems relate in exactly two ways, contain and compose. E5 Boundaries: a system is "Not a repository, a deployment unit or a process by definition" and is "Not defined by size or by traits". E6 adds that a component is "a system seen as a part of a larger system that contains it".

### axiom-direction.Q1
The service is stateful, so A1 binds. State kept only in process memory is A1's named fault: "Hidden State Problem - state lives inside a process; other actors reason about a different reality" (A1 Mandate: "No functional unit possesses private, opaque, or transient truth"). A5 Perceptual Parity also binds, because the service is multi-agent. If your feature does not touch that component, A0 does not require you to fix it: "Beyond the scope, improvement is encouraged, never mandated". You may close it opportunistically, as a change of its own, only if it is adjacent (shares a declared interface, E6) and passes A14's tangent discipline. Otherwise it "is recorded with its evidence and a revival trigger (RU3) rather than closed", and A0 says "Either way the gap is recorded. Passing it silently is what the axiom forbids." For your feature, A0 says "new work never repeats a gap the axiom names": its state must live in the shared, durable backplane (A1 Mechanics), not in process memory. If the feature newly depends on that component, the component is "touched but not altered, so its gaps must not be built on", so do not rely on its hidden state. If the feature modifies the component, you must close "as much of it as the touch allows".

### axiom-direction.Q2
An axiom is a limit to steer toward, not a test to pass. A0 calls it "a load-bearing asymptote - a limit a system is built toward". A system "is not wrong for being short of it; it is wrong for moving away from it." When you change a system an axiom binds, the axiom does two things: "No change may move the system away from the limit, and each change moves it toward the limit as far as the change's own scope allows" ("never backwards, and forward with every step"). A0 records the pass/fail reading as a fault ("The conformance reading") and keeps a CORRECTION banner retracting the older invariant wording. A gate checks only the direction: "that the change moved the system no further from any limit in force, and repeated no gap it touched". Axioms are "conjunctive in force", so you cannot trade one against another: "a regression with thirteen consolations".
