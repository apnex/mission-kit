### design-rulings.R1
Your change has to declare the interface between T and N, and get N to use it. Without that, T and N count as one system with the traits of both (E5 Boundaries, A0 "What brings an axiom into force"). E5 Boundaries says: "A change that alters what an undeclared neighbour reaches into owns that boundary: declaring and honouring the interface is inside its scope, not optional." Your change also answers to N's axioms, because it alters a contract in fact that N relies on (E5: "Behaviour another unit depends on without any declaration is a contract in fact ... and a change to it reaches across"). Before you finish, check the interface against T's duty. Then do one of two things: move N onto the interface, or adjust the interface to what N legitimately needs (E5 "Declared against honoured"; A3 Mechanics, "Bypass as Signal"). Versioning the new interface is "encouraged, not required"; if you do not add it, record the gap (E5 versioned-contract discriminator). GUESS: the service probably counts as multi-agent under T3, which would bring in A5/A6/A7/A10/A13. The corpus defines T3 by work crossing between actors "inside the system", and the question does not say whether the handoffs happen inside the service.

### design-rulings.R2
(1) No. E5 Boundaries says: "The merge chains only through what a change can reach: if A reaches into B and B into C, a change to A is one system with C only when it alters something B takes from C." A change that only A uses alters nothing B takes from C, so C's axioms do not bind it. A and B still count as one system for this change, so B's axioms do (A0; E5). (2) Yes. The change alters something B takes from C, and that is exactly the condition under which the merge chains to C (E5 Boundaries). Each undeclared reach is also a fault under A3 (A3 Mechanics, "Air-Gap Principle"). GUESS: in (2) I assumed "alters data that ... B itself takes from C" means the change alters what flows from C to B. The question does not say which unit the change sits in.

### design-rulings.R3
Yes, the service is stateful, and A1 binds your change. The module that writes records and later reads them back to act on them passes T1's test ("write something it will later read back, and would anything act differently if that record were wrong?"). E5 says "A system has every trait any part it contains has", and T0 says "a service with one stateful module is stateful". A change answers to "every system containing it" (A0), and E5 adds: "units inside one system need no chaining, because a change to any of them answers to the containing system". So A1 (applies-to: stateful) binds the change even though the module you touch is stateless. In practice that means the change must not move the service away from A1's limit, and must move it toward that limit as far as the change's own scope allows (A0). E5 "Why precision matters" names the alternative reading as the error: "a stateful system escapes its own axioms by being described as stateless modules".

### design-rulings.R4
Yes. A1 binds the organisation's records, not the tool. E5 says "The organisation doing the work is a system" and "A stateless product built by a team that keeps records it relies on has `A1` binding the team's records, not the product." The team writes records, reads them back and relies on them, which passes T1's test, so the organisation is stateful. The tool is stateless and has no model in the loop, so it is not stateful. Its binding axioms are the any-system floor (A3, A4, A8, A9, A14), plus T2-declarative (A2) if it happens to be declarative, which the question does not state (A0 applicability matrix). E5 also says the two questions are asked separately. A1 governs how a change is made and recorded, and the organisation "is not one of the systems the change alters". The handoffs also make the organisation multi-agent (T3), so A5/A6/A7/A10/A13 bind how the work is done as well.

### design-rulings.R5
You must build the small feature itself so that it does not repeat or worsen the tangle. Where the feature already alters the tangled code to do its own work, it must reduce the tangle as far as that touch allows (A0; A3 Mandate: "a change short of it adds none of them, and removes what it touches"). The full split goes beyond what the feature needs, so it is "the encouraged improvement ... not a requirement" (A0: "restructuring beyond that, even inside the same component"). A3 "Composable by Default" encourages the split within K's duty ("fix it, fracture it, re-cut its seams"). A0 says an agent who sees such an improvement "is expected to weigh doing it, not merely permitted to". If you do the split, make it a separate change of its own. K's interface is unversioned, so that change alters all three consumers at once and answers to all of their axioms (E5; A0). Adding versioning while you are there is encouraged, not required; if you do not add it, record the gap (E5). If you do not do the split, record the gap with its evidence and a revival trigger (A0; RU3), because passing it silently is what A0 forbids.

### design-rulings.R6
Publishing 2.4 alters all ten consumers. E5 says "A declared version range - *any 2.x* - is adoption in advance: a release within it alters every consumer bound by the range, whether or not the consumer's own files change." All ten use the floating 2.x range, and 2.4 falls inside it. Using only L's declared interface does not protect them, because 2.4 changes the behaviour that interface documents. The usual rule, that a published version alters no consumer until it adopts it, does not help here: the range is adoption already given. So publishing 2.4 answers to all ten consumers' axioms (A0: "any system whose contract with it the change alters"). NOT SETTLED: whether something like a lockfile, which delays resolution until the next build, changes when the alteration happens. The corpus does not address this. It also does not address whether 2.4 should have been a major version under semantic versioning.

### OBSERVATIONS
- E5's "Declared against honoured" says a bypass ends "after the interface is evaluated against the component's duty" with one of two outcomes. A3 "Bypass as Signal" says the same. But E5 Boundaries says the change that alters the reached-into function "owns that boundary", and it does not say how far a small change must go if adjusting the interface turns out to be large. Neither entry reconciles this with A0's "as much as the touch allows".
- E5 and A0 make a direct undeclared dependency (A into B) merge the two unconditionally, "for deciding what a change answers to". The transitive case (to C) is merged only if the change alters what B takes from C. So a change to A always answers to B, even when it alters nothing B exposes. That asymmetry may be intended, but no entry states it.
- R2(2) is worded ambiguously about which unit the change sits in. E5's chaining rule is phrased as "a change to A", so it does not directly cover a change made in B or C that alters the data flow.
- T3's test uses the phrase "inside the system", so it is unclear whether "a service operated by several agents" makes the service multi-agent or only the organisation operating it. E5 separates product systems from the organisation, but it does not say where operation of a running service falls.
- A0 line 87 refers to "an adjacent component" when it describes expected-to-weigh improvement. A3 "Composable by Default" encourages improving the touched unit itself. Neither entry says whether the "expected to weigh" duty also covers the touched component's own internals beyond the touch, which is the R5 case. I read it as covering them.
