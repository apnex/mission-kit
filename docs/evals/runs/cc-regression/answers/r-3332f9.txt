### s0.Q1
The corpus names this as a fault: style/README.md, Faults, "The forked enforcer. Two tools holding one rule, disagreeing at the edges. This is why a rule names exactly one."
Its Enforcement boundary section says "An enforced rule names exactly one tool" and "One rule, one tool, and that tool owns both the check and the fix, so a rule cannot be reported by one implementation and refused by another."
The pairing is declared in each rule's `enforced-by` frontmatter, and tools/check-enforcers.sh checks it in both directions: "a rule naming a tool that does not exist is a broken promise" and "a per-rule tool that no rule claims is orphaned".
So the remedy is to collapse to one tool, owned by the rule, and delete or merge the other.
NOT SETTLED: the corpus does not say which of the two tools should win, or how to resolve the edge cases themselves.
GUESS: keep the tool the rule's `enforced-by` already names, and fold the other's edge-case handling into it as fixtures/tests.

### s0.Q3
No, not by default.
style/README.md, Enforcement boundary: "Style is gated on changed files rather than on the whole corpus. The corpus carries debt that predates the checkers, so gating the diff blocks new debt and converts the rest opportunistically as sections are edited."
tools/check-all.sh confirms it: "s6 s8 s10 s12 s13 s14 one sovereign checker per style rule, on changed files only", where changed means committed against the base (default origin/main) plus staged, unstaged and untracked `.md` files.
A whole-corpus run is available on request with `tools/check-all.sh --all`.
Note that only the six tool-held rules are run at all; the nine reading-only rules are not checked by the gate on any file.
The Faults list also warns against "The corpus-wide sweep" - converting all legacy debt in one unreviewable commit.

### s0.Q7
style/README.md, Faults, describes it: forked enforcers (two tools holding one rule and disagreeing at the edges); orphaned rules ("A convention nobody enforces and nobody reviews, which teaches readers that the layer is decorative"); an unscoped medium (rules for one medium scattered among the document rules with nothing grouping them); work rules in style clothing (conventions about what the work does or records filed as style); and corpus-wide sweeps (one unreviewable commit converting all legacy debt, hiding a real change).
From "What earns an entry", rules born of aesthetic preference or confined to one document would also be unhealthy members.
The Axiom alignment section names the present weak points: nine of fifteen rules held only by reading, so "their hold is as strong as the review that reads for them", and three claimed media with no rule.

### OBSERVATIONS
- tools/README.md (around line 63) defines "changed" as "committed against the base plus staged plus unstaged", while tools/check-all.sh also includes untracked files; the README is behind the script.
- tools/check-all.sh repeats a comment line ("Committed against the base, plus staged, plus unstaged.") before an expanded version; it looks like a leftover from an edit.
- The style gate only considers `.md` files, so a future rule for source-code names or comments (the gaps) could not be gated by the current check-all.sh logic without changing it; the charter does not mention this.
- The style/README.md index row for S0 has an empty "Held by" cell, which is fine for a charter but is not explained.
- Contrary to the "one rule, one tool" claim, the charter does not say how to resolve edge-case disagreement itself, only that it should not arise.
