### component.C1
Your fix touches X (axioms/README.md: "A change touches what it modifies, what it newly depends on, and any consumer whose contract it alters"), and it answers to X and the service that contains it; Y is not touched, because X already depended on it, and Z is not touched, because "code that merely sits beside it ... is not touched". Y is adjacent, since X consumes Y's declared interface (entities/E6-component.md), and it is the "closer" direction ("the one the other stands on"), so A0 says improvement there is "encouraged, never mandated", and you are "expected to weigh doing it, not merely permitted to". The A14 tangent test it names passes here: adjacency, near payback (it cost you 20 minutes), and a five-minute cost that "does not significantly distract", so the corpus leans toward closing it, provided the yield is captured. Make it "a change of its own", not part of the X fix; if consumers depend on the message text, it alters them too (A0; E5). Z is not adjacent to X ("nearby and not adjacent", E6), and two days would displace the goal, so it fails the test: record it "with its evidence and a revival trigger (RU3) rather than closed", leaving the choice of next work to the director (R4, AR3). "Either way the gap is recorded. Passing it silently is what the axiom forbids." That only obliges the X change not to move away from A1's limit, for example by adding hidden state or building on Z's gap; it does not oblige you to fix Z.

### component.C2
It is defined in entities/E6-component.md: "A component is a system seen as a part of a larger system that contains it. It has one duty at the altitude where it appears as a part, and it exposes and consumes interfaces". A system (entities/E5-system.md) is "a unit of engineering with a boundary: what is inside it, and the contracts through which anything outside reaches it". They are not different kinds of thing: "Every component is a system; component names its place in a containing system, not a different kind of thing." They differ by which question you are answering: "Traits, axioms and what a change answers to are questions about a system. Duty, interfaces, neighbours and blast radius are questions about a component". A system that nothing contains, such as a whole product seen from outside, "is not a component of anything" (E6). A component is not, by definition, a file, module, package, repository, deployable, SysML part or registered (components/) unit (E6 Boundaries).

### component.C3
No. E6: "A component's directory addresses it ... Its boundary is its declared interfaces", and E5: "A directory ... is the boundary of neither the system nor the component." Because nothing is declared, parts/thing/ "is still a component, but nothing separates it yet: for deciding what a change answers to, it is one system with whatever reaches into it" (E6). So parts/other/ and parts/thing/ count as one system "with the traits of both" (E5 Boundaries). What is wrong is the undeclared dependency, which "is itself a fault against A3" ("no unit reaches into another's internals", A3 Air-Gap Principle). E6 also says a detected crossing "is a signal about the interface as well as a fault in the consumer". The remedy is to declare the interface and move the dependency onto it, which "is what makes them two again" (E5). A change that alters what parts/other/ reaches into "owns that boundary: declaring and honouring the interface is inside its scope, not optional" (E5).

### component.C4
Your change answers to P and to the service that contains it (A0: "the system it modifies, every system containing it, and any system whose contract with it the change alters"). Q only composes with P through an interface the change "leaves as it was", so Q "is not altered, and its axioms do not bind" (A0), and it is not touched (A0's touch definition). One nuance: the service contains Q and "has every trait any part it contains has" (E5), so axioms that Q's traits bring in still bind your change through the service, not through Q. All of this assumes Q honours the interface; if Q reaches past it, or relies on undeclared behaviour ("a contract in fact", E5), the two are one system. Q is adjacent, because it consumes what P exposes (E6), so A0 allows it as an opportunistic candidate "when compounding learning supports it", made as a change of its own, with the gap recorded either way. It is the lower-payback direction: "the other direction is adjacency with less payback, not none" (E6), whereas payback is "strongest where the work stands on the component" (A0).

### OBSERVATIONS
- A0 says "Scope and binding are different sets", but the containing-system rule (E5: "A system has every trait any part it contains has") means Z's or Q's traits can bind a change that never touches them. The corpus is consistent on this, but it is easy to misread.
- A3's "Bypass as Signal" is written for reaching past a *declared* interface. E6 applies the same "signal about the interface" language to a crossing where no interface exists (C3), which leaves open what interface is being evaluated.
- A0 says improvement beyond scope is "encouraged, never mandated" and also that an agent is "expected to weigh doing it, not merely permitted to". These reconcile (weigh is required, doing is not), but on first read they look like a tension.
- NOT SETTLED: whether an error message's text is part of Y's declared interface. That decides whether improving it alters Y's consumers (E5 "parsing output the interface does not promise").
- NOT SETTLED: whether in-process memory "persists beyond a single operation" in T1's sense; T1 says only that storage alone does not decide it.
- INDEX.md says to resolve links against a local checkout or else GitHub; this corpus copy was read locally only.
