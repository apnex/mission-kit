### work-layers.L1
It belongs in the rules layer (`rules/`, prefix RU). The reason is M0's placement test: guidance that "only *requires* a record to carry something - a field, a reason - produces nothing itself, and is a rule". M0 even uses this case as its example: "*every deferral records its revival trigger* ... is still a rule, because it governs what the work records" (methods/README.md). It is already covered by RU3 "Anti-amnesia deferral" (rules/RU3-anti-amnesia-deferral.md): "When you defer, park, or cut a unit of work, record - at the moment of deferral - a concrete **revival trigger**", which is a required field, with trace "every deferred, parked or cut item's record carries a revival trigger". The document that holds such rows is the artifact type AR5 Backlog (artifacts/AR5-backlog.md), whose rows need "revival trigger | required unless closed; an observable condition". It says "Later" is not a trigger. M5 is the old, superseded location of this rule ("Moved to RU3 by Delta-1").

### work-layers.L2
It belongs in the skills layer (`skills/`, prefix K). In M0's table, "a capability you execute" goes to `skills/` because "the object is a procedure with inputs and outputs, invoked rather than followed" (methods/README.md). K0 adds that a skill "earns its packaging where scripts or assets make it necessary" and earns an entry when it is "executable, repeatable, and would otherwise be reconstructed from scratch" (skills/README.md). A fixed artefact layout shipped as templates is exactly that kind of asset. It is also already covered: K3 substrate-audit runs a "**five-pass meta-process**" (Sweep, Triangulation, Promotion audit, Synthesis, Reconciliation) and is "structured around a fixed artefact layout" under `docs/<domain>/<substrate>/`, with templates in skills/substrate-audit/templates/ (skills/K3-substrate-audit.md). So the new proposal should strengthen or extend K3, not add a neighbour (M0: "Prefer strengthening an existing entry to adding a neighbour").

### work-layers.L3
It belongs in the work-types layer (`work-types/`, prefix W), because a work-type is "taxonomy-grade **iff it compiles to a closeable claimable node**". Its schema carries exactly the parts asked for: `roleEligibility` (who), `domainEligibility` (what it may be pointed at), and `evidenceContract`/`evidenceAuthority`/`falsifier` (what proof ends it) (work-types/README.md). It is already covered by W10 adversarial-design-review-upstream: "A verifier red-teams a design **before** build or merge, producing a critique doc that raises specific, falsifiable failure hypotheses". W10 sets `roleEligibility: [verifier]` and allows all seven domains (`domainFreedom: free`). Its evidence is a `kind: review` critique doc with `evidenceAuthority: verifier-attestation`, and its falsifier is "review after the decision, or no falsifiable concerns raised" (work-types/W10-adversarial-design-review-upstream.md). It cites M1 as its conducting method.

### work-layers.L4
It is a methodology entry (`methods/`). Following it produces "a result of its own - a verdict", which is M0's placement question 2 (methods/README.md). It is not a skill: no scripts or assets need packaging (skills/README.md). It is not a work-type: it does not compile to a claimable node, and work-types cite it instead (W8 and W10 both have `methods: [M1]`). It is already covered by M1 Triangulated review: "require **at least four genuinely independent inputs** before reaching a verdict", triggered by "Reviewing patches or designs that ship to production or upstream" (methods/M1-triangulated-review.md). M0 calls M1 the primitive that "carries the set". Caveat: M1 itself softens the number ("sometimes 3 is enough; sometimes 5 is needed"), and its body heading is "## Rule" even though it is not in the rules layer.

### work-layers.L5
The corpus names this moment "**handing over**", one of six moments shared by methods, rules and practices, and records it as a gap in all three. methods/README.md says: "handing work in progress to another agent or a later session has no procedure at all". It explicitly includes the same agent tomorrow: "a lone agent hands over to its own next session". The only member in that row is M10, which hands over to a human. rules/README.md says: "*Handing over:* a handover record names what is unfinished - a rule that would leave a trace, and none exists". practices/README.md lists handing over as "none - gap" with "no checked candidate yet". So the layer depends on form, by M0's placement ladder: a procedure producing a handover record goes in `methods/`, a required record field goes in `rules/`, and untraceable judgement goes in `practices/`. A4 still binds ("A cold pickup from the record alone reproduces the same outputs as a warm actor"), and T1/T3 class next-session notes as stateful but not multi-agent. GUESS: the first entry would be a rule or a method, because the rules charter already drafts the candidate wording.

### work-layers.L6
Method: "steps that **produce a result of their own** - a verdict, an artifact, a record" (methods/README.md). Skill: "invoked, not followed ... A method is a procedure held as guidance, the single source of its content; a skill packages a procedure so an agent can install and invoke it, and earns its packaging where scripts or assets make it necessary" (skills/README.md). Work-type: "taxonomy-grade **iff it compiles to a closeable claimable node**", and it "cites the procedure that conducts it, in `methods`" (work-types/README.md). Method vs skill is the hard pair, because both are result-producing procedures and only packaging separates them. The corpus admits this. M0 lists the fault "The procedure that is really a skill", and K0 says "A skill that only describes is a method ... as `M9` was before it moved" (M9 supersedes K1). Also, M0's five-step placement ladder has no skill or work-type rung, so by question 2 a skill such as K3 would be classed as a "procedure, here". Method vs work-type is easier to tell apart because they are joined by citation: W10 cites M1.

### work-layers.L7

### OBSERVATIONS
- W10 says that with a collapsed roster verifier-attestation "falls back to plain `kind:review`". W0 constraint 2 says a collapsed roster must "fail the seed", wait for an independent agent or director ratification, and "a same-agent review never stands in". These appear inconsistent.
- M0's five-question placement ladder (axiom, procedure, style, rule, practice) has no rung for skills or work-types. Read literally, it would class a result-producing skill such as K3 as a method. K0's packaging criterion is needed to separate them, and only K0 and M0's table state it.
- M1 and K3 use a "## Rule" body heading even though they are a method and a skill, which blurs the RU "rule" layer name.
- K3's artefact layout lists `05-coverage.md`, which has no template, and omits `02-code-trace.md`, which has one. The SKILL.md description lists a different set ("summary, architecture map, goal mapping, prober assessment, sources").
- W0 "Gaps recorded" contradicts itself on the governance/coordination machinery: "The domains set has not said which", followed immediately by "The domains charter's tie-break, applied to one such change, settles which."
- INDEX.md calls itself a "flat ledger" in README.md ("the flat ledger across every category") but is grouped by layer.
- E2 gives schemas the category `contract`, and SC0 matches that. README's table, however, describes the layer only by prefix SC, so the category name differs from the directory name, as E2 warns.
