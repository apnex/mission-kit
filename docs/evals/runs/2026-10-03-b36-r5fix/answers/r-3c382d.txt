### component.C2
It is defined in entities/E6-component.md: "A component is a system seen as a part of a larger system that contains it. It has one duty at the altitude where it appears as a part, and it exposes and consumes interfaces". "System" is defined in entities/E5-system.md as "a unit of engineering with a boundary: what is inside it, and the contracts through which anything outside reaches it". They are not different kinds of thing: "Every component is a system; component names its place in a containing system, not a different kind of thing." What separates them is the question being asked: "Traits, axioms and what a change answers to are questions about a system. Duty, interfaces, neighbours and blast radius are questions about a component". So a system nobody contains "is not a component of anything until it is part of some larger whole" (E6). Being registered in components/ is not part of the definition ("Most components are never registered", E6).

### component.C3
No. E6 ("Boundary against directory") says: "A component's directory addresses it... Its boundary is its declared interfaces", and E5 adds that a directory "is the boundary of neither the system nor the component." The fault is that parts/other/ reaches into parts/thing/'s internals and no interface is declared. That breaks A3's Air-Gap Principle: "no unit reaches into another's internals" (axioms/A3-sovereign-composition.md; E5 calls the undeclared dependency "itself a fault against A3"). The consequence is that parts/thing/ "is still a component, but nothing separates it yet: for deciding what a change answers to, it is one system with whatever reaches into it" (E6), "with the traits of both" (E5). The fix is to declare the interface and move parts/other/ onto it: "Declaring the boundary, and moving the dependency onto it, is what makes them two again" (E5). Any change that alters what parts/other/ reaches into "owns that boundary: declaring and honouring the interface is inside its scope, not optional" (E5).

### component.C4
Your change answers to P, which it modifies, and to every system containing P, including the service: A0 says "a change answers to every system it alters... the system it modifies, every system containing it, and any system whose contract with it the change alters." Q is not altered and its axioms do not bind as Q's: "A system it only composes with, through a contract the change leaves as it was, is not altered" (A0; E5 makes the same point for unchanged interfaces). One caveat from the text: the service "has every trait any part it contains has" (E5), so any axiom Q's traits bring into force still binds your change through the service. That holds only if Q uses the interface honestly; if Q reaches past it, P and Q "remain one system" (A3 "Bypass as Signal"; E5 "Declared against honoured"). Q is a candidate for opportunistic improvement, because adjacency means "a shared declared interface, in either direction", and A0 allows "one it stands on, or one that stands on it". Q stands on P, though, so this is "adjacency with less payback, not none" (E6), and it must still pass A14's tangent test and be made as its own change, or else be recorded with a revival trigger (A0, RU3).

### OBSERVATIONS
- The corpus does not say whether an error message's text is part of a declared interface. That decides whether improving Y (C1) alters Y's consumers.
- In C1, X's fix is not yet landed. A0 says an opportunistic improvement is "a change of its own" but does not say how to order it against the main change. NOT SETTLED.
- In C3 no interface exists, yet E6 says "A detected crossing is a signal about the interface", and A3's "Bypass as Signal" is written for declared interfaces. It is unclear how the interface evaluation applies when there is no interface to evaluate.
- Inconsistency: components/README.md says A3 "mandates that a new capability is assembled by composing existing units rather than by modifying them", but A3's "Composable by Default" explicitly encourages improving existing units within their duty.
- A join that is easy to miss in C4: Q's own axioms do not bind the change, but because a containing system takes on every trait of its parts (E5), Q's traits still reach the change through the service. Neither A0 nor E6 says this in one place.
- E6 says a component's boundary "separates the component from a neighbour only where they are declared and that neighbour uses them". In the same entry, the Boundaries section names declared interfaces as "the limit a component is built toward... not the price of being one". These are consistent, but on a first read the second looks like it contradicts the first.
