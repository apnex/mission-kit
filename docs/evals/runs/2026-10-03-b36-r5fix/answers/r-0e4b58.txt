### design-rulings.R1
Your change must declare an interface on T for what N legitimately needs and move N onto it, as part of this change; it is not optional. E5 Boundaries: "A change that alters what an undeclared neighbour reaches into owns that boundary: declaring and honouring the interface is inside its scope, not optional." Until then N and T are "one system, with the traits of both" (E5 Boundaries; A0 "What brings an axiom into force"), so the change answers to the axioms either brings, and the undeclared reach is itself an A3 fault ("no unit reaches into another's internals", A3 Air-Gap Principle). How the bypass ends is set out in E5 ("Declared against honoured") and A3 ("Bypass as Signal"). First the interface is evaluated against T's duty. Then either N is moved onto the interface, or the interface is adjusted to what N legitimately needs. Both modules sit inside one service, and a change to either already answers to that containing service (E5 Contain; E5 Boundaries: "units inside one system need no chaining").

### design-rulings.R3
Yes, the service is stateful. The writing module passes T1's test: it "write[s] something it will later read back", and acting on those records means a wrong record would change behaviour. E5 Contain says "A system has every trait any part it contains has", and T0 says "a service with one stateful module is stateful". Yes, A1 binds your change. A0 says a change answers to "the system it modifies, every system containing it", so changing the stateless module alters the containing service, and A1 (applies-to: stateful) is in force for that service. E5 "Why precision matters" names the error this rule prevents: "a stateful system escapes its own axioms by being described as stateless modules". How far the change must move toward A1 is set by its scope (A0). It must not move the service away from A1's limit. It must close any A1 gap only as far as the part it already alters.

### design-rulings.R4
Yes. A1 binds the team's records of the work, not the tool. E5 states this case directly: "A stateless product built by a team that keeps records it relies on has `A1` binding the team's records, not the product." ### design-rulings.R5
The axioms require you to make the feature without adding to the tangle. You must also close the tangle in the part your feature already alters. A3: "a change short of it adds none of them, and removes what it touches". A0 limits that to "the part the change already alters to do its own work". The full split goes beyond that part. So it is encouraged improvement, "not a requirement" (A0). You are still expected to weigh it, not just allowed to: "within the unit's own duty, fix it, fracture it, re-cut its seams and recompose it so it makes better sense for every consumer downstream" (A3 Composable by Default; A0 "expected to weigh doing it"). If you do the split, make it a separate change. K's interface is not versioned, so the split alters all three consumers, and that change answers to each consumer's axioms (A0; E5 versioned-contract discriminator). Either way the gap must be recorded, and if you leave it open it needs evidence and a revival trigger under RU3: "Either way the gap is recorded. Passing it silently is what the axiom forbids" (A0).

### design-rulings.R6
Publishing 2.4 alters all ten consumers. E5: "A declared version range - *any 2.x* - is adoption in advance: a release within it alters every consumer bound by the range, whether or not the consumer's own files change." Using only the declared interface does not protect them, because 2.4 changes the behaviour that interface documents, which alters each consumer's contract with L (A0: a change answers to "any system whose contract with it the change alters"). So the release answers to each of the ten consumers' axioms, as well as L's own.
