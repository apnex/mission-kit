### component.C1
Y: your fix modifies X, and Y is a component X stands on through a declared interface, so Y is "adjacent" (E6: "share a declared interface - one consumes what the other exposes"), in the closer direction ("the one the other stands on is the closer", E6), but it is not in scope, because A0 says a change "touches what it modifies, what it newly depends on, and any consumer whose contract it alters", and X already depended on Y. So A0 does not require you to fix Y. It does say "An agent that sees how to bring an adjacent component nearer its limit ... is expected to weigh doing it", and the gap "may be closed opportunistically when compounding learning supports it" (A14 tangent discipline: payback near, yield captured, cost does not displace the goal). A 20-minute cost against a 5-minute fix passes that test. The fix goes in "as a change of its own", and "Either way the gap is recorded"; passing it silently "is what the axiom forbids" (A0). If the error text is part of Y's declared contract, the change alters Y's consumers and answers to them (A0, E5); NOT SETTLED whether an error message counts as part of an interface. Z: X does not use Z, so Z is neither touched nor adjacent ("nearby and not adjacent", E6), and about two days is "large enough to displace the goal", so A0 says to record it "with its evidence and a revival trigger (RU3) rather than closed", leaving the choice to the director (R4, AR3); A1's "Hidden State Problem" names the gap, and because the service contains Z it takes Z's traits (E5), so if Z passes T1's stateful test, A1 binds your X change too (no new hidden state in X), but A1 still does not require you to fix Z.

### component.C2
Defined in entities/E6-component.md: "A component is a system seen as a part of a larger system that contains it", with "one duty at the altitude where it appears as a part", and it "exposes and consumes interfaces"; its boundary is those interfaces, and only "where they are declared and that neighbour uses them". A system is defined in entities/E5-system.md as "a unit of engineering with a boundary". The two are not different kinds of thing: "Every component is a system; component names its place in a containing system". The difference is in the question being asked: "Traits, axioms and what a change answers to are questions about a system. Duty, interfaces, neighbours and blast radius are questions about a component" (E6). A system that nothing contains "is not a component of anything" (E6). E6 also separates this from a registered component in components/ ("registration is a property of a few, not part of what a component is"), and from a file, package, directory or SysML part.

### component.C3
No. E6, "Boundary against directory": "A component's directory addresses it ... Its boundary is its declared interfaces"; E5: a directory "is the boundary of neither the system nor the component". With no declared interface, nothing separates the two: parts/other and parts/thing are "one system" for deciding what a change answers to, "with the traits of both" (E5 Boundaries; E6 Definition). What is wrong: "The undeclared dependency is itself a fault against A3" (E5), which breaks A3's Air-Gap Principle ("no unit reaches into another's internals"). E6 says a crossing is "a signal about the interface as well as a fault in the consumer". The fix is to declare an interface, evaluated against thing's duty, and move other's dependency onto it: "Declaring the boundary, and moving the dependency onto it, is what makes them two again" (E5). A change that alters what parts/other reaches into "owns that boundary: declaring and honouring the interface is inside its scope, not optional" (E5).

### component.C4
Your change answers to "the system it modifies, every system containing it, and any system whose contract with it the change alters" (A0): that is P and the service; the interface is unchanged, so no contract is altered. Q is not altered: "A system it only composes with, through a contract the change leaves as it was, is not altered, and its axioms do not bind" (A0; E6 blast radius: an adjacent component is reached "only if the interface between them changes"). There is a catch: the service "has every trait any part it contains has" (E5), so any axioms Q's traits bring in still bind your change through the service, not as Q's own. This only holds if Q actually honours the interface; if Q reaches past it, P and Q "stay one system" (E5 "Declared against honoured"). Q is a candidate: it shares a declared interface with P, which you touch, so it is adjacent ("one it stands on, or one that stands on it", A0). It is in the lower-payback direction, though ("the other direction is adjacency with less payback, not none", E6). So improving Q is encouraged rather than required, subject to A14's tangent test, done as a separate change, and recorded under RU3 if not done.

### OBSERVATIONS
- A0's scope rule ("what it newly depends on") leaves it unclear whether a dependency you already had, and that your fix exercises (Y in C1), counts as touched. I read it as not touched but adjacent.
- Whether an error message is part of a declared interface, so that changing it alters Y's consumers, is not settled anywhere I read.
- E6 says A3 "states what it triggers" for a crossing, but A3's "Bypass as Signal" is worded for reaching past a declared interface. For the C3 case, where no interface is declared, E5's "undeclared dependency is itself a fault against A3" fits better.
- T1's test ("persists beyond a single operation") leaves it unclear whether state held only in process memory makes Z, and so the service, stateful. That decides whether A1 is in force at all.
- INDEX.md says to resolve links against a GitHub URL when there is no local checkout. I used only the local corpus, as instructed.
