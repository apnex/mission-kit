### explain.X4
Subject: Before you add the new payment event type - how we avoid charging customers twice

Welcome. Before you change the payment event code, there is one idea you need: idempotency. It is what keeps a customer from being charged twice.

The problem
Our system can deliver the same event to us more than once. This isn't a bug we can fix; the systems that send us events can retry, for example when they didn't get our reply in time. If we process an event that charges a customer and then it arrives again, processing it again would charge them a second time.

The idea
An operation is idempotent if doing it twice has the same effect as doing it once. Pressing a lift call button is idempotent: pressing it five times still calls one lift. Charging a card is not idempotent by itself - every charge takes money. So we make the event handling idempotent by remembering what we have already done.

How our code does it
Every event carries a unique id. When we process an event:
1. Check whether its id is already recorded. If it is, we have already handled this event, so we skip it.
2. If not, make the charge and record the id - in the same database transaction.

The "same transaction" part matters. A transaction means both steps happen or neither does. If we recorded the id separately, a crash between the two steps would leave either a charge with no record (so a redelivery charges again) or a record with no charge (so the customer is never charged). Keeping them together rules out both.

What this means for your new event type
Two rules:

1. Send it through the same check. Don't write a separate path that charges without checking and recording the id. Any path that skips the check brings back double charging.

2. Its id must be the same every time that event is delivered. The check only works if a redelivered event has the same id as the original. So the id has to come from the event itself, as set by whoever sent it. Don't make one up when it arrives - for example a fresh random id, or the time we received it - because a redelivery would get a different id, pass the check, and charge again.

A good test for your change: deliver the same event twice and confirm the customer is charged exactly once.

If you are unsure where the new event's id comes from, ask before writing the code - that is the part most likely to go wrong.
