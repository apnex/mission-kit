### explain.X4
Subject: Before you add the new payment event type - idempotency, and why it matters here

Hi,

You will change the code that handles incoming payment events. There is one idea you need to understand first. If you get it wrong, customers can be charged twice.

The problem
The system that sends us payment events can deliver the same event more than once. This is normal, not a fault, and we cannot stop it. If we process an event a second time, we charge the customer a second time.

The idea: idempotency
An operation is idempotent if doing it twice has the same effect as doing it once. A light switch set to "on" is idempotent: pressing "on" again changes nothing. A button that adds 1 to a counter is not. Our event handling must behave like the switch. The first delivery of an event charges the customer, and any repeat delivery of that event does nothing.

How our code does it
Every event has a unique id. When we process an event, we save its id and make the charge in the same database transaction. Before processing, we check whether that id is already saved. If it is, we skip the event.

Why the same transaction matters
A transaction either saves everything or saves nothing. So it is not possible to have a charge without its id saved, or an id saved without its charge.
- If we saved the id first and then crashed before the charge, the customer would never be charged.
- If we made the charge first and then crashed before saving the id, the next delivery would charge them again.
Doing both in one transaction removes both failures.

What this means for your new event type
1. It must go through the same check as the existing types. Do not add a separate path that charges first and checks later, or never checks.
2. Its id must be the same every time that event is delivered. The check only works if a repeat delivery has the same id as the first one. Use an id that comes with the event from the sender. Do not create one when the event arrives, for example a random value or the time we received it. An id like that is different on every delivery, so every repeat looks new and gets charged again.

How to check your change
Write a test that delivers the same event of the new type twice. Then check that exactly one charge exists and that the id is saved once. If the test shows two charges, one of the two rules above has been broken.

If you are not sure where the id for your event type comes from, ask before you write the code. That is the part most likely to go wrong.
