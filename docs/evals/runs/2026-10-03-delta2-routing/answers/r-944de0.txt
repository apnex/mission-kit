### component.C2
It is defined in entities/E6-component.md: "A component is a system seen as a part of a larger system that contains it", with "one duty" at that altitude, and it "exposes and consumes interfaces"; its boundary is those interfaces. "Every component is a system; component names its place in a containing system, not a different kind of thing" (E6). The difference is which question you are answering: "Traits, axioms and what a change answers to are questions about a system. Duty, interfaces, neighbours and blast radius are questions about a component" (E6 Discriminators; see also E5-system.md "A system against a component"). A system that nothing contains, such as a whole product seen from outside, "is not a component of anything" (E6). A system is defined in E5 as "a unit of engineering with a boundary", related to others by contain or compose. A component is not a file, module, package, repository or deployable by definition. It is not a SysML part, and it does not have to be registered or shareable (E6 Boundaries).

### component.C3
No. "A component's directory addresses it ... Its boundary is its declared interfaces" (E6, "Boundary against directory"), and "A directory places a component's documents; it is the boundary of neither the system nor the component" (E5). parts/thing/ is still a component, but "nothing separates it yet" (E6 Definition). Because no interface is declared, parts/thing/ and parts/other/ "are one system, with the traits of both" for deciding what a change answers to (E5 Boundaries; A0). So a change to thing's internals reaches other, and the axioms either one brings all bind it. The undeclared dependency "is itself a fault against A3" (E5; A0), which violates A3's Air-Gap Principle: "no unit reaches into another's internals". The fix is to declare thing's interface and move other's dependency onto it: "Declaring the boundary, and moving the dependency onto it, is what makes them two again" (E5). A3's "Bypass as Signal" also asks you to check that the interface covers the component's duty, so that the reaching-in is not simply moved somewhere else.

### component.C4
Your change answers to the systems it alters: "the system it modifies, every system containing it, and any system whose contract with it the change alters" (A0). That means P and the service that contains it. Q composes with P "through a contract the change leaves as it was", so Q "is not altered, and its axioms do not bind" (A0). E6's blast-radius row says the same: a change reaches "an adjacent component only if the interface between them changes". This holds only if Q actually honours the interface; if Q reaches past it, Q and P stay one system (E5 "Declared against honoured"). Q is adjacent, because it shares a declared interface with P, and A0 allows opportunistic improvement to "one it stands on, or one that stands on it". So Q is a candidate, but in the weaker direction: Q stands on P, not the reverse, so it is "adjacency with less payback, not none" (E6). Any improvement still has to pass A14's tangent test and be made as a separate change.
