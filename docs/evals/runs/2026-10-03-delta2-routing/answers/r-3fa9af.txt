### component.C2
It is defined in entities/E6-component.md: "A component is a system seen as a part of a larger system that contains it", with "one duty at the altitude where it appears as a part", and it "exposes and consumes interfaces"; its boundary is those interfaces. It is not a different kind of thing from a system: "Every component is a system; component names its place in a containing system, not a different kind of thing." The difference is in the question you ask: "Traits, axioms and what a change answers to are questions about a system. Duty, interfaces, neighbours and blast radius are questions about a component" (E6 Discriminators; mirrored in entities/E5-system.md, "A system against a component"). "A system nobody contains ... is not a component of anything." E6 also says a component is not a file, module, package, repository or deployable by definition, not a SysML part, and not necessarily a registered entry in components/ (registration is "a property of a few").

### component.C3
No. E6 says "A component's directory addresses it ... Its boundary is its declared interfaces", and code that reaches past the interface "is not kept out by the directory; it has crossed the boundary"; E5 says a directory "is the boundary of neither the system nor the component". Here no interface is declared, so nothing separates them: for deciding what a change answers to, parts/thing and parts/other are "one system, with the traits of both" (E5 Boundaries; E6 Definition). The undeclared dependency "is itself a fault against A3" (E5), which violates A3's Air-Gap Principle: "no unit reaches into another's internals". The remedy is "Declaring the boundary, and moving the dependency onto it" (E5). A3's Earned Exposure is met, because parts/other is a real consumer. A0 makes this fix mandatory only for a change that touches the gap; otherwise it is an opportunistic improvement or a recorded gap.

### component.C4
Your change answers to P's axioms and to the axioms of every system containing P, including the service: "a change answers to every system it alters. That is the system it modifies, every system containing it, and any system whose contract with it the change alters" (axioms/README.md; E6 "Blast radius"). Q is not altered: "A system it only composes with, through a contract the change leaves as it was, is not altered, and its axioms do not bind" (A0). That holds only if Q honours the interface; if Q reaches past it into P's internals, the two "stay one system" and Q's axioms bind too (E5 "Declared against honoured"). Q is a candidate for opportunistic improvement because it is adjacent (it consumes what P exposes, E6), and A0 counts a component "that stands on it" as adjacent. But Q stands on P rather than P on Q, so per E6 this is "adjacency with less payback, not none"; it must still pass A14's tangent discipline, or be recorded with a revival trigger (RU3).

- A1's fault fits in-process hidden state, but T1's test ("persists beyond a single operation", "authoritative") leaves unclear whether in-memory state makes the service stateful.
