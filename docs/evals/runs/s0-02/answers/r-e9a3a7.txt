### s0.Q1
The corpus names this as a fault. `style/README.md` (S0), Faults: "The forked enforcer. Two tools holding one rule, disagreeing at the edges. This is why a rule names exactly one."
The remedy is in S0 "Enforced and unenforced rules": an enforced rule "declares `enforced-by` in its frontmatter naming exactly one tool ... One rule, one tool, and that tool owns both the check and the fix, so a rule cannot be reported by one implementation and refused by another." `tools/README.md` lines 5-7 say the same.
`tools/check-enforcers.sh` holds the pairing. Any per-rule tool matching `tools/s[0-9]*-*` that the rule's `enforced-by` line does not name is reported as "orphan tool". So a second `s6-*` checker would fail the gate.
The fix is to keep one tool, retire the other, and make the remaining tool own both check and fix.
GUESS: a second checker named outside the `s<N>-` pattern would not be caught by `check-enforcers.sh`, because it only globs that pattern.

### s0.Q3
No, not by default. S0: "Style is gated on changed files rather than on the whole corpus. The corpus carries debt that predates the checkers, so gating the diff blocks new debt".
`tools/check-all.sh` lines 15-20 and 103-119: the style checkers run only on `.md` files changed against `origin/main` (or `--since REF`). That means committed, staged, unstaged and untracked changes, and `.md` files only. If nothing changed, the style step passes with "no markdown changed".
`--all` runs style over every `.md` file in the corpus, but it is opt-in.
The other gates in `check-all.sh` are not limited to the diff: structure, enforcers, entry bodies, index, schema and standing context. The `*.test.sh` tool tests are not limited either; they run "unconditional" over fixtures (lines 74-80).

### s0.Q7
S0 Faults lists four signs:
(1) "The unfalsifiable convention" - rules phrased as qualities ("be clear") with no predicate, cited only when people already disagree.
(2) "The orphaned rule" - nobody enforces it and nobody reviews it, which teaches readers "that the layer is decorative".
(3) "The forked enforcer" - two tools on one rule, disagreeing at the edges.
(4) "The corpus-wide sweep" - all legacy debt converted in one unreviewable commit that hides a real change.
From S0 "What earns an entry", two more signs: entries based on aesthetic preference, and rules that "only hold inside one document". `tools/README.md` line 55 adds an unread checker: "Five checkers existed and nothing ran any of them".

### OBSERVATIONS
- S0 and `tools/README.md` line 6 say each enforcing tool "owns both the check and the fix". But `tools/README.md` lists S8 and S14 with Fix "no, needs judgement", so the claim does not hold for every enforced rule.
- `tools/README.md` line 55 cites "the unread-checker fault the charter names". S0's Faults list has no fault with that name; the closest is "the orphaned rule".
- `tools/README.md` line 55 says "Five checkers existed"; six exist now. This is probably a historical statement, but it is ambiguous.
- `tools/README.md` line 63 defines "changed" as committed, staged and unstaged. `check-all.sh` lines 106-112 also include untracked files. The README is behind the script.
- `check-all.sh` has a duplicated, partly superseded comment (lines 104-108).
- `check-enforcers.sh` detects a second tool only when it follows the `s<N>-` naming. "Exactly one tool" is not checked in general.
- S0 calls itself "Doc, commit, and naming conventions", but it has no commit or naming entry. Naming is covered by skill K27.
- M0 line 107-108: a "---" rule follows the paragraph with no blank line (minor formatting).
