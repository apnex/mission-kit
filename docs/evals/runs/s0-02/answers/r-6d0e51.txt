### system-boundary.S1
Only the launcher's axioms: A3, A4, A8, A9, A14 (the `any-system` floor, axioms/README.md "Applicability matrix", matching each axiom's `applies-to` frontmatter).
The launcher has no traits: it holds no state (T1), is watched by an operator, so a human sees a failure first and it is not autonomous (T4 test), has one actor (T3), no model (T5), and no reconciled spec (T2); E5 Boundaries: "A one-shot script with no traits is a system, bound by the axioms every system carries."
The service is not bound: A0 says "A system it only composes with, through a contract the change leaves as it was, is not altered, and its axioms do not bind."
The two compose, because the declared session interface is the only crossing and is unchanged (E5: "A launcher that hands sessions to a service through a declared interface composes with it").
(Separately, E5 notes the organisation doing the work is a system whose axioms govern how the change is made and recorded; that is not one of the systems this change alters.)

### system-boundary.S2
Both systems' axioms: the launcher's floor plus the service's, i.e. A1, A3, A4, A5, A6, A7, A8, A9, A10, A13, A14 (not A2, A11, A12).
A0: a change answers to "any system whose contract with it the change alters", and E5: "changing an unversioned interface alters every consumer at once, so the change answers to all of them immediately."
The service is stateful (T1 -> A1), multi-agent (T3 -> A5, A6, A7, A10, A13) and autonomous (T4 -> A7, A10, A13); it is not declarative (no A2) and has no model (no A11, A12), and traits bind by union (T0).
Note A5 binds through `multi-agent` even though there is no model in the loop (A5 `applies-to: [multi-agent, llm-in-the-loop]`).
E5 also says adding versioning to an interface you are changing "is encouraged, not required; if it is not done, the gap is recorded."

### system-boundary.S3
The service's axioms: A1, A3, A4, A5, A6, A7, A8, A9, A10, A13, A14.
E5 Contain: "A module inside a service is a system, and the service contains it, whether or not the module's interfaces are declared. A system has every trait any part it contains has."
A0: a change answers to "the system it modifies, every system containing it"; the module alone brings only the floor, which is a subset.
That the module holds no state on its own does not matter: E5 "Why precision matters" warns that otherwise "a stateful system escapes its own axioms by being described as stateless modules", and T0 repeats it.

### system-boundary.S4
Only the library's own axioms: the floor A3, A4, A8, A9, A14 (axioms/README.md: "a plain library takes `any-system`").
The interface and its behaviour are unchanged, so no consumer's contract is altered (A0); and even a new version "alters no consumer that has not adopted it; each adoption is a change to that consumer, and answers to that consumer's axioms; the component is not altered by being adopted" (E5).
E5 "Why precision matters" names exactly this case as the conflation to avoid: "a small shared library would carry the axioms of every system that uses it".
The caveat in E5 - a declared version range such as "any 2.x" is adoption in advance - does not apply here, because the question says each consumer adopts as its own separate change.

### system-boundary.S5
The union of both units' axioms, which here equals the service's set: A1, A3, A4, A5, A6, A7, A8, A9, A10, A13, A14.
E5 Boundaries: where one unit depends on another and nothing declares the boundary, "they are one system, with the traits of both"; A0 says the same and that "the axioms either unit would bring all bind".
Something else is wrong: "The undeclared dependency is itself a fault against A3" (E5, A0), since the service depends on log lines no interface promises - a "contract in fact, not a declared boundary" (E5 Discriminators).
And your change owns that boundary: "A change that alters what an undeclared neighbour reaches into owns that boundary: declaring and honouring the interface is inside its scope, not optional" (E5).
Per E5, the bypass ends by moving the consumer onto a declared interface, or adjusting the interface to what the consumer legitimately needs (A3).

### system-boundary.S6
It is defined in entities/E5-system.md: "A system is a unit of engineering with a boundary: what is inside it, and the contracts through which anything outside reaches it."
The boundary separates it from a neighbour "only where it is declared and honoured"; otherwise the two are one system for deciding what a change answers to.
"Traits describe a system, and axioms bind it"; systems relate only by contain or compose.
E5 says it is not a repository, deployment unit or process by definition, and is not defined by size or traits.
E6 adds that a component is "a system seen as a part of a larger system that contains it", and A0 hands its definitions of system, contain and compose to E5.

### OBSERVATIONS
- The applicability matrix in axioms/README.md matches each axiom's `applies-to` frontmatter and the trait entries (checked against all fourteen files); I found no inconsistency there.
- It is easy to misread A5 as needing a model: it binds a model-free service through `multi-agent`.
- Launcher autonomy is settled by the T4 test only because the prompt says the operator watches it; "does not restart anything that dies" alone would not decide it.
- S5 rests on "the service parses the very log lines you change". If the change did not alter what the service reads, E5's chaining limit ("only when it alters something B takes from C") hints the merge might not reach, but E5 states that limit for transitive chains, not for a direct dependency. GUESS: the direct undeclared dependency still merges the two for any change.
- T0 says "the six applicability tags", which reads as five traits plus `any-system`; it is correct but could confuse readers, since `any-system` is explicitly not a trait.
- E5 says the organisation is also a system whose axioms bind how work is done. A reader could wrongly add its axioms to S1-S5; E5 says to ask that question separately.
