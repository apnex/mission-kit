### system-boundary.S3
The service's axioms: A1, A3, A4, A5, A6, A7, A8, A9, A10, A13, A14.
E5 Contain: "A module inside a service is a system, and the service contains it, whether or not the module's interfaces are declared", and Discriminators: "changing a module changes the service it sits in".
A0: a change answers to "the system it modifies, every system containing it".
The module being stateless on its own does not help: E5 Boundaries says a change inside one system "answers to the containing system, which has the traits of every part it contains", and E5 "Why precision matters" names the escape it forbids - "a stateful system escapes its own axioms by being described as stateless modules".
The module itself, with no traits, carries only the floor, which is a subset of the above.

### system-boundary.S4
Only the library's axioms: A3, A4, A8, A9, A14 (the floor; it has no trait).
E5: "A versioned contract changes only for the systems that adopt the new version ... each adoption is a change to that consumer, and answers to that consumer's axioms; the component is not altered by being adopted."
The interface and behaviour are unchanged, so no consumer's contract is altered (A0), and the ten consumers' traits do not reach this change.
E5 "Why precision matters" names the error this avoids: otherwise "a small shared library would carry the axioms of every system that uses it".
Exception the corpus states: a consumer bound by a declared version range ("any 2.x") has adopted in advance and is altered by a release within it; the prompt says each adopts as its own separate change, so that exception does not apply here.

### system-boundary.S6
It is defined in entities/E5-system.md: "A system is a unit of engineering with a boundary: what is inside it, and the contracts through which anything outside reaches it."
The boundary separates it from a neighbour "only where it is declared and honoured"; otherwise the two are one system for deciding what a change answers to.
Traits describe a system and axioms bind it; systems relate only by contain or compose (E5).
It is not a repository, deployment unit or process, and is not defined by size or traits (E5 Boundaries).
A component is a system seen as part of a containing system (entities/E6-component.md), and the organisation doing the work is also a system (E5).
