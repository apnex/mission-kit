Trait derivation used throughout (from traits/T1-T5 tests and axioms/README.md "Applicability matrix"):
- Launcher: one operator watching (not T4 autonomous, not T3 multi-agent), no state (not T1), no model (not T5), not reconciled (not T2). No traits, so only the floor `any-system`: A3, A4, A8, A9, A14. entities/E5-system.md: "A one-shot script with no traits is a system, bound by the axioms every system carries."
- Service: T1 stateful (A1), T3 multi-agent (A5, A6, A7, A10, A13), T4 autonomous (A7, A10, A13); not T2, not T5. Union plus floor (traits/README.md "Traits bind by union"): A1, A3, A4, A5, A6, A7, A8, A9, A10, A13, A14. Not A2, A11, A12.

### system-boundary.S1
The launcher's floor axioms only: A3, A4, A8, A9, A14.
axioms/README.md: "a change answers to every system it alters... A system it only composes with, through a contract the change leaves as it was, is not altered, and its axioms do not bind."
The launcher and service compose (E5: "A launcher that hands sessions to a service through a declared interface composes with it"), the interface is unchanged, and nothing bypasses it, so the boundary is "declared and honoured".
The service's axioms (A1, A5, A6, A7, A10, A13) do not bind this change.

### system-boundary.S2
The launcher's axioms and the service's axioms, because the change alters the service's contract: A1, A3, A4, A5, A6, A7, A8, A9, A10, A13, A14 (not A2, A11, A12).
axioms/README.md: a change answers to "any system whose contract with it the change alters"; it touches "any consumer whose contract it alters".
E5: "changing an unversioned interface alters every consumer at once, so the change answers to all of them immediately."
NOT SETTLED: the question does not say whether the session interface is versioned. If it were, and the service stayed on the old version, E5 says publishing a new version "alters no consumer that has not adopted it", and the service's adoption would be its own change under its own axioms.
GUESS: as described ("you change how the launcher hands sessions"), the service is altered at once, so the full service set binds.

### system-boundary.S3
The service's full set: A1, A3, A4, A5, A6, A7, A8, A9, A10, A13, A14.
axioms/README.md: a change answers to "the system it modifies, every system containing it". E5: "A module inside a service is a system, and the service contains it, whether or not the module's interfaces are declared. A system has every trait any part it contains has."
The module being stateless on its own does not matter. E5 "Why precision matters": otherwise "a stateful system escapes its own axioms by being described as stateless modules".
The module's own floor axioms (A3, A4, A8, A9, A14) are already in that set.

### system-boundary.S4
Only the library's floor axioms: A3, A4, A8, A9, A14.
The library has no traits. Its consumers reach it through a declared, versioned interface that is unchanged, so they compose with it and are not altered (axioms/README.md, "not altered, and its axioms do not bind").
E5: "Publishing a new version of an interface alters no consumer that has not adopted it; each adoption is a change to that consumer, and answers to that consumer's axioms; the component is not altered by being adopted."
E5 "Why precision matters" names this case: otherwise "a small shared library would carry the axioms of every system that uses it".
Caveat from E5: "A declared version range - any 2.x - is adoption in advance: a release within it alters every consumer bound by the range". The question says each consumer adopts as a separate change, so I take it that no range binds them. If one did, that consumer's axioms would bind the release.

### system-boundary.S5
The launcher and service count as one system with the traits of both, so the full service set binds: A1, A3, A4, A5, A6, A7, A8, A9, A10, A13, A14.
E5 Boundaries: "Where one unit depends on another and nothing declares the boundary between them ... they are one system, with the traits of both." axioms/README.md: "the axioms either unit would bring all bind".
Something else is wrong. The undeclared dependency "is itself a fault against A3, which requires units to interact only through declared contracts" (E5; A3 "Air-Gap Principle").
The change also owns the fix. E5: "A change that alters what an undeclared neighbour reaches into owns that boundary: declaring and honouring the interface is inside its scope, not optional."
Note that "one system" here is a rule for deciding what binds. It does not declare a larger containing system, so it does not contradict the premise.
NOT SETTLED: whether the service actually parses the log lines you changed. If the format change does not touch what it parses, the change may not "alter" that dependency. The merge rule in E5 is based on dependency with no declared boundary, so GUESS: the full set still binds.

### system-boundary.S6
Defined in entities/E5-system.md: "A system is a unit of engineering with a boundary: what is inside it, and the contracts through which anything outside reaches it."
The boundary separates it from a neighbour "only where it is declared and honoured". Traits describe a system, and axioms bind it.
Systems relate in exactly two ways: contain and compose. Undeclared dependency means "one system" for binding purposes.
E5 also says a system is not "a repository, a deployment unit or a process by definition" and is "Not defined by size or by traits". It says "The organisation doing the work is a system", and the organisation's axioms govern how a change is made, separate from the product systems the change alters.
entities/E6-component.md adds that a component is "a system seen as a part of a containing system".

### OBSERVATIONS
- S2: the corpus makes the answer depend on whether an interface is versioned (E5), and the scenario does not say. I treated the interface as unversioned / adopted at once.
- S4: the "declared version range" rule in E5 says a release within a range alters bound consumers even when behaviour is unchanged. The question's "each adopts as its own separate change" seems to rule that out, but this is inferred.
- S5: E5's merge rule depends on dependency, while axioms/README.md frames binding as "every system it alters". If the changed log lines are not the ones the service parses, the two framings could disagree. The corpus answers this only for the chaining case ("only when it alters something B takes from C", which applies to units in different systems).
- E5's statement that the organisation is a system means the organisation's own axioms also govern how each change is made. I left them out of the answers because E5 says they "are not one of the systems the change alters".
- Axiom applies-to frontmatter matches the applicability matrix in axioms/README.md and the trait entries. I found no inconsistency there.
