### system-boundary.S1
Only the launcher's axioms: A3, A4, A8, A9, A14 (the `any-system` floor, axioms/README.md "Applicability matrix").
The launcher has no traits under T1-T5: it holds no state (T1), runs one-shot with no reconciliation (T2), has one actor (T3), has an operator watching (T4 test: "would a human see it before the system acted on the failure?" - yes, so not autonomous), and has no model (T5); E5 Boundaries: "A one-shot script with no traits is a system, bound by the axioms every system carries."
A0 "What brings an axiom into force": "A system it only composes with, through a contract the change leaves as it was, is not altered, and its axioms do not bind."
The launcher and service compose (E5: "A launcher that hands sessions to a service through a declared interface composes with it"), and the interface is unchanged and is the only crossing, so the service's axioms do not bind.
Separately, E5 says the organisation's own axioms govern how the change is made and recorded, but they are "not one of the systems the change alters".

### system-boundary.S2
The union of the launcher's and the service's axioms: A1, A3, A4, A5, A6, A7, A8, A9, A10, A13, A14 (not A2, A11, A12).
A0: a change answers to "the system it modifies ... and any system whose contract with it the change alters" - changing the declared interface alters the contract, so the service is altered too (E6 blast radius: "an adjacent component only if the interface between them changes").
The service is stateful (T1 -> A1), multi-agent (T3 -> A5, A6, A7, A10, A13) and autonomous (T4 -> A7, A10, A13), plus the floor A3, A4, A8, A9, A14; it is not declarative (no A2) and has no model (no A11, A12) (axiom `applies-to` frontmatter; T0 "Traits bind by union").
Caveat: if the interface were versioned, E5 says the service is altered only when it adopts the new version, and that adoption is the change that answers to the service's axioms; the question does not say it is versioned, so I treat it as unversioned.

### system-boundary.S3
The service's axioms: A1, A3, A4, A5, A6, A7, A8, A9, A10, A13, A14.
E5 "Contain": "A module inside a service is a system, and the service contains it, whether or not the module's interfaces are declared. A system has every trait any part it contains has."
A0: a change answers to "the system it modifies, every system containing it".
So the module's own statelessness does not limit what binds. E5 "Why precision matters" names this failure: "a stateful system escapes its own axioms by being described as stateless modules, each of which passes on its own." T0 says the same thing.

### system-boundary.S4
Only the library's own axioms, the floor: A3, A4, A8, A9, A14.
The library has no traits. The consumers compose with it through a declared, versioned interface, and the change leaves that interface and its behaviour unchanged, so no consumer's contract is altered (A0).
E5: "Publishing a new version of an interface alters no consumer that has not adopted it; each adoption is a change to that consumer, and answers to that consumer's axioms; the component is not altered by being adopted."
E5 "Why precision matters" rules out the opposite reading: otherwise "a small shared library would carry the axioms of every system that uses it".
Limit: E5 says a declared version range ("any 2.x") is "adoption in advance", which would make a release alter every consumer bound by the range. The question says each consumer adopts separately, so I assume no range is in place.

### system-boundary.S5
The launcher and the service count as one system with the traits of both, so the change answers to A1, A3, A4, A5, A6, A7, A8, A9, A10, A13, A14.
E5 Boundaries: "Where one unit depends on another and nothing declares the boundary between them ... they are one system, with the traits of both"; A0 says the same ("the axioms either unit would bring all bind").
Something else is wrong: the undeclared dependency is itself an A3 fault (A0; E5; A3 "Air-Gap Principle": "units interact only through declared adapters and contracts").
E5: "A change that alters what an undeclared neighbour reaches into owns that boundary: declaring and honouring the interface is inside its scope, not optional." The fix is to declare the interface and move the service's parsing onto it.
NOT SETTLED: whether the service parses these particular log lines. GUESS: the one-system merge applies either way (E5 merges on the dependency itself), but the duty to "own that boundary" applies only if the log lines are part of what the service parses.

### system-boundary.S6
Defined in entities/E5-system.md: "A system is a unit of engineering with a boundary: what is inside it, and the contracts through which anything outside reaches it."
The boundary separates it from a neighbour "only where it is declared and honoured"; where it is not, the two are one system for binding.
"Traits describe a system, and axioms bind it." Systems relate in exactly two ways, contain and compose.
E5 also says a system is not by definition a repository, deployment unit or process, and is not defined by size or traits. E6 adds that a component is "a system seen as a part of a larger system that contains it".

### OBSERVATIONS
- S5: E5 merges two units whenever "one unit depends on another" with no declared boundary, but says a change "owns that boundary" only when it "alters what an undeclared neighbour reaches into". The prompt does not say whether the service's parsing includes the log lines, so the merge seems settled and the ownership duty is not.
- S2: neither the prompt nor the corpus says whether the launcher-service session interface is versioned, and E5's versioning rule would change the answer (the service is altered only when it adopts the new version).
- E5 treats the organisation as a system whose axioms govern how a change is made. That is a second set of obligations alongside the product answers above, which a reader could confuse with them; E5 does say to ask the two questions separately.
- The trait classifications rest on the prompt's descriptions applied to the T1-T5 tests (for example, "one operator ... watches it" -> not autonomous). These are inferences, not text from the corpus.
