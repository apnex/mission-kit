### design-rulings.R1
Your change has to declare an interface between T and N and get N using it. That work is inside your change's scope, not an optional extra. entities/E5-system.md (Boundaries) says: "A change that alters what an undeclared neighbour reaches into owns that boundary: declaring and honouring the interface is inside its scope, not optional." "Honoured" means the interface is "the only way the neighbour reaches it" (E5 Definition). So N must go through it, not just have it written down next to N's existing calls. Until that is done, N and T are "one system, with the traits of both" (E5; axioms/README.md "What brings an axiom into force"), so your change answers to the axioms N's side brings as well as T's. The undeclared reach is itself an A3 fault (A3 Air-Gap Principle). A3 "Bypass as Signal" and E5 "Declared against honoured" say how it should end: check the interface against T's duty, then either move N onto the interface or adjust the interface to what N legitimately needs.

### design-rulings.R2
(1) No. E5 Boundaries says: "The merge chains only through what a change can reach: if A reaches into B and B into C, a change to A is one system with C only when it alters something B takes from C." A change used only by A alters nothing that B takes from C, so C's axioms do not bind it. The A-to-B dependency is a separate matter. It is undeclared, so for binding A is still one system with B (E6 Definition: "one system with whatever reaches into it or it reaches into"). (2) Yes. Altering data that B takes from C is exactly the case E5 names, so the merge chains through to C and C's axioms bind too, because the merged units carry "the traits of both" (E5). Per E5, your change also owns the undeclared boundaries it alters, so declaring and honouring them is in scope. GUESS: the question does not say which module the change sits in. The ruling is the same either way, because E5 makes "alters something B takes from C" the test.

### design-rulings.R3
Yes on both counts. The service is stateful: the module "writes something it will later read back" and acts on it, which passes the T1 test (traits/T1-stateful.md). E5 Definition says "A system has every trait any part it contains has", and traits/README.md says "a service with one stateful module is stateful, so a stateful system cannot escape its axioms by being described as stateless parts." A0 says "a change answers to every system it alters. That is the system it modifies, every system containing it...". Changing the stateless module changes the service that contains it (E5: "changing a module changes the service it sits in"), and A1 (applies-to: stateful) is in force for that service. So A1 binds your change in A0's two directions: it must not move the service away from A1's limit, and it should move it toward the limit as far as the change's scope allows. NOT SETTLED: what A1 concretely demands of a change to a module that holds no state. GUESS: mostly that the change adds no private or opaque truth (A1 Mandate) and keeps the module stateless (A1 Mechanics).

### design-rulings.R4
Yes. A1 binds the team's records, not the tool. E5 says the organisation doing the work is a system, and it covers this case directly: "A stateless product built by a team that keeps records it relies on has `A1` binding the team's records, not the product." Those records pass the T1 test because they are written, read back and relied on (T1). That makes the organisation stateful, and A1 applies-to [stateful] (A1 frontmatter; A0 matrix). The CLI is stateless and has no model in the loop. It does not meet A1's only tag, so A1 does not bind it. E5 says axioms bind "how the work is done, separately from what is built".

### design-rulings.R5
What is mandatory: your feature must not add to the tangle ("new work never repeats a gap the axiom names", A0). If the feature modifies the tangled code, it must also close as much of that gap as the touch allows (A0). The split itself is encouraged, not mandated. A3 Composable by Default says "within the unit's own duty, fix it, fracture it, re-cut its seams and recompose it so it makes better sense for every consumer downstream - as a change of its own." A0 says you are "expected to weigh doing it, not merely permitted to". Do it as a separate change. Because K's interface is unversioned, that change alters all three consumers at once and answers to each of their axioms (A0; E6 Blast radius: "only on adoption" applies only to versioned interfaces). Decide with A14's tangent discipline: near payback, the yield captured, and no significant distraction from the feature. If the split fails that test, record it with evidence and a revival trigger (RU3). Either way the gap is recorded (A0). NOT SETTLED: whether the tangle counts as "touched" depends on whether the feature modifies the tangled code, because A0 says code that "merely sits beside it, in the same file or module, is not touched".

### design-rulings.R6
All ten. E5 says: "A declared version range - *any 2.x* - is adoption in advance: a release within it alters every consumer bound by the range, whether or not the consumer's own files change." 2.4 changes the behaviour the declared interface documents, so it changes the contract each consumer relies on. Using only the declared interface does not protect a consumer here. It protects a consumer only through "a contract the change leaves as it was" (A0), and this contract has changed. So publishing 2.4 answers to all ten consumers' axioms (A0: "any system whose contract with it the change alters"). NOT SETTLED: whether a consumer whose lockfile pins an earlier 2.x counts as "bound by the range". GUESS: a lockfile would mean that consumer has not adopted 2.4 yet.

### OBSERVATIONS
- E5's chaining rule ("a change to A is one system with C only when it alters something B takes from C") does not explain how a change confined to A could alter what B takes from C. R2(2) also leaves unclear where the change sits.
- A0 says a change "touches what it modifies" but code "in the same file or module" that merely sits beside it is not touched. So for a tangled module, whether the tangle is "touched" (fix mandatory) or adjacent (fix optional) turns on what exactly the change edits, and the corpus gives no finer test.
- A3 "Bypass as Signal" talks about reaching past a *declared* interface. R1 involves no declared interface at all, so the evaluation step applies only by analogy through E5's "owns that boundary" sentence.
- E5 and A0 both say an undeclared dependency merges units into one system. Whether the A-to-B merge in R2(1) still binds a change used only inside A depends on reading E5's chaining qualifier as limiting only the extension to C, not the A-to-B merge itself. I read it that way, but the text does not say so explicitly.
- A1 gives no specific guidance for a change to a stateless part of a stateful system beyond A0's general direction rule.
