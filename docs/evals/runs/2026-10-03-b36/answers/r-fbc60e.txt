### design-rulings.R1
N and T are one system for binding: "where one unit depends on another across a boundary nobody declared ... the two are one system for deciding what a change answers to" (entities/E5-system.md, Definition; axioms/README.md, "What brings an axiom into force"). The function N calls is "a contract in fact, not a declared boundary - and a change to it reaches across" (E5, Discriminators), so your change alters N and answers to the axioms either unit brings (A0: "the axioms either unit would bring all bind"). The undeclared reach "is itself a fault under A3" (A0; E5 Boundaries), and A3's Air-Gap Principle says "units interact only through declared adapters and contracts". Because N is a consumer whose contract you alter, N is inside your change's scope (A0: "A change touches ... any consumer whose contract it alters"). Inside scope the direction rule applies: "new work never repeats a gap the axiom names, and work that touches a gap closes as much of it as the touch allows" (A0). So your change must not add new undeclared reach, and it should close the gap as far as the touch allows. E5 names the remedy: "Declaring the boundary, and moving the dependency onto it, is what makes them two again". NOT SETTLED: how much closing "the touch allows" here (declare only the function you change, or all of T's surface N uses). GUESS: at minimum, declare the altered function as an interface and move N's call onto it, and record the rest of N's reach with a revival trigger (rules/RU3).

### design-rulings.R2
(1) A depends on B with no declared boundary, so A and B are one system "with the traits of both" (E5 Boundaries; A0), and B and C are one system for the same reason. The corpus states this collapse only for direct pairs, for example E6's blast radius: "any unit that reaches it, or that it reaches, with no declared interface" (entities/E6-component.md). It never says whether the collapse is transitive, and your change does not alter C. So whether the A-B-C chain alone makes C's axioms bind is NOT SETTLED. Separately, all three modules sit in the service, and a change answers to "every system containing it" (A0), so whatever traits C gives the service bind through containment anyway. GUESS: if C's traits are traits of the service (for example C is stateful, so the service is), then in practice yes. (2) Yes. You cannot alter that data without changing B or C. If you change C, you modify C. If you change B, then B and C are one system and "the axioms either unit would bring all bind" (A0). Either way A's axioms bind as well, because A's contract in fact is altered (E5, "A declared boundary against an assumed one").

### design-rulings.R3
Yes, the service is stateful. T1 (traits/T1-stateful.md) defines the test as "Does the system write something it will later read back, and would anything act differently if that record were wrong?", and the service passes it through its one module. A trait's "test is applied to a system, never to a task" (E5), and E5 warns against the opposite reading: "a stateful system escapes its own axioms by being described as stateless modules, each of which passes on its own". The service contains your module (E5: "A module inside a service is a system, and the service contains it, whether or not the module's interfaces are declared"). Your change therefore alters the service, and "a change answers to every system it alters. That is the system it modifies, every system containing it" (A0). So A1 binds your change, because A1 applies to `stateful` (axioms/A1). What it asks is the direction rule: do not move the service away from the A1 limit, for example by giving the stateless module "private, opaque, or transient truth" (A1 Mandate), and close any A1 gap the change touches. A1's Mechanics already expect acting components to be stateless ("read, transform, and write back").

### design-rulings.R4
A1 does not bind the tool itself. A1 applies only to `stateful` (axioms/A1), and the tool is stateless, so it is bound only by the `any-system` floor (A3, A4, A8, A9, A14; A0 applicability matrix). The team's work system is a different matter. It is multi-agent ("agents, people, or both", where "one actor's output becomes another's input"; traits/T3). It is also stateful: it writes records it reads back and relies on, and T1 names this case as "Stateful, often missed: an agent that keeps notes for its next session". So A1 binds the team's records and coordination system, and with it T3's axioms (A5, A6, A7, A10, A13). The domain split supports keeping the two apart: the product (D1) and the coordination substrate (D5) are separate surfaces (domains/README.md). NOT SETTLED: the corpus never says outright that a team's work organisation is a "system" in E5's sense. GUESS: it is, because it is "a unit of engineering with a boundary". On that reading, changes to the tool's code answer to A1 only if they alter those records.

### design-rulings.R5
The tangle is an A3 gap: "god objects, spaghetti coupling and dual-purpose modules", and "Law of One - a module does exactly one thing" (axioms/A3). Inside your feature's scope, the feature must not add to the tangle, and if it touches the tangled code it must close as much of it as the touch allows. A3 says "a change short of it adds none of them, and removes what it touches", and A0 says the same. Code "that merely sits beside it, in the same file or module, is not touched" (A0), so splitting parts the feature does not modify is not mandated. The split is within K's duty, so it can stay internal (E6: descend an altitude and K is "a containing system in turn"). Redesigning K's interface is a different change. Because the interface is unversioned, changing it alters all three consumers at once, with no adoption step (E5 versioned clause, read in reverse; A0: "if it changes a component's interface, its consumers are altered too"). That makes it "considered, never mandated". If A14's tangent discipline supports it, do it "as a change of its own" that answers to all three consumers. Otherwise record it with its evidence and a revival trigger (RU3). "Either way the gap is recorded" (A0). GUESS: the missing version is itself an A3 gap ("interfaces are explicit, versioned contracts", Semantic Bit-Masking), so any change to the interface should version it.

### design-rulings.R6
E5 says: "Publishing a new version of an interface alters no consumer that has not adopted it; each adoption is a change to that consumer" (E5 Discriminators). E6 says the same: a change reaches an adjacent component "for a versioned interface, only on adoption". Read literally, publishing 2.4 alters no consumer by itself. Each consumer is altered when it adopts 2.4. NOT SETTLED: the corpus does not say whether a floating range like "any 2.x" counts as adopting 2.4 in advance, or whether adoption happens only when a consumer re-resolves its dependencies. The two readings disagree. Under the first, all ten consumers are altered as soon as they resolve. Under the second, only those that pick up 2.4. GUESS: a floating range is a declared acceptance of whatever 2.x delivers, so the ten are altered as each one resolves 2.4, and this does not need any change of their own. GUESS: changing documented behaviour inside a range that promises compatibility is itself an A3 fault on L's side ("bit-perfect ... both sides agree on the exact shape").

### OBSERVATIONS
- E5's versioned-contract clause assumes adoption is an explicit act by the consumer. It does not cover floating ranges or auto-resolution, which decides R6.
- The undeclared-dependency collapse (E5, A0, E6 blast radius) is stated only for direct pairs. Transitivity (R2.1) is never addressed.
- A3's Bypass as Signal covers reaching past a declared interface. It does not cover the case with no interface at all (R1), which is covered only by the Air-Gap Principle and the E5/A0 collapse rule.
- A0 defines "adjacent" between components. For a gap inside the same component that the change does not touch (R5), it is unclear whether the gap is "adjacent" (so opportunistic) or simply out of scope.
- The corpus never says whether the work organisation or team counts as a system with traits, though T1's examples and the D5 domain imply it does (R4).
