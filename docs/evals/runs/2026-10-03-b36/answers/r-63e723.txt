### design-rulings.R1
Because N reaches T with no declared interface, N and T count as "one system, with the traits of both" for binding purposes (entities/E5-system.md, Boundaries; axioms/README.md: "nothing shows the change is contained, so the two are one system ... and the axioms either unit would bring all bind"). So your change answers to N's axioms as well as T's. N is also touched: E5 says behaviour another unit depends on without a declaration "is a contract in fact ... and a change to it reaches across", and A0 says a change touches "any consumer whose contract it alters".
The undeclared dependency "is itself a fault under A3" (A0; A3 Air-Gap Principle: "no unit reaches into another's internals"). Under A0's direction rule, "new work never repeats a gap the axiom names, and work that touches a gap closes as much of it as the touch allows". So the change must not deepen the reach. It should close as much as it can, and E5 names the fix: "Declaring the boundary, and moving the dependency onto it, is what makes them two again". Leaving the gap unrecorded is not allowed either: "Passing it silently is what the axiom forbids" (A0).
NOT SETTLED: how much closure "as much as the touch allows" requires here, that is, whether this change must fully declare the interface and move N onto it. GUESS: at least declare the function N calls as T's interface and move N onto it, or record the rest with a revival trigger (RU3).

### design-rulings.R2
(1) Your change modifies A and alters no contract that B or C rely on. A and B are one system because A reaches into B undeclared (E5; A0), so B's axioms bind. The corpus states this pairwise ("the two are one system"; E6 blast radius: "any unit that reaches it, or that it reaches, with no declared interface") and never says whether the one-system rule chains from A through B to C. NOT SETTLED for the chain. GUESS: no, C's axioms do not bind through the chain, because A neither reaches C nor alters anything C depends on. Caveat (inferred): the change does answer to the containing service (A0: "every system containing it"). If C's traits make the service itself, for example, stateful, those axioms bind through containment anyway, not through the chain.
(2) Yes. The altered data comes from C and B consumes it through an undeclared contract in fact (E5: "a change to it reaches across"). So the change alters C, or C's contract with B, and B and C are one system "with the traits of both" (E5; A0). C's axioms bind, and so do B's and A's, because each consumer's contract in fact is altered.

### design-rulings.R3
Yes, the service is stateful. The module passes the T1 test: "Does the system write something it will later read back, and would anything act differently if that record were wrong?" (traits/T1-stateful.md). The service contains that module, and E5 warns against the opposite reading: "a stateful system escapes its own axioms by being described as stateless modules, each of which passes on its own". (Inferred: a system that contains a state-writing module itself writes and reads back that state.)
A1 binds your change. A0: "a change answers to every system it alters. That is the system it modifies, every system containing it", and A1 is in force for any stateful system (applies-to: [stateful]). How far the change must move toward A1 depends on its scope (A0). At minimum it must not move the service away from the limit, for example by giving the stateless module private or transient truth (A1 Mandate; Mechanics: components "are stateless: they read, transform, and write back").

### design-rulings.R4
Traits are tested on a system, "never ... a task" (E5). The tool is stateless, has no model and does not pass work between actors internally, so A1 (applies-to: [stateful]) does not bind the tool. Only the any-system floor binds it: A3, A4, A8, A9, A14 (axioms/README.md matrix).
A1 does bind the team's own working system. Its records are written, read back and relied on, which passes the T1 test, and T1 lists "an agent that keeps notes for its next session" as stateful. Work also crosses between independent actors, including a human, so it is multi-agent too (T3). So the records must move toward A1: one sovereign, queryable, durable store with no private or opaque truth (A1 Mandate, Success signals 1-2).
NOT SETTLED: the corpus never says outright that a development team plus its records is an E5 "system" separate from the tool it builds, though A0's "an organisation of one" discussion and T1's notes example point that way. GUESS: changes to the tool's code answer only to the tool's axioms unless they also alter the team's records.

### design-rulings.R5
A3 forbids dual-purpose units ("Law of One"; Mandate: "a change short of it adds none of them, and removes what it touches"). Under A0, your feature must not add to the tangle, and if it modifies the tangled code it must untangle "as much of it as the touch allows". If the feature does not modify that code, the tangle is not in scope: "code that merely sits beside it, in the same file or module, is not touched" (A0). It is also not "adjacent", because adjacency needs a shared declared interface, and "nearby" is not enough (E6).
Beyond scope, "improvement is considered, never mandated". A gap that fails the opportunistic test is "recorded with its evidence and a revival trigger (RU3) rather than closed", and bigger choices go to the director (A0; R4; AR3). Any split is "made as a change of its own". Because it changes K's unversioned interface, it alters all three consumers right away, not only on adoption (E6 blast radius; A0: "if it changes a component's interface, its consumers are altered too"), so it answers to each consumer's axioms.
NOT SETTLED: whether a gap inside the touched component's own internals can qualify for opportunistic closure, since the adjacency test is written for neighbouring components. GUESS: record it with a revival trigger, or do it as a separate change answering to all three consumers.

### design-rulings.R6
E5: "Publishing a new version of an interface alters no consumer that has not adopted it; each adoption is a change to that consumer". On that text, publishing 2.4 by itself alters none of the ten. Each consumer is altered when it adopts 2.4, and that adoption answers to the consumer's own axioms.
NOT SETTLED: the corpus never discusses floating ranges, so it does not say whether "any 2.x" counts as adopting in advance or whether picking up 2.4 at the next resolve counts as an adoption. It also does not say whether changing documented behaviour inside 2.x alters the declared "2.x" contract itself, in which case all ten would be altered as consumers "whose contract it alters" (A0).
GUESS: every consumer that resolves 2.4 is altered, with no deliberate adoption step. Changing documented behaviour inside a range the consumers trust is arguably an unversioned interface change, which would reach all ten (E6: "for a versioned interface, only on adoption").

### OBSERVATIONS
- The corpus states the one-system collapse for undeclared dependencies pairwise (E5, A0, E6). It never says whether the collapse is transitive across chains (R2), and containment by a shared parent partly blurs the question.
- A3 "Bypass as Signal" and E6 "detected crossing" are written for reaching past a declared interface. Neither says what is triggered when no interface exists at all (R1).
- A0 says closure goes "as much ... as the touch allows" but gives no measure of what the touch allows (R1, R5).
- A0's adjacency and opportunistic-improvement test is written for neighbouring components. It is unclear how it applies to a gap inside the internals of the component the change itself modifies, given the line "code that merely sits beside it ... is not touched" (R5).
- E5's versioned-contract rule assumes a deliberate adoption act. Floating ranges and documented-behaviour changes inside a version range are not covered (R6).
- T0 says traits describe "the system an organisation is working on". Whether the organisation's own work and records system is an E5 system the axioms bind is only implied (by A0's "organisation of one" and T1's notes example), never stated (R4).
