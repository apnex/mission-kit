### boundary-bypass.B1
Yes. A declared interface "separates two units only for the neighbours that use it", and a unit that reaches past it by "calling internals ... stays one system with it" (entities/E5-system.md, "Declared against honoured"). axioms/README.md (A0, "What brings an axiom into force") says that where a boundary is "one written and reached past", the two "are one system with the traits of both, and the axioms either unit would bring all bind". So a change to T's internals answers to O's axioms, as well as to T's and to the containing service's ("every system containing it", A0). On the bypass: A3 says it "is a fault in the consumer and a signal about the interface". A detected bypass "triggers an evaluation of the interface against the component's duty and its vision, ending in the consumer being moved onto the interface or the interface being adjusted" (axioms/A3-sovereign-composition.md, "Bypass as Signal"; also entities/E6-component.md, "Boundary against directory"). Whether your own change must close the bypass is NOT SETTLED. GUESS: E5 calls such a dependency "a contract in fact" whose change "reaches across", so O is probably touched. A0 then asks that "work that touches a gap closes as much of it as the touch allows", or that the gap is at least recorded with a revival trigger (M5).

### boundary-bypass.B2
It answers to O, not P (as well as to T and the containing service). E5 says "The separation is per pair: a neighbour that uses the interface composes with the unit, while one that bypasses it does not" (entities/E5-system.md). A0 says "A system it only composes with, through a contract the change leaves as it was, is not altered, and its axioms do not bind". The change leaves T's interface unchanged, so P's own axioms do not bind it. O bypasses, so O is one system with T and its axioms bind (A0, "What brings an axiom into force"). E6's blast-radius row agrees: a change reaches "an adjacent component only if the interface between them changes ... and any unit that reaches it ... with no declared interface" (entities/E6-component.md, "Why precision matters").

### boundary-bypass.B3
No. E5 says: "declaring an interface and leaving the bypass in place separates nothing" (entities/E5-system.md, "Declared against honoured"). E6 says "Declaring its interfaces, and its neighbours using them, is what separates it" (entities/E6-component.md, Definition). E5 Boundaries says the same: "Declaring the boundary, and moving the dependency onto it, is what makes them two again". So T and O are still one system for binding. Declaring the interface does change what O's calls count as. Before, they were an undeclared dependency, which is also an A3 fault (E5, Boundaries). Now they are a bypass of a declared interface, and that brings in A3's "Bypass as Signal" evaluation. A3 calls this "a detected bypass", and the corpus does not say whether declaring the interface counts as detecting it. That point is NOT SETTLED.

### boundary-bypass.B4
Evaluate T's interface against T's duty and its vision. The evaluation ends either with the consumers moved onto the interface or with the interface adjusted (axioms/A3-sovereign-composition.md, "Bypass as Signal"). A3 success signal 5 asks that each detected violation be "evaluated against the component's duty rather than only corrected in the consumer". E6 says a detected crossing "is a signal about the interface as well as a fault in the consumer". Until that resolves, each bypassing component "remain[s] one system" with T for what a change answers to (A3; A0). If the interface is adjusted, that change "answers to every system it alters", including the consumers whose contract it changes (A0). If the work falls outside the current change's scope, record it "with its evidence and a revival trigger (M5)" instead of passing it silently, because larger choices of what to do next belong to the director (A0; R4, AR3). How much weight "several" bypassers carry, as opposed to one, is NOT SETTLED. GUESS: several bypassers make it more likely that the interface "falls short of the component's duty".

### OBSERVATIONS
- A3 "Bypass as Signal" evaluates the interface "against the component's duty and its vision". No entry I read defines a component-level vision (AR6 is a programme vision), so "its vision" is ambiguous.
- A3 says the consumer "has not signalled the change it needs", but no signalling mechanism, owner or work-type for running the bypass evaluation is named. The corpus does not say who runs the evaluation or when.
- A3 is triggered by a "detected" bypass, but the corpus does not say whether its force depends on detection, or whether an undetected bypass still collapses the two units. E5 and A0 imply it does collapse them regardless.
- In these questions O and T are both contained by the same service, so the service's axioms bind the change anyway. The one-system collapse adds only O's own axioms as a system. The corpus does not separately spell out how the collapse interacts with containment.
- Whether a bypass consumer counts as "touched" in A0's scope rule ("any consumer whose contract it alters") hinges on E5's "contract in fact". This is a two-step inference, not a stated rule.
- A3's mandate and mechanics say "module"/"unit", while E5 and E6 use "system"/"component". The mapping is implied, not stated in A3.
- INDEX.md says links resolve against GitHub when there is no local checkout. That conflicts with the instruction to read only this corpus copy, but it did not affect the answers.
