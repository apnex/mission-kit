### OBSERVATIONS
- W0 constraint 2 says that if the roster collapses attester and executor, "fail the seed or downgrade to kind:review" (W8 repeats this, despite "do not restate it"). Constraint 9 and R0 say "Same-agent review is never a valid degradation". If kind:review by the same agent is allowed, the two conflict, and the text does not say who performs the downgraded review.
- Nothing mechanically checks the trait bodies' "Axioms it brings into force" lists against applies-to. tools/check-traits.mjs checks only that the applies-to enum and the traits/ set match. The lists agree today, but they are duplicated and can drift, which is the "two lists of one thing" problem tools/README.md names.
- Domain lists omit pairings that work-types declare (measured from the frontmatter). D1 omits W10, W11, W12; D2 omits W1, W2, W4, W6, W10, W12, W14; D3 omits W5, W6, W7, W10, W12, W14, W26; D4 omits W10; D5 omits W10, W12, W14; D6 omits W8, W12. D0 acknowledges this ("every disagreement an omission on the domain side").
- R3's engagement-mode list (W8, W9, W10, W11, W12, W13) omits W16, W20, W22 and W25, which all name verifier in roleEligibility.
- D1 cites A1 with no qualification. Read alone, it suggests A1 constrains all delivery-code work whatever the system's traits, which conflicts with A0's "only field" rule. D0 also says "A domain cites the axioms it must satisfy", which raises the same ambiguity.
- W7 is defined as shipping "a landed change to the estate/channel". Applying a migration to records reaches it only through D7's analogy, and no work-type names applying data changes explicitly.
- T4's test is hard to apply to an interactive CLI or a "long-running service", because the test depends on human supervision, which descriptions often leave unstated.
- INDEX.md tells readers to resolve links against GitHub. This corpus copy is local, so I resolved links locally.
