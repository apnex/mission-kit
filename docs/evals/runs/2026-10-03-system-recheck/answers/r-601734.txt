### system-boundary.S1
Only the launcher's axioms apply, and those are the five floor axioms: A3, A4, A8, A9 and A14 (axioms/README.md, applicability matrix, `any-system` row).
A0 says "a change answers to every system it alters... A system it only composes with, through a contract the change leaves as it was, is not altered, and its axioms do not bind" (axioms/README.md, "What brings an axiom into force").
The launcher and the service compose: "A launcher that hands sessions to a service through a declared interface composes with it" (entities/E5-system.md, Definition).
The interface is declared and honoured, because nothing else crosses it, so the service's axioms do not bind this change.
The launcher has none of the traits: it is watched, so not autonomous (T4); it has one actor, so not multi-agent (T3); and it holds no state and has no model, so not T1 or T5.
E5 says "A one-shot script with no traits is a system, bound by the axioms every system carries" (E5, Boundaries).
No containing system is declared, so no containing system adds axioms.

### system-boundary.S2
This change answers to the union of both systems' axioms: A1, A3, A4, A5, A6, A7, A8, A9, A10, A13 and A14 (11 of the 14).
A0 says a change answers to "any system whose contract with it the change alters" (axioms/README.md), and E6 says a change reaches "an adjacent component only if the interface between them changes" (entities/E6-component.md, blast radius).
Launcher: floor only (A3, A4, A8, A9, A14).
Service: T1 stateful (A1), T3 multi-agent (A5, A6, A7, A10, A13) and T4 autonomous (A7, A10, A13), plus the floor.
A2 (declarative), A11 and A12 (llm-in-the-loop) do not bind, because neither system has those traits.
Caveat: E5 says "Publishing a new version of an interface alters no consumer that has not adopted it" (E5, Discriminators).
NOT SETTLED by the question is whether this interface is versioned. GUESS: it is not, so the service is altered now; if it is versioned, the service's axioms bind only the change that adopts the new version.

### system-boundary.S3
The service's full set binds: A1, A3, A4, A5, A6, A7, A8, A9, A10, A13 and A14.
A0 says a change answers to "the system it modifies, every system containing it" (axioms/README.md).
E5 says "A module inside a service is a system, and the service contains it, whether or not the module's interfaces are declared", and "changing a module changes the service it sits in" (entities/E5-system.md).
The module on its own has no traits and would carry only the floor, but that does not limit what binds the change.
E5 names the error directly: "a stateful system escapes its own axioms by being described as stateless modules, each of which passes on its own" (E5, Why precision matters).
How much the change must improve is set by its scope, meaning what it modifies or newly depends on. It is not set by the whole service (A0, "How far a change must move").

### system-boundary.S4
Only the library's axioms apply, which are the five floor axioms: A3, A4, A8, A9 and A14 (the library has no traits; axioms/README.md matrix).
The interface and its behaviour are unchanged, so no consumer's contract is altered, and the consumers compose with the library rather than contain it (E5, Compose).
E5 says "each adoption is a change to that consumer, and answers to that consumer's axioms; the component is not altered by being adopted" (entities/E5-system.md, Discriminators).
E5 also rejects the opposite reading: "a small shared library would carry the axioms of every system that uses it, and the most-reused code would carry the most obligations" (E5, Why precision matters).
So when each of the ten consumers adopts the new version, that adoption is a separate change bound by that consumer's own axioms (for example A1 or A5 to A13 where they apply). Those axioms do not bind this change.
This holds only while no consumer depends on undeclared behaviour. "Behaviour another unit depends on without any declaration is a contract in fact... a change to it reaches across" (E5).

### system-boundary.S5
The launcher and the service count as one system with the traits of both, so all 11 apply: A1, A3, A4, A5, A6, A7, A8, A9, A10, A13 and A14.
E5: "Where one unit depends on another and nothing declares the boundary between them... they are one system, with the traits of both" (entities/E5-system.md, Boundaries). A0 says the same (axioms/README.md: "the axioms either unit would bring all bind").
The log format is "a contract in fact, not a declared boundary - and a change to it reaches across" (E5, Discriminators), so the change may break the service's parsing.
Something else is wrong: "The undeclared dependency is itself a fault against A3" (E5). A3's Air-Gap Principle says "units interact only through declared adapters and contracts" (axioms/A3-sovereign-composition.md).
Your change modifies the exact output the service parses, so it touches that gap. A0 requires that "work that touches a gap closes as much of it as the touch allows", and "Passing it silently is what the axiom forbids" (axioms/README.md).
The remedy is in E5: "Declaring the boundary, and moving the dependency onto it, is what makes them two again".
GUESS: if closing the gap fully is out of scope, at least record the gap with evidence and a revival trigger (M5) rather than ship the format change silently.

### system-boundary.S6
A system is defined in entities/E5-system.md: "a unit of engineering with a boundary: what is inside it, and the contracts through which anything outside reaches it."
That boundary separates it from a neighbour "only where it is declared and honoured - written down, and the only way the neighbour reaches it". Otherwise the two units "are one system for deciding what a change answers to".
Traits describe a system and axioms bind it, and "A trait's test is applied to a system, never to a task" (E5).
Systems relate in two ways only, contain and compose (E5).
A system is not by definition a repository, a deployment unit or a process, and size and traits do not define it. "A one-shot script with no traits is a system" (E5, Boundaries).
E6 adds that a component is "a system seen as a part of a larger system that contains it" (entities/E6-component.md).

### axiom-direction.Q1
The service is stateful, multi-agent and autonomous, so A1 binds it. A1 says "No functional unit possesses private, opaque, or transient truth" and names the "Hidden State Problem - state lives inside a process" as a fault (axioms/A1-sovereign-state-transparency.md). A5 Perceptual Parity also binds.
The component is a real gap, but A0 makes closing it mandatory only inside your change's scope: what the change "modifies, what it newly depends on, and any consumer whose contract it alters" (axioms/README.md).
Inside that scope, "new work never repeats a gap the axiom names". So your feature must keep its own state durable and queryable by the other agents. If it newly depends on the component, the component is "touched but not altered, so its gaps must not be built on". For example, your feature must not read or rely on that hidden in-memory state.
"Beyond the scope, improvement is considered, never mandated" (A0).
If the component is adjacent (it shares a declared interface; E6) and the A14 tangent test passes (payback is near, the yield is captured, and the cost does not distract from your goal), you may close the gap as a separate change. That change answers to every system it alters (A0; axioms/A14-compounding-learning.md).
Otherwise, record the gap with its evidence and a revival trigger (M5), because "larger choices of what work happens next are the director's" (R4, AR3, cited in A0).
Either way, "the gap is recorded. Passing it silently is what the axiom forbids" (A0).

### axiom-direction.Q2
An axiom is not a pass/fail test. It is a limit, an "asymptote", that the system is built toward to stay aligned with its intent. "a system is not wrong for being short of it; it is wrong for moving away from it" (axioms/README.md, "Standing commitment, not situated move").
In my own words, the axiom gives the change a direction. It sets a floor (no step backwards) and a requirement to move forward as far as the change's scope allows. A0: "No change may move the system away from the limit, and each change moves it toward the limit as far as the change's own scope allows."
A0 explicitly rejects the pass/fail reading as "The conformance reading". Under that reading nothing is owed, or nothing moves, "and the gaps the axioms name become permanent" (A0, Faults; see also the CORRECTION banner in "How the set composes").
The axioms bind together ("conjunctive in force"), so one axiom cannot be traded against another (A0).
A gate checks only what can be checked at the gate: that "the change moved the system no further from any limit in force, and repeated no gap it touched" (A0).

### OBSERVATIONS
- S2: E5 treats versioned interfaces differently (only an adopting consumer is altered), but the question does not say whether the session interface is versioned. The answer depends on that fact.
- S1/S2: E5 says containment exists "whether or not the module's interfaces are declared". So "no larger system containing both is declared" does not strictly prove that no containing system exists. I took it to mean that none exists.
- S5: A0 requires closing a touched gap "as much as the touch allows", but the corpus does not say how far a log-format change must go: declare an interface, move the service onto it, or only record the gap. My answer here is labelled GUESS.
- INDEX.md tells readers to resolve links against a checkout or against GitHub `main`. For a bounded corpus copy like this one, that could send a reader outside the corpus.
- A9 (Chaos-Validated Deployment) is tagged `any-system`, so it binds even a one-shot watched launcher script. A0 itself notes this as the "pointed case". It is consistent with the text but odd in practice.
- Q1: by T1's test (state that "persists beyond a single operation"), a component holding state only in process memory may not be stateful on its own. A1 still binds it because the stateful service contains it.
