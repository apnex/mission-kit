Preliminary trait classification, used by every system-boundary answer (from traits/T1-T5 and axioms/README.md "Applicability matrix", cross-checked against each axiom's `applies-to` frontmatter):
- Launcher: no traits. It is not stateful (T1), not declarative (T2), not multi-agent because one operator using a tool is one actor (T3: "One actor using several tools is not multi-agent"), not autonomous because a human watches it (T4 test), and has no model (T5). So only the `any-system` floor binds: A3, A4, A8, A9, A14 (E5 Boundaries: "A one-shot script with no traits is a system, bound by the axioms every system carries").
- Service: stateful (T1), multi-agent (T3), autonomous (T4); not declarative and not llm-in-the-loop. Axioms by union (T0 "Traits bind by union"): floor A3, A4, A8, A9, A14; plus A1 (stateful); plus A5, A6, A7, A10, A13 (multi-agent and/or autonomous). That is 11 axioms. A2 (declarative only) and A11, A12 (llm-in-the-loop only) do not bind.

### system-boundary.S1
Only the launcher's axioms: A3, A4, A8, A9, A14 (the `any-system` floor), because the launcher has no traits.
axioms/README.md "What brings an axiom into force" says "a change answers to every system it alters", and "A system it only composes with, through a contract the change leaves as it was, is not altered, and its axioms do not bind."
The launcher composes with the service through a declared interface that is honoured ("nothing crosses ... except a declared session interface"), and E5 gives this exact case as its example of Compose: "A launcher that hands sessions to a service through a declared interface composes with it."
The interface is unchanged, so the service is not altered, and its axioms (A1, A5, A6, A7, A10, A13) do not bind this change.

### system-boundary.S2
The union of both systems' axioms: A1, A3, A4, A5, A6, A7, A8, A9, A10, A13, A14. A2, A11 and A12 do not bind.
axioms/README.md: a change answers to "the system it modifies, every system containing it, and any system whose contract with it the change alters".
Changing the declared session interface alters the service's contract with the launcher, so the service is altered and its axioms bind as well as the launcher's floor.
E6 "Blast radius" agrees: a change reaches "an adjacent component only if the interface between them changes".
NOT SETTLED: whether this interface is versioned with separate adoption. E5 says a versioned contract "changes only for the systems that adopt the new version". If it were, the service would be altered only when it adopts the new version, and that adoption would be the change that answers to the service's axioms.

### system-boundary.S3
All 11 of the service's axioms: A1, A3, A4, A5, A6, A7, A8, A9, A10, A13, A14. That the module holds no state on its own makes no difference.
E5 Contain: "A module inside a service is a system, and the service contains it, whether or not the module's interfaces are declared", and "changing a module changes the service it sits in".
axioms/README.md: a change answers to "every system containing it".
E5 "Why precision matters" rules out the opposite reading: "a stateful system escapes its own axioms by being described as stateless modules, each of which passes on its own."
The module itself, as a system, carries only the floor (A3, A4, A8, A9, A14). The containing service adds A1, A5, A6, A7, A10 and A13.

### system-boundary.S4
Only the library's own axioms: the `any-system` floor A3, A4, A8, A9, A14 ("a plain library takes `any-system`", axioms/README.md matrix).
The ten consumers compose with the library through a declared, versioned interface. Your change leaves that interface and its behaviour unchanged, so no consumer is altered and their axioms do not bind (axioms/README.md, "What brings an axiom into force").
E5: "Publishing a new version of an interface alters no consumer that has not adopted it; each adoption is a change to that consumer, and answers to that consumer's axioms; the component is not altered by being adopted."
E5 "Why precision matters" names the error this avoids: "a small shared library would carry the axioms of every system that uses it, and the most-reused code would carry the most obligations."
When a stateful, multi-agent consumer later adopts the new version, that adoption answers to that consumer's axioms. Your library change does not.
Caveat: this depends on no consumer reaching past the interface. Any consumer that does stays one system with the library (E5 "Declared against honoured"). The question rules this out by saying the systems depend on the declared interface.

### system-boundary.S5
All axioms either unit brings: A1, A3, A4, A5, A6, A7, A8, A9, A10, A13, A14. A2, A11 and A12 still do not bind.
E5 Boundaries: "Where one unit depends on another and nothing declares the boundary between them ... they are one system, with the traits of both". axioms/README.md says the same: "the axioms either unit would bring all bind".
Something else is wrong. The undeclared dependency "is itself a fault under A3" (axioms/README.md; E5), which breaks A3's Air-Gap Principle ("units interact only through declared adapters and contracts").
The output the service parses is "a contract in fact, not a declared boundary - and a change to it reaches across" (E5). So a format change can break the service without anyone noticing.
Under the direction rule (axioms/README.md) your change touches that gap, so it must "close as much of it as the touch allows" and must not pass it silently. The fix E5 names is "Declaring the boundary, and moving the dependency onto it".
NOT SETTLED: whether the service parses the log line itself, since the question only says "some of" the launcher's output. The corpus makes the two units one system either way.

### system-boundary.S6
It is defined in entities/E5-system.md, under "Definition".
"A system is a unit of engineering with a boundary: what is inside it, and the contracts through which anything outside reaches it." The boundary separates it from a neighbour "only where it is declared and honoured".
"Traits describe a system, and axioms bind it". Systems relate in exactly two ways, Contain and Compose.
E5 Boundaries adds that a system is not a repository, deployment unit or process by definition, and is not defined by size or by traits. Units joined by an undeclared dependency count as one system.
E6 defines a component as "a system seen as a part of a larger system that contains it".

### axiom-direction.Q1
The service is stateful and multi-agent, so A1 binds. A1's mandate says "No functional unit possesses private, opaque, or transient truth; all state is perceivable by any authorized entity and durable across any infrastructure restart". This component is the "Hidden State Problem" fault and risks "Ephemeral Truth Loss". A5 and A7 ("Hydrated Startup") are also affected.
An axiom is an asymptote. Every change must not move the system away from the limit, and must move it toward the limit "as far as the change's own scope allows" (axioms/README.md, "Standing commitment, not situated move").
For your feature: do not repeat the gap, and keep your new state in the shared persistent store, not in memory ("new work never repeats a gap the axiom names"). Do not build on the component's hidden state ("its gaps must not be built on").
If your feature touches the component (modifies it or newly depends on it), you must close as much of the gap as the touch allows.
If not, and it is adjacent through a declared interface, you may fix it as a separate change, but only if A14's tangent discipline supports that (near payback, yield captured, no major distraction from your goal). Otherwise record it with its evidence and a revival trigger (M5), and leave the decision on that work to the director (R4, AR3).
Either way, you must record it: "Passing it silently is what the axiom forbids". Being in the same file or module only makes code "nearby", not touched or adjacent (axioms/README.md; E6).

### axiom-direction.Q2
An axiom is a limit the system is built toward, not a test to pass or fail. axioms/README.md: "a load-bearing asymptote - a limit a system is built toward to stay aligned with its architecture's intent".
When you change a system it binds, the axiom does two things. Your change must not move the system further from that limit. It must also move the system toward the limit as far as the change's scope allows ("never backwards, and forward with every step").
A system is not wrong because it is short of the limit, only because it moves away from it. That is why the charter's CORRECTION banner rejects the old reading of axioms as invariants that hold or fail.
In practice, your new work must not repeat a gap the axiom names, work that touches a gap must narrow it, and gaps you find outside your scope must be recorded, not passed silently.
All axioms in force bind at once and cannot be traded against each other ("conjunctive in force"). A gate checks only the backwards part: that the change moved the system no further from any limit and repeated no gap it touched.

### OBSERVATIONS

The service has no model in the loop, so it is unclear what A5 asks of it beyond its general rule ("perception precedes cognition").
- The "Applicability matrix" in axioms/README.md matches the `applies-to` frontmatter of all 14 axiom files. I found no drift.
- S2: whether a changed declared interface alters the other side at once or only when that side adopts it depends on whether the interface is versioned (E5). The question does not say which.
- S5: "parses some of the launcher's output" does not say whether the log line is part of what the service parses. E5 makes the two one system either way, but how likely an actual break is depends on it.
- INDEX.md tells the reader to resolve links from GitHub when there is no local checkout. That would leave the corpus, so I did not do it. All links I needed resolved inside the corpus directory.
- A0's sentence "a component the change newly depends on through a declared interface is touched but not altered ... its axioms do not bind the change" can look like it contradicts Q1. For a component inside the same service, the containing service's axioms bind anyway, so I read the sentence as being about the component's own extra axioms.
