### system-boundary.S6
Yes, it is defined in entities/E5-system.md: "A system is a unit of engineering with a boundary: what is inside it, and the contracts through which anything outside reaches it."
The boundary separates it from neighbours "only where it is declared". Units that depend on each other across an undeclared boundary are one system for binding purposes.
"Traits describe a system, and axioms bind it". A trait's test applies to a system, never to a task.
Systems relate in exactly two ways: contain (a module inside a service) and compose (through a declared contract).
E5 says a system is not a repository, deployment unit or process by definition, and is not defined by size or traits.
entities/E6-component.md adds that a component is "a system seen as a part of a larger system that contains it".

### axiom-direction.Q1
The service is stateful, multi-agent and autonomous, so A1 binds. Its mandate says "No functional unit possesses private, opaque, or transient truth", and its faults name the "Hidden State Problem" and "Ephemeral Truth Loss". A5 (multi-agent) binds as well.
A0 says an axiom binds every change in two directions: "No change may move the system away from the limit, and each change moves it toward the limit as far as the change's own scope allows".
For your feature, "new work never repeats a gap the axiom names". Its own state must therefore be durable and perceivable by the other agents, not kept in process memory. If the feature newly depends on that component, the component is touched but not altered, and "its gaps must not be built on" (A0).
If your feature touches the component (modifies it, newly depends on it, or alters its contract), you must close as much of the gap as the touch allows. Code that "merely sits beside it" is not touched.
If it is not touched, fixing it is "considered, never mandated". You may close it as a separate change if it is adjacent through a declared interface and passes A14's tangent discipline (near payback, yield captured, no significant distraction).
Otherwise, record it with its evidence and a revival trigger (M5), because what work happens next is the director's choice (R4, AR3). "Either way the gap is recorded. Passing it silently is what the axiom forbids" (axioms/README.md).

### axiom-direction.Q2
An axiom is a direction to build in, not a test to pass. axioms/README.md calls it "a load-bearing asymptote - a limit a system is built toward". A system "is not wrong for being short of it; it is wrong for moving away from it."
So when you change a system it binds, the axiom does two jobs at once. It forbids regression ("never backwards"), and it requires every change to move the system nearer the limit within its own scope ("forward with every step").
It is a standing commitment, "not advice you weigh against deadlines". Axioms are conjunctive, so none may be traded against another.
The charter keeps a correction banner showing that the pass/fail ("conformance") reading was rejected. Read that way, nearly every system fails and "the rule gives no direction".
A gate only checks the binary form: "that the change moved the system no further from any limit in force, and repeated no gap it touched".
Beyond the change's scope, an axiom asks only that gaps be considered and recorded, never silently passed.
