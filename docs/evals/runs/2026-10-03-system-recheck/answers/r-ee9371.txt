### system-boundary.S3

### system-boundary.S4
Only the library's own axioms, the floor: A3, A4, A8, A9, A14 (A0 matrix: "a plain library takes `any-system`"). The ten consumers compose with it through a declared contract that you leave unchanged, so they are not altered (A0). E5: "Publishing a new version of an interface alters no consumer that has not adopted it; each adoption is a change to that consumer, and answers to that consumer's axioms; the component is not altered by being adopted." E5 also names the opposite reading as the conflation to avoid: "a small shared library would carry the axioms of every system that uses it." Each consumer's later adoption is its own change, and that change answers to its own (stateful, multi-agent) axioms.

### system-boundary.S6
It is defined in entities/E5-system.md: "A system is a unit of engineering with a boundary: what is inside it, and the contracts through which anything outside reaches it." A boundary separates systems "only where it is declared". Where a dependency crosses an undeclared boundary, "the two are one system for deciding what a change answers to." Systems relate in exactly two ways: contain (a module inside a service) and compose (through a declared contract, with neither containing the other). "Traits describe a system, and axioms bind it". A trait test is applied to a system, never to a task. E5 Boundaries says a system is not a repository, a deployment unit or a process by definition, and is "Not defined by size or by traits" ("A one-shot script with no traits is a system"). E6 adds that a component is "a system seen as a part of a containing system."

### axiom-direction.Q1
The service is stateful, so A1 binds, and multi-agent, so A5 binds (plus A6, A7, A10, A13 and the floor). The component has A1's named faults: "No functional unit possesses private, opaque, or transient truth" (Hidden State Problem, Ephemeral Truth Loss), and other agents cannot perceive it (A5). A0's direction rule sets what you owe: "No change may move the system away from the limit, and each change moves it toward the limit as far as the change's own scope allows". So your feature must not repeat the gap ("new work never repeats a gap the axiom names"): put its state in the shared, durable store and not in process memory. Do not build on the component's hidden state either ("its gaps must not be built on"). If your feature touches the component (modifies it, newly depends on it, or alters its contract), close as much of the gap as the touch allows. If you do not touch it, closing the gap is "considered, never mandated": you may close it as a separate change if it is adjacent (shares a declared interface) and passes A14's tangent discipline. If not, record it with evidence and a revival trigger (M5), because A0 says "Either way the gap is recorded" and "Passing it silently is what the axiom forbids."

### axiom-direction.Q2
An axiom is a direction to build toward, not a test to pass. axioms/README.md calls it "a load-bearing asymptote - a limit a system is built toward", and says "a system is not wrong for being short of it; it is wrong for moving away from it." So for a change it says two things at once: "never backwards, and forward with every step". You build at the limit, or nearer to it than what was there, inside what the change touches. Beyond that scope, improvement is considered, never mandated, but any gap you see is recorded. A0 retains, under a CORRECTION banner, the earlier pass-or-fail reading it rejected, and lists "The conformance reading" as a fault, because under that reading no change ever moves the system forward. A gate fits this view: it checks that the change "moved the system no further from any limit in force, and repeated no gap it touched". The axioms are conjunctive, so you may not trade one axiom against another.

### OBSERVATIONS
- S2: the scenario does not say whether the declared session interface is versioned. E5's adoption rule changes the answer (the service is altered now, or only when it adopts the new version), so I assumed it is not versioned.
- Q1 does not say whether the service is autonomous or has a model in the loop, or whether the "cooperating agents" are independent actors (the T3 test). I assumed T3 holds and left T4 and T5 unstated; that changes A7, A10 and A13 only by which tag brings them in, since multi-agent already does.
- A0's rule leaves a small gap. It says a component the change newly depends on is "touched but not altered", so its axioms do not bind and its gaps "must not be built on". It also says "work that touches a gap closes as much of it as the touch allows." It is unclear how much a touch that only adds a dependency "allows" you to close, so Q1 and S5 depend on judgement here.
- E5 says two units with an undeclared dependency "do neither" (in Discriminators), then says they "are treated as one" (in Boundaries). The two statements are reconciled in the text, but the reconciliation sits in a different section from the first statement.
- S5: the corpus does not say whether touching an undeclared contract-in-fact obliges the change to declare it, or only to record the gap.
- INDEX.md tells readers to resolve links against a GitHub URL when there is no local checkout. That instruction is not relevant inside this sandboxed corpus.
