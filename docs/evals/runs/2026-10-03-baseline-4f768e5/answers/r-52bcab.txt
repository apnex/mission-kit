### system-boundary.S4
Only the library's own axioms: the floor, A3, A4, A8, A9, A14 ("a plain library takes `any-system`", `axioms/README.md` matrix).
The ten consumers are not altered. Their contract is unchanged, and E5 says "Publishing a new version of an interface alters no consumer that has not adopted it; each adoption is a change to that consumer, and answers to that consumer's axioms".
E5 rules out the opposite reading directly: "a small shared library would carry the axioms of every system that uses it, and the most-reused code would carry the most obligations" (Why precision matters).
When a consumer adopts the new version, that adoption is a separate change, and it answers to that consumer's axioms (A1, A5, A6 and so on), not the library change.

### system-boundary.S6
It is defined in `entities/E5-system.md` (ID E5): "A **system** is a unit of engineering with a **boundary**: what is inside it, and the contracts through which anything outside reaches it."
A boundary separates systems only where it is declared. Systems relate in exactly two ways: *contain* and *compose*.
A system is not defined by repository, deployment unit, process, size or traits. Traits describe it, and axioms bind it.
A *component* is "a system seen as a part of a containing system" (`entities/E6-component.md`).

### axiom-direction.Q1
The service is stateful and multi-agent, so A1 binds it ("No functional unit possesses private, opaque, or transient truth", `axioms/A1-sovereign-state-transparency.md`). A5 also binds it. Process-memory state is A1's named "Hidden State Problem".
A0 makes an axiom a limit, not a pass/fail test: "No change may move the system away from the limit, and each change moves it toward the limit as far as the change's own scope allows" (`axioms/README.md`).
For your feature: do not repeat the gap. Any state the feature adds goes in shared, durable, queryable state ("new work never repeats a gap the axiom names"). If you depend on that component, "its gaps must not be built on".
If your change touches the component, close as much of the gap as the touch allows.
If it does not, fixing the component is "considered, never mandated". You may fix it as a separate change if it is adjacent and passes A14's tangent discipline (near payback, yield captured, no significant distraction). Otherwise record it with evidence and a revival trigger (M5), because what happens next is the director's call (R4, AR3).
"Either way the gap is recorded. Passing it silently is what the axiom forbids."

### axiom-direction.Q2
An axiom is a limit (an "asymptote") that the system is built toward so it stays aligned with its architecture's intent. It is not a checklist the change must pass (`axioms/README.md`, "Standing commitment, not situated move").
For a change, it does two things at once: the change must not move the system away from the limit, and it must move the system toward the limit as far as its scope allows. "never backwards, and forward with every step."
A system short of the limit is not wrong for that. It is wrong only if it moves away. The "conformance reading" is a named fault because, under it, "no change advances the system" (A0 Faults).
Axioms are conjunctive and cannot be traded against each other. A gate can check the direction rule: the change moved no further from any limit and repeated no gap it touched.
