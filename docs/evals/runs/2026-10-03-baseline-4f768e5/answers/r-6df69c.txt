### component-a3.C5
Your change must not add to the accretion: "a change short of it adds none of them, and removes what it touches," where "them" includes "god objects, spaghetti coupling and dual-purpose modules", and the Faults list names "God-Object Accretion - "utils", "helpers", "managers" accumulate unrelated concerns."
So the feature should not go into `utils`; it should be its own unit, because "a module does exactly one thing" (Law of One), and "a new capability is assembled by composing existing units, never by modifying them" (Composable by Default).
If your change touches the `utils` module, the Mandate says the change "removes what it touches", but how much that covers is NOT SETTLED: it could mean only the concern you touch, or the whole bucket.
GUESS: pull the concern(s) your change actually touches out into a single-concern unit, and leave the rest of `utils` alone.
Do not make the new unit a stable public surface on speculation, because it "earns promotion to a stable, depended-upon surface only when a real consumer outside its origin needs it", and doing it early is the "Speculative Surface" fault.
How strictly an axiom binds a single change is deferred ("How an axiom binds a change is stated in [`A0`]"), so the exact obligation is NOT SETTLED by this file.

### OBSERVATIONS
- Two rules pull against each other. "Removes what it touches" requires changing the existing `utils` unit, but Composable by Default says capabilities are assembled "never by modifying" existing units. The file does not say which one wins when a change touches an accretion bucket.
- How far "removes what it touches" reaches is unclear: does it mean the touched concern, the touched lines, or the whole module?
- The binding rule for changes lives in A0, which this file points to but does not contain, so the strength of the obligation cannot be settled from A3 alone.
- "Bit-perfect semantic interfaces" / "bit-perfect message formats" is not defined, and the text gives no test for meeting it.
