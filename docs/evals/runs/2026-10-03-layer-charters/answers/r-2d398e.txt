### layer-charters.H5
A rule (`RU`) must declare `trace`. The catalog-entry schema's `allOf` requires it when the category is `rule` and the id matches `^RU[1-9][0-9]*$`. It must be a string of at least 20 characters stating "the observable trace a check could test".
A practice (`PC`) has no such requirement, and the schema says "a practice leaves none".
A rule may also declare `enforced-by`, which the schema calls optional: "Naming a tool that checks it is enforced-by's job, and is optional". When it is present, it must start with `tools/`, and `tools/check-enforcers.sh` checks `rules/RU*.md` so that the named tool exists.
Both take the common fields: `id`, `category`, `title`, `status` and `hydrate-when` are required, and `related`, `supersedes` and the others are optional. The test file `schemas/tests/catalog-entry/catalog-entry.test.mjs` confirms this ("a rule must declare the trace a check could test").
Caveat: this comes from the schema and tests only. Neither `rules/` nor `practices/` exists as a directory or charter in this corpus.

### layer-charters.H6
NOT SETTLED. No file gives an ordered decision procedure across all five, and no charter exists for methods (`methods/`), rules or practices.
The text supplies pieces. A0 asks first whether the guidance is a standing commitment or a situated move: an axiom is "not declinable" and "in force whether you reach for it or not" (M0 table, A0).
M0's boundary test then separates style from methodology: "what a reviewer would inspect ... If they would read the output, it is style. If they would have to know how you arrived at it, it is methodology."
The schema separates rules from practices: a rule leaves an observable trace, and "a practice leaves none".
GUESS at the order: (1) Is it always in force, not declinable? If yes, it is an axiom. (2) Is it judged by reading the artifact? If yes, it is style. (3) Is it a named procedure, a sequence that binds in a stated situation? If yes, it is a method. (4) Otherwise, does it leave an observable trace a check could test? If yes, it is a rule; if not, it is a practice.

### OBSERVATIONS
- The schema (`category` enum: `method`, `rule`, `practice`; id prefixes `RU` and `PC`), `catalog-entry.test.mjs` (CATALOGUE_DIRS lists `methods`, `rules`, `practices`) and `tools/check-enforcers.sh` (globs `rules/RU*.md`) all refer to layers that do not exist. There are no directories, no `RU0`/`PC0` charters, no README Mechanics rows and no INDEX sections for them. This breaks the README's layer-admission costs and E2's "every category names a knowledge layer". Both `methodology` and `method` are valid categories during the pending "Delta-1" rename.
- The schema's top-level `description` lists only eight categories ("axiom, style, methodology, role, pattern, domain, work-type or mission-required"), but its enum has seventeen.
- README.md calls INDEX.md "the flat ledger across every category", but INDEX.md is grouped by layer.
- The README Mechanics table lists `docs/`, which is absent from this corpus snapshot.
- M1 is titled "minimum 4 independent inputs" and its rule says "at least four", but its rationale says "sometimes 3 is enough" and "below 3 the failure mode is predictable", so the floor is stated inconsistently.
- E2 says "The three mechanism layers", but the README table lists four prefix-less layers (`bundles/`, `tools/`, `plugins/`, `docs/`).
