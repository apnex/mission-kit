### system-boundary.S6
It is defined in entities/E5-system.md.
"A system is a unit of engineering with a boundary: what is inside it, and the contracts through which anything outside reaches it."
The boundary separates it from a neighbour "only where it is declared and honoured". Traits describe a system and axioms bind it.
Systems relate only by "Contain" or "Compose". A system is "Not a repository, a deployment unit or a process by definition" and "Not defined by size or by traits".
E6 adds that a component is "a system seen as a part of a larger system that contains it".

### axiom-direction.Q1
The service is stateful, so A1 binds (A1 `applies-to: [stateful]`). Process-memory-only state is A1's named "Hidden State Problem" ("state lives inside a process; other actors reason about a different reality"), and it cuts against A5 too.
A0 ("Standing commitment, not situated move") says how far you must act depends on scope. Scope is what the change modifies, newly depends on, or whose contract it alters. Code "that merely sits beside it ... is not touched". So you are not mandated to fix an untouched component.
Your feature must be built at or nearer the limit: "new work never repeats a gap the axiom names". Keep your feature's state in the shared, durable, queryable store, not in process memory. If your feature depends on that component, "its gaps must not be built on".
If the component is adjacent (shares a declared interface), you may close the gap opportunistically, as its own change, under A14's tangent discipline. Otherwise record it with evidence and a revival trigger (RU3), because "larger choices of what work happens next are the director's".
"Either way the gap is recorded. Passing it silently is what the axiom forbids."

### axiom-direction.Q2
An axiom is a limit (an "asymptote") that the system is built toward. It is not a pass/fail test (axioms/README.md, "Standing commitment, not situated move").
It sets a direction for every change: "No change may move the system away from the limit, and each change moves it toward the limit as far as the change's own scope allows."
A system is not wrong for being short of the limit. It is wrong for moving away from it. Gaps outside your scope are considered and recorded, not ignored.
The CORRECTION banner in the same file records that the "holds or fails" reading was rejected, and A0's Faults list names it "The conformance reading". Under that reading, gaps "become permanent".
Gates check the direction rule: the change moved the system no further from any limit in force, and it repeated no gap it touched.
