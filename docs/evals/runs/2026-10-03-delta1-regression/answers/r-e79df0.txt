### component.C1
Y is outside the fix's scope: a change touches "what it modifies, what it newly depends on, and any consumer whose contract it alters" (axioms/README.md, A0), and your fix already called Y. But Y is adjacent to X, because X consumes Y's declared interface (entities/E6-component.md: adjacency is "a shared declared interface"), and it is the closer direction because X stands on Y. So A0 says the vague error "may be closed opportunistically when compounding learning supports it": the payback is near, the yield is captured, and the cost (five minutes, against twenty minutes of friction it caused) "does not significantly distract" (A0; A14 "Tangent discipline"). If you do it, make it "a change of its own" rather than folding it into X's unlanded fix. If changing the message alters Y's interface, Y's consumers are altered as well (A0, E5); whether error text is part of a declared interface is NOT SETTLED. Z is not adjacent: X does not use it and they share no interface, so they are "nearby and not adjacent" (E6). Two days would also displace the goal, so A0 says it "is recorded with its evidence and a revival trigger (RU3) rather than closed", and the choice of when to do it is the director's (R4, AR3). Either way both gaps must be recorded, because "Passing it silently is what the axiom forbids" (A0); Z's hidden state is A1's "Hidden State Problem", and A1 binds only if the service is `stateful`.

### component.C2
It is defined in entities/E6-component.md: a component is "a system seen as a part of a larger system that contains it", with "one duty at the altitude where it appears as a part", and it "exposes and consumes interfaces". "Every component is a system; component names its place in a containing system, not a different kind of thing" (E6). The difference is which question you are asking: "Traits, axioms and what a change answers to are questions about a system. Duty, interfaces, neighbours and blast radius are questions about a component" (E6; also E5-system.md "A system against a component"). A system that nothing contains "is not a component of anything" (E6). A system is "a unit of engineering with a boundary", and relates to other systems by contain or compose (E5). The registered entries in components/ (C0) are a narrower idea: "Most components are never registered" (E6).

### component.C3
No. "A component's directory addresses it ... Its boundary is its declared interfaces" (E6, "Boundary against directory"), and a directory "is the boundary of neither the system nor the component" (E5; also artifacts/README.md). The fault is that parts/other/ reaches into parts/thing/'s internals with no declared interface. This breaks A3's Air-Gap Principle ("no unit reaches into another's internals"), and E5 names "the undeclared dependency" as "itself a fault against A3". So, for what a change answers to, thing and other "are one system, with the traits of both" (E5 Boundaries; E6; A0). parts/thing/ is still a component, "but nothing separates it yet" (E6). They are also not adjacent, because adjacency needs a declared interface. The remedy is to declare the interface and move the dependency onto it: "Declaring the boundary, and moving the dependency onto it, is what makes them two again" (E5).

### component.C4
The change answers to P's axioms and to the axioms of every system that contains P (the service and anything above it): "the system it modifies, every system containing it, and any system whose contract with it the change alters" (A0; E5 "changing a module changes the service it sits in"). Q is not altered. "A system it only composes with, through a contract the change leaves as it was, is not altered, and its axioms do not bind" (A0). This holds only if Q honours the interface. If Q bypassed it, the two would stay one system (E5 "Declared against honoured"). Q is not touched either, but it is adjacent, because Q consumes what P exposes (E6). A0 allows opportunistic improvement of a component "it stands on, or one that stands on it", so Q is a candidate. It is the weaker direction, though: "adjacency with less payback, not none" (E6). It is subject to the A14 tangent tests, must be made as its own change, and must be recorded either way (A0).

### OBSERVATIONS
- A0's scope rule covers only what a change "newly depends on". It does not say whether an existing dependency that the fix exercises (Y in C1) counts as touched. I read it as not touched but adjacent; the text does not state this directly.
- Whether an error message is part of a declared interface is not settled. E5 treats "parsing output the interface does not promise" as a bypass, which suggests that callers depending on the error text would not be using the interface.
- A14's tangent discipline defines adjacency in one direction only ("sits under load-bearing infrastructure the main line will stand on"). A0 and E6 define it in both directions. E6 reconciles the two explicitly, but A14 read alone suggests that Q in C4 is not adjacent.
- A3's mandate says "Every module is a self-contained sovereign unit", but E6 says a module is not a component by definition. These are probably compatible (A3 states a limit), but the wording is loose.
- INDEX.md says to fetch from GitHub when no local checkout exists. I used only the local corpus, as instructed.
