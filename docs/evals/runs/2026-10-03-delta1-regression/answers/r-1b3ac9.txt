### component.C1
Your change answers to X and to every system containing X, i.e. the service (axioms/README.md: "a change answers to every system it alters ... the system it modifies, every system containing it"); Y and Z are outside its scope, so for both "improvement is considered, never mandated", and passing either gap silently "is what the axiom forbids".
Y: X consumes Y's declared interface, so Y is adjacent to X in the closer direction ("the one the other stands on is the closer", entities/E6-component.md), and A0 says such a gap "may be closed opportunistically when compounding learning supports it": payback is near, the yield is captured, and the cost "does not significantly distract" from the goal. A five-minute fix to friction that cost twenty minutes passes that test, and A14's mechanic "Friction -> root cause, never workaround" points the same way.
If you do it, make it "a change of its own, so its yield is captured and its cost is visible", and that change answers to Y, to the service, and to any consumer whose contract it alters (A0). GUESS: whether a new error message alters Y's contract depends on whether the interface promises the message text; E5 treats a consumer that parses output the interface does not promise as a bypass.
Z: X does not use Z, so Z is not adjacent, and two days would displace the goal. So A0 says record it "with its evidence and a revival trigger (RU3) rather than closed", because what work happens next is the director's call (R4, AR3).
Hidden important state in process memory is the A1 "Hidden State Problem", and A1 binds the service if it is stateful (traits/T1-stateful.md). Because your change answers to the service, it must not move the service further from A1, but it is not required to fix Z.
NOT SETTLED: whether the service passes T1's test. That it "keeps important state" suggests it does, but the corpus cannot decide it for you.

### component.C2
It is defined in entities/E6-component.md: "A component is a system seen as a part of a larger system that contains it", with "one duty" at the altitude where it is a part, and it "exposes and consumes interfaces".
It is not a different kind of thing: "Every component is a system; component names its place in a containing system". The difference is which question you are asking. "Traits, axioms and what a change answers to are questions about a system. Duty, interfaces, neighbours and blast radius are questions about a component" (E6; also entities/E5-system.md, "A system against a component").
A system that nothing contains, "such as a whole product seen from outside, is not a component of anything" (E6).
A system is defined in E5 as "a unit of engineering with a boundary", and systems relate by contain or compose.
A component is not by definition a file, module, repository, directory, registered component (components/) or SysML part (E6 Boundaries).

### component.C3
No. "A directory places a component's documents; it is the boundary of neither the system nor the component" (E5), and a component's "boundary is its declared interfaces" (E6, "Boundary against directory").
parts/thing/ is still a component ("A part whose interfaces are undeclared is still a component, but nothing separates it yet", E6). Because parts/other/ depends on it with no declared boundary, the two are "one system, with the traits of both" for deciding what a change answers to (E5 Boundaries; A0).
What is wrong: the undeclared dependency "is itself a fault against A3" (E5), which breaks the Air-Gap Principle ("no unit reaches into another's internals", axioms/A3-sovereign-composition.md).
The remedy is "Declaring the boundary, and moving the dependency onto it" (E5). Under A3 "Earned Exposure", parts/other/ is a real consumer, so it can justify a declared surface.
GUESS: A3's "Bypass as Signal" is written for reaching past a declared interface. Here no interface exists, but an evaluation against thing's duty seems the right way to decide what that interface should offer.

### component.C4
Your change answers to P and to every system containing P, including the service (A0: "the system it modifies, every system containing it"; E5).
Q is not altered: "A system it only composes with, through a contract the change leaves as it was, is not altered, and its axioms do not bind" (axioms/README.md). The E6 blast-radius row reaches "an adjacent component only if the interface between them changes".
That holds only if Q actually uses the interface. If Q reaches past it, Q and P are one system and Q is in scope (E5, "Declared against honoured").
Q is adjacent to P because they share a declared interface (E6), so Q is a candidate for opportunistic improvement under A0 and A14's tangent discipline. Q stands on P, not the other way round, so this is "adjacency with less payback, not none" (E6).
Any such improvement must pass A0's test (payback, yield captured, cost does not distract), and it must be made as a separate change or recorded with a revival trigger.

### OBSERVATIONS
- A0 says a change touches "what it newly depends on". X's existing dependency on Y is not new, so whether Y counts as touched (in scope) or only adjacent is slightly unclear. Adjacency to X still makes Y a candidate either way.
- A14's "Friction -> root cause, never workaround" reads like a mandate. A0 says improvement beyond a change's scope is "considered, never mandated". The two are reconciled only by reading A14 through A0's tangent discipline.
- The corpus does not say whether an opportunistic change should land before or after the main fix. Here that matters because the X fix is written but not landed.
- "Bypass as Signal" (A3) is scoped to declared interfaces. The case with no declared interface (C3) has no stated evaluation trigger, only E5's "declare and move the dependency".
- Whether changing error-message text alters an interface contract is not addressed.
