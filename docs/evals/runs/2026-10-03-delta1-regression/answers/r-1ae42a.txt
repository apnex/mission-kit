Trait readings used below (from traits/T1..T5 tests and axioms/README.md "Applicability matrix", cross-checked against each axiom's `applies-to` frontmatter):
- Launcher: no traits. Not T1 (holds no state), not T2 ("a script run once" is listed as not declarative), not T3 (one operator; T3 says tools are not independent actors), not T4 (the operator watches it, so a human sees a failure), not T5. It carries only the `any-system` floor: A3, A4, A8, A9, A14.
- Service: T1 stateful (A1), T3 multi-agent (A5, A6, A7, A10, A13), T4 autonomous (A7, A10, A13). Not T2, not T5. Union with the floor: A1, A3, A4, A5, A6, A7, A8, A9, A10, A13, A14. A2, A11 and A12 do not bind it.

### system-boundary.S1
Only the launcher's axioms apply: A3, A4, A8, A9, A14.
axioms/README.md says "a change answers to every system it alters... A system it only composes with, through a contract the change leaves as it was, is not altered, and its axioms do not bind."
The launcher and service compose, because they "reach each other only through a declared contract that can stay unchanged while either side changes" (entities/E5-system.md, "Contains against composes"). Nothing reaches past that contract, so the boundary is also honoured.
No larger system containing both is declared, so there is no containing system's axioms to add.
The service's extra axioms (A1, A5, A6, A7, A10, A13) do not bind this change.

### system-boundary.S2
The change answers to the launcher's axioms and the service's axioms. Together: A1, A3, A4, A5, A6, A7, A8, A9, A10, A13, A14 (not A2, A11, A12).
axioms/README.md: a change alters "any system whose contract with it the change alters", and changing the declared session interface alters the service's contract.
NOT SETTLED: whether the session interface is versioned. E5 says "A versioned contract changes only for the systems that adopt the new version". If the interface is versioned, publishing the new version answers only to the launcher's axioms, and the service's adoption is a separate change that answers to the service's axioms.
GUESS: the scenario means an unversioned interface changed in place, so the full union applies.

### system-boundary.S3
All of the service's axioms apply: A1, A3, A4, A5, A6, A7, A8, A9, A10, A13, A14.
axioms/README.md: a change answers to "the system it modifies, every system containing it".
E5 says "A module inside a service is a system, and the service contains it, whether or not the module's interfaces are declared".
That the module holds no state on its own does not matter. E5 "Why precision matters" names the failure where "a stateful system escapes its own axioms by being described as stateless modules, each of which passes on its own."
The module's own traits only add to that set. They cannot take anything away from it (traits/README.md: "Adding a trait to a system can only add obligations").

### system-boundary.S4
Only the library's own axioms apply. It has no traits, so that is the floor: A3, A4, A8, A9, A14.
E5: "Publishing a new version of an interface alters no consumer that has not adopted it; each adoption is a change to that consumer, and answers to that consumer's axioms".
The interface and its behaviour are unchanged, so no consumer's contract is altered. The dependents compose with the library rather than contain it, so their axioms (A1, A5 and so on) do not bind.
E5 "Why precision matters" rejects the opposite reading by name: "a small shared library would carry the axioms of every system that uses it".
This holds only while every dependent honours the interface. A dependent that reaches past the interface "stays one system with it" (E5, "Declared against honoured"), and then that dependent's axioms would bind.
The scenario does not say whether any dependent bypasses the interface. GUESS: they all honour it.

### system-boundary.S5
For this change the launcher and the service count as one system with the traits of both. The change answers to A1, A3, A4, A5, A6, A7, A8, A9, A10, A13, A14.
E5 Boundaries: "Where one unit depends on another and nothing declares the boundary between them... they are one system, with the traits of both". It also says "Behaviour another unit depends on without any declaration is a contract in fact... and a change to it reaches across". Here the log format is that contract in fact.
Something else is wrong: "The undeclared dependency is itself a fault against A3, which requires units to interact only through declared contracts" (E5; A3 "Air-Gap Principle").
Your change touches that gap. A0 says "work that touches a gap closes as much of it as the touch allows", so you should declare the boundary and move the parsing dependency onto it. E5: "Declaring the boundary, and moving the dependency onto it, is what makes them two again."
If you do not close the gap, A0 still requires recording it: "Passing it silently is what the axiom forbids."
In practice, the format change may also break the service's parser.

### system-boundary.S6
It is defined in entities/E5-system.md.
The definition: "A system is a unit of engineering with a boundary: what is inside it, and the contracts through which anything outside reaches it." The boundary separates it from a neighbour "only where it is declared and honoured".
Systems relate in exactly two ways: they contain one another, or they compose through a declared contract.
"Traits describe a system, and axioms bind it". A system is not a repository, deployment unit or process "by definition". It is also not defined by size or traits: "A one-shot script with no traits is a system".
entities/E6-component.md adds that a component is "a system seen as a part of a larger system that contains it".

### axiom-direction.Q1
The service is stateful, so A1 binds it. The component is an instance of A1's "Hidden State Problem": "No functional unit possesses private, opaque, or transient truth". Its invisibility to other agents also falls short of A5, which binds through multi-agent.
How far you must act depends on your change's scope (axioms/README.md): "Beyond the scope, improvement is considered, never mandated."
If your feature modifies that component, you must close as much of the gap as the touch allows.
If your feature depends on it, it is "touched but not altered, so its gaps must not be built on". Do not rely on its in-memory state.
If the component is adjacent, you may close the gap opportunistically, as a separate change, under A14 tangent discipline. Otherwise record it "with its evidence and a revival trigger (RU3)". Either way, "the gap is recorded. Passing it silently is what the axiom forbids."
For your own feature: "new work never repeats a gap the axiom names". Keep its state in the shared, durable backplane and keep its components stateless (A1 Mechanics).
NOT SETTLED: whether the component is adjacent or touched. The scenario does not say.

### axiom-direction.Q2
An axiom gives a change a direction to move in. It is not a test the change passes or fails.
axioms/README.md calls it "a load-bearing asymptote - a limit a system is built toward". "a system is not wrong for being short of it; it is wrong for moving away from it."
When I change a bound system, the axiom applies in two ways at once: "No change may move the system away from the limit, and each change moves it toward the limit as far as the change's own scope allows."
So new work must not repeat a named gap, and work that touches a gap should close what it can. Gaps outside the scope are considered, and recorded if not closed.
The corpus kept its earlier pass/fail wording under a CORRECTION banner and names that reading as a fault ("The conformance reading"), because under it "no change advances the system".
A gate stays binary, but what it checks is this direction rule: that the change "moved the system no further from any limit in force, and repeated no gap it touched".

### OBSERVATIONS
- INDEX.md tells readers to fetch from a remote raw URL when there is no local checkout. Under this eval's constraints I used only the local corpus files and fetched nothing.
- S2: the corpus has a rule for versioned contracts (E5) but the scenario does not say whether the session interface is versioned, so the answer depends on that.
- A0's scope rule says a gap beyond scope is "recorded" with a revival trigger. It is a little unclear whether recording is required for every gap you notice, or only for adjacent ones you decline to close. The sentence "Either way the gap is recorded" points to every gap, but it sits inside the paragraph about adjacent gaps.
- T3 applied to the launcher: a human operator plus a script. T3 counts "a human reviewing an agent's output" as multi-agent, but a script is a tool, not an independent actor. I read the launcher as not multi-agent. The corpus does not address a human-plus-script pair directly.
- I checked A0's claim of "thirty-five relations axioms declare to one another" against the axiom `related` fields: 35 references to axioms. It matches. I did not check the citation-count table.
- I compared the A0 applicability matrix with each axiom's `applies-to` frontmatter. They agree.
